# D0 数据制备版本对照（证据 E01 补充）

- 采集时间：2026-11-16 04:10–04:25（Asia/Shanghai），本机 Windows + 服务器 `lavm-txyjj7xzr7`
- 目的：交接包指出「服务器与本地两个数据制备脚本存在功能差异」。本轮用**同一输入、同一窗口**分别跑两版，判断差异是否会改变业务输出，并决定部署哪一版。
- 产物目录：`.tmp/handover/d0/`（不入库，可重跑再生）

## 一、方法

| 域 | 输入 | 两版差异 | 对照方式 |
| --- | --- | --- | --- |
| 交易域 UCI | `.tmp/realdata/uci/combined.pkl`（1,067,371 行缓存，sha 见日志） | 本地默认全量两年并可用 `--win-lo/--win-hi` 覆盖；服务器版固定 2011-11-01~12-01 且无参数 | 两版都跑 **2011-11-01 ~ 2011-12-01**（本地显式传窗口，服务器版用其默认窗口），输出逐文件比对 |
| 流量域 天池 | `.tmp/realdata/tianchi/traffic_events.csv`（10,098,974 行抽样文件） | 本地按商品出现次数取**主导类目**并断言主键唯一；服务器版按 `(product_id, category_id)` 分组 | 同一输入文件分别构建，输出逐文件比对 |

## 二、交易域结果：两版**逐行完全相同**

| 产物 | 本地版行数 | 服务器版行数 | 行数 | 整行集合 |
| --- | ---: | ---: | --- | --- |
| orders.csv | 62,937 | 62,937 | 相同 | **完全相同** |
| payment.csv | 62,937 | 62,937 | 相同 | 完全相同 |
| refund.csv | 578 | 578 | 相同 | 完全相同 |
| product.csv | 2,690 | 2,690 | 相同 | 完全相同 |
| user.csv | 1,660 | 1,660 | 相同 | 完全相同 |
| Σ orders.amount | 1,135,997.00 | 1,135,997.00 | 相等 | — |
| Σ payment.amount | 1,135,997.00 | 1,135,997.00 | 相等 | — |
| Σ refund.refund_amount | 16,500.73 | 16,500.73 | 相等 | — |

结论：两版在 UCI 上的**清洗与派生逻辑等价**，唯一差别是「窗口是写死还是可配置」。本地版是严格超集（默认可复现全量，也能切子窗口做对照），因此选用本地版。

## 三、流量域结果：商品维度差 356 行

| 产物 | 本地版 | 服务器版 | 结论 |
| --- | ---: | ---: | --- |
| tianchi_user.csv | 100,000 | 100,000 | 相同 |
| tianchi_behavior.csv | 10,098,974 | 10,098,974 | 相同 |
| ↳ 事件类型分布 | VIEW 9,045,077 / CART 559,566 / FAVORITE 290,869 / BUY 203,462 | 同左 | 一致 |
| tianchi_product.csv 行数 | 1,598,617 | **1,598,973** | 不同 |
| ↳ 唯一 product_id | 1,598,617 | 1,598,617 | — |
| ↳ **重复主键行数** | **0** | **356** | 服务器版会写出重复主键 |

结论：服务器版按 `(product_id, category_id)` 分组，同一商品挂过多个类目时会写出多行，装载时主键冲突（或用 UNIQUE KEY 静默覆盖，导致类目不确定）。必须部署本地版。

## 四、三处版本不一致（本次最重要的发现）

同一件事在三个位置是**三个不同版本**：

| 位置 | 实际版本 | 证据 |
| --- | --- | --- |
| 已装载进数据库的 CSV | **新版（去重）** | 服务器 `data-generator/data/real/tianchi_product.csv` sha256 = `2f2f02379a0c321bda04df9e2bc389134b435ee201c2586567a14507fcd012b8`，与**当前本地脚本**在同一输入下重新构建的产物**逐字节相同**（98,447,014 B / 1,598,617 行 / 0 重复） |
| 服务器上的制备脚本 | **旧版（不去重）** | 部署前 `build_tianchi_dataset.py` sha256 前 16 位 `162835b8ee2c1dc1`，产出 1,598,973 行 / 356 重复 |
| 本地 `.tmp/realdata/upload/` 暂存件 | **旧版产物** | `tianchi_product.csv` 98,468,951 B / 1,598,973 行 / 356 重复 |

这正是交接包提醒的那句话：**脚本版本不同，不能推出已装载数据有误**。反过来也成立：数据是对的，但脚本和暂存件仍是旧的，任何一次「按服务器脚本重制再上传」都会把数据做坏。

## 五、已采取的动作

1. 部署两版脚本到服务器（小范围、可回滚，只动这两个文件）：
   - `scripts/real-data/build_uci_dataset.py`：`bc0211952836ed98` → `f760bb21ff7f1e0d`（LF 归一化 sha256 前 16 位）
   - `scripts/real-data/build_tianchi_dataset.py`：`162835b8ee2c1dc1` → `9cca081d63de6f44`
   - 部署后 `python -m py_compile` 通过（`COMPILE_OK`）
2. 本地暂存件 `.tmp/realdata/upload/tianchi_product.csv` 换成去重版，sha256 = `2f2f0237…`，与服务器已装载文件一致。
3. 未重跑装载、未重放 Kafka、未改动任何数据库表。

回滚办法：两个脚本的旧版仍可从未部署前的哈希对应的历史版本取回（`git log` 中早于真实数据改造的提交），或用 `.backup/20261106_042632/` 恢复；本次改动仅替换文件，不涉及数据。

## 六、复现命令

```powershell

python scripts/real-data/build_uci_dataset.py --win-lo "2011-11-01 00:00:00" --win-hi "2011-12-01 00:00:00" --out .tmp/handover/d0/uci_local
python .tmp/handover/remote/scripts__real-data__build_uci_dataset.py --out .tmp/handover/d0/uci_remote

# 流量域：同一输入对照

# 汇总
python .tmp/handover/d0_report.py
```
