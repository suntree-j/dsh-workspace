## 一、定位

### 1.1 现象一：归档任务每晚失败，其后 11 个阶段全部 `upstream_failed`

Airflow 元数据（MySQL `airflow` 库，`task_instance` 表）实测：

| 任务 | failed | success | upstream_failed |
|---|---|---|---|
| `archive_behavior` | **24** | 18 | 0 |
| `ods_extract` | 3 | 42 | 0 |
| `restore_realtime` | 2 | 43 | 0 |
| 其余阶段（含 traffic 系列） | 0 | 18 | **27**（traffic 系列 16/24） |

`dag_run` 最近 8 次全部 `success`，且这 8 次的 `archive_behavior` 与 `restore_realtime` 都是 `success`
——说明失败是**周期性复现**、不是一次性事故，且当 topic 有数据时链路是通的。

### 1.2 现象二：调度链从不执行 `iceberg-migrate`

`airflow/dags/offline_lakehouse_pipeline.py` 的链路在修改前是：

```
pause_realtime → ods_extract → archive_behavior → dwd_layers → dws_layers → ads_layers
→ traffic_dwd_layers → traffic_dws_layers → traffic_ads_layers → reconcile
→ traffic_reconcile → load_to_doris → restore_realtime
```

`load_to_doris` 之后直接是 `restore_realtime`，**没有 `iceberg-migrate`**。
而论文中"湖仓"指的是 Iceberg 库 `iceberg.lakehouse_iceberg` 的 23 张表；
`migrate_parquet_to_iceberg.py` 只能靠人工 `bash scripts/batch-mode.sh` 触发。
推论：只靠调度跑几天，Hive/Parquet 与 Iceberg 必然分叉，且分叉在页面上看不见。

### 1.3 触发条件与代码入口

| 现象 | 触发条件 | 代码入口 |
|---|---|---|
| 归档每晚失败 | `behavior_event` 消息被 retention 清空后再次运行归档 | `infrastructure/spark/jobs/archive_behavior_events.py` 的 `verify()` 旧判据「整表行数 == 本次 Kafka 消息数」 |
| Iceberg 落后 | 只靠 Airflow 定时触发、不手工跑 `batch-mode.sh` | `airflow/dags/offline_lakehouse_pipeline.py` 缺 `iceberg_migrate` 任务 |

### 1.4 为什么旧判据必然失败

`behavior_event` 没有显式 retention 覆盖，继承 broker 默认 `log.retention.hours=168`。
消息过期被删后：

- 本次从 topic 读到 **0** 条；
- 湖仓 `lakehouse.ods_behavior_event` 仍保留 **10,098,974** 行历史归档（这是设计意图：归档是 topic 的超集）；
- 旧判据比的是「整表 10,098,974 == 本次 0」→ **永远不成立** → 归档判失败 → 其后全部 `upstream_failed`。

实测现状（2026-11-16 05:16）：

```
behavior_event 消息数 10,098,974，earliest offset 0，无显式 retention 覆盖
lakehouse.ods_behavior_event: 10,098,974 行 / 9 个 dt 分区
逐日：11-25 1,048,300 / 11-26 1,069,923 / 11-27 1,018,571 / 11-28 996,923 / 11-29 1,038,260
      11-30 1,054,775 / 12-01 1,097,244 / 12-02 1,386,445 / 12-03 1,388,533
```

## 二、改动

### 2.1 判据抽成纯函数并改成 retention-safe 口径

新增 `infrastructure/spark/jobs/archive_criteria.py`（53 行，无 pyspark 依赖）：

```python
def archive_criteria(kafka_count, archived_total, archived_touched, parsed_count)
    -> list[tuple[str, bool, str]]
```

规则：

1. `kafka_count == 0` → 只记录「本次无新消息（topic 已被 retention 清空，归档保留历史）」，**通过**；
2. `kafka_count > 0` → 比「**本次覆盖的 dt 分区行数** == Kafka 消息数」，另加「整表行数 ≥ 本次消息数（归档是 topic 的超集）」；
3. 无论哪种情况都比「可解析行数 == Kafka 消息数」。

`archive_behavior_events.py` 的 `verify()` 改为调用它并逐条 `checker.check_true`，
不再把判据写死在方法体里（原来无法单测）。

**为什么单独成文件**：作业脚本顶层 `import pyspark`，在无 Spark 的机器上无法 import 做单测；
把判据放到无依赖模块里，测试才能直连。作业用 `from archive_criteria import archive_criteria` 导入
（`spark-submit` 会把脚本目录放进 `sys.path[0]`，已验证）。

### 2.2 调度链补上 `iceberg-migrate`

```python
iceberg_migrate = _stage("iceberg_migrate", "iceberg-migrate", "把 Parquet 发布为 Iceberg 表")
... >> load_to_doris >> iceberg_migrate >> restore_realtime
```

`restore_realtime` 仍是 `trigger_rule="all_done"`，所以迁移失败也不会把实时链路留在暂停状态。

### 3.2 新判据在真实数据上成立（纯 SQL，不重跑归档）

按 `verify()` 同口径计算「本次覆盖的 dt 分区行数」（当前 topic 含全部 9 天，故 touched 即全表）：

```sql
SELECT COUNT(*) AS ods_rows, COUNT(DISTINCT dt) AS days FROM lakehouse.ods_behavior_event;
-- 10098974 | 9
SELECT SUM(c) FROM (SELECT dt, COUNT(*) c FROM lakehouse.ods_behavior_event GROUP BY dt) t;
-- 10098974
```

`archived_touched 10,098,974 == kafka_count 10,098,974` ⇒ 判据 1、2、3 全通过。
（这正是旧判据在新数据上也会通过的场景——因为 topic 还没被清空；旧判据的失败形态要等清空后才出现，
所以这里只能证明"新口径在正常态不误报"，异常态由 3.1 的单测覆盖。）

### 3.5 一次失败的验证尝试（结论：归档必须与实时链路互斥）

在 Flink 8 个作业 RUNNING、available ≈ 4.4 GB 的情况下单跑
`MIN_AVAILABLE_MB_FOR_BATCH=2200 bash scripts/run-batch-pipeline.sh --stage archive`：

```
26/11/16 05:15:46 ERROR TaskSchedulerImpl: Lost executor 0 on 172.28.0.3: Command exited with code 137
26/11/16 05:15:46 WARN TaskSetManager: Lost task 0.0 in stage 29.0 (TID 38) ... ExecutorLostFailure
[archive] 开始自检   ← 写入完成后、自检查询阶段被 OOM kill
```

`exit 137` = 被 OOM killer 杀死。这条**不是**缺陷，而是把「为什么 DAG 第一步是 `pause_realtime`」
和「为什么有 `MIN_AVAILABLE_MB_FOR_BATCH` 闸门」用现场证据固定下来：
Kafka 批量读 1,010 万条 + 归档写入与自检查询的内存峰值，与 Flink 常驻内存之和超过 16 GB。

**失败未损坏数据**：事后实测 `lakehouse.ods_behavior_event` 仍是 10,098,974 行 / 9 天，
行为分布 VIEW 9,045,077 / CART 559,566 / FAVORITE 290,869 / BUY 203,462 不变；Flink 8 作业仍 RUNNING。
