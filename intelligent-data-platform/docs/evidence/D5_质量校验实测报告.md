## 一、定位

### 1.1 这份报告要解决的问题

在此之前，"质量校验"在材料里只有一个结论：**25 条全部通过**。
这个说法有两个缺陷：

1. **不可复核**：读者不知道这 25 条各自在防什么、实测值是多少，
   也无法判断"通过"是因为数据真的对，还是因为判据写得太松（恒真）。
2. **混淆了"执行方式"与"是否覆盖"**：湖仓那条在 `--all` 模式下打印 `SKIP`，
   实际是在脚本末段由 `--with-lake` 单独执行的——只报数字不报结构，容易被读成"有一条没跑"。

### 1.2 与 D3 的关系（同一类问题的两个侧面）

D3 修的是**归档判据**（拿"整表行数"比"本次消息数"，topic 被清空后必然失败）；
D5 要把"判据本身是否可信"这件事做成**可逐条复核的清单**。
两者共同的前提是：判据如果写错，会同时制造假通过与假失败。

## 二、改动

本轮**没有修改任何校验代码**。理由：25 条判据在真实数据上确实成立，
现在需要的是把结论变成可复核的清单，而不是为了"做点改动"去动已经正确的判据。

唯一的结构性说明（写进文档、不改代码）：`--all` 模式下那条 `SKIP`
是**执行方式标注**，不代表未覆盖——脚本在 Doris 侧跑完后，用 `--with-lake`

### 3.2 失败路径证明（`--proof-fail`）

只报"全部通过"不够，还要证明**失败真的会大声失败**，否则无法排除"退出码恒为 0"的脚本假象：

```
  [ OK ] 演示 1 退出码 = 1（期望 1）—— 失败真的会 exit 1
  [ OK ] 演示 2 退出码 = 1（期望 1）—— 失败真的会 exit 1
```

做法：不改数据库，只把某条判据的**期望值**换成不可能出现的值，再跑一次——
脚本必须以 `exit 1` 结束；随后立即复跑正常校验，应重新全绿
（证明失败来自断言，不是数据被改坏）。

| 退出码 | 含义 |
|---|---|
| 0 | 全部 error 级校验通过 |
| 1 | 有 error 级校验失败（大声失败，不是"无论如何返回 0"） |
| 2 | 湖仓侧被内存闸门**拒绝执行**（不是失败的另一种说法） |
