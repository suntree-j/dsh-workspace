## 一、定位

### 1.1 现象

顶栏右侧有一个时间戳，标签写的是「**数据时间**」，取值为页面加载时刻（例如 `2026-11-16 05:34:12`）。
但本平台的数据是两份**公开历史数据集**：交易域 2009-12～2011-12、流量域 2017-11～2017-12。
把"我什么时候取的数"标成"数据时间"，会直接读成"数据更新到了今天"。

同一页的指标卡还挂着环比徽标：GMV `▼ -26.5%`、订单量 `▲ +275.0%`、支付金额 `▼ -26.5%`。
这些数字来自 `buildDelta()`：比较**最后两个分钟窗口**。
在实时链路上这是"最近的变化"，在本平台上是"某个历史日最后两分钟之间的差额"——
读起来像"业务今天在跌 26.5%"，与事实无关。

### 1.2 触发条件

- 顶栏：任何页面都会出现（顶栏是全局组件）。
- 环比徽标：数据集的最后一个窗口距当前超过 48 小时时必现（历史数据集恒满足）。

### 1.3 代码入口

| 位置 | 问题 |
|---|---|
| `services/web/index.html:1743` | 标签写死「数据时间」，绑定的是 `updatedText` |
| `services/web/app.js:1048` | `updatedAt.value = formatDateTime(new Date().toISOString())` —— 客户端时钟，不是数据时间 |
| `services/web/app.js:470` `buildDelta()` | 只判断"两个窗口是否非零"，没判断"这两个窗口是不是历史" |

### 1.4 与交接包的关系

交接包第四节要求逐个入口确认「日期契约」：看板上的每个时间必须能回答"它是取数时刻，还是数据时刻"。
本页是 10 个入口里唯一同时暴露两种时间的页面，因此先在这里把契约写死。

## 二、改动

### 2.1 三条时间口径（契约）

| 名称 | 含义 | 出现位置 |
|---|---|---|
| **观测时间** | 浏览器发出请求并拿到响应的时刻（客户端时钟） | 顶栏；对账横条「观测于 …」 |
| **数据窗口** | 数据本身覆盖的时间范围 | 总览「数据窗口 2009-12-01 07:45 ~ 2011-12-09 12:50」；实时链路「最新窗口」 |
| **对账区间** | 对账作业实际比对的两个半开区间 | 离线与对账「对账区间」「区间 12-01 ~ 12-09」 |

三者**不得共用一个标签**。顶栏改为「观测时间」，并加 `title` 说明数据时刻去各页看。

### 2.2 `buildDelta()` 增加历史数据集判断

新增模块级常量 `DELTA_HISTORICAL_LIMIT_MIN = 48 * 60`（与实时链路页判断"历史数据集"同阈值）。
最后窗口距当前超过该阈值时，直接返回 pending 态：

```js
text: '历史数据集 · 不展示环比'
pending: true   // 与「待下一窗口」同分支：灰字，不出彩色 pill
title: '该数据集是历史区间（最新窗口 …），最后两个窗口之间的差不是"最近的变化"，因此不展示环比'
```

选择"不展示"而不是"改成按天比较"：按天比较同样会踩到"最后一天是不完整日"的坑
（交易域数据止于 2011-12-09 12:48，当天只有半个上午），改口径会把一个坑换成另一个坑。
在论文里，"识别出这类比较不成立并拒绝展示"本身就是判据设计的一部分。

### 2.3 兼容性

- 只改展示与文案，接口未动，旧调用方无影响。
- `delta` 对象结构不变（仍为 `{text, glyph, tone, pending, a11y, title}`），模板的 `v-if="delta && delta.pending"` 分支复用。
- 实时链路页的 `freshness` 逻辑未动；两处阈值目前是**两个常量**（见第五节待办）。
