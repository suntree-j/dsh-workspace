## 一、定位

### 1.1 流量页：模板调用了未导出的 `fmtTime`

`services/web/index.html:529` 的流量面板元信息要显示窗口边界，模板里调用 `fmtTime(...)`；
但 `TrafficPanel` 的 `setup` 返回值（`services/web/app.js:1745`–`1758`）只导出了
`fmtInt`，没有 `fmtTime`。Vue 在渲染该模板时对未定义函数求值抛错，整页组件树中断，
表现是**页面只剩页头与侧栏**（改动前截图约 47 KB），不是接口没数据。

对照：`TradePanel`（`app.js:1753`）与 `OrdersPanel`（`app.js:2308`）都已导出
`fmtTime: formatTime`，因此同一写法在交易页/订单页正常。

### 1.2 类目页：排行结果里没有时间字段

`GET /metrics/category` 的 `data` 每行只有
`category_name / order_cnt / gmv / total_quantity / avg_order_amount`。
原因是 `repository.category_top()` 对 `ads_realtime_category_1m` 做
`GROUP BY category_name`，时间列已被聚合掉；`main.py:276`–`290` 的信封也没有传
`time_range`，于是 `source.time_range` 恒为 `{start: null, end: null}`。

不能把 `api.category` 改成返回整个信封：`OrdersPanel`（`app.js` 的类目下拉）仍把它当数组用。
因此需要一条“只读信封”的旁路，而不是改既有返回形态。

### 1.3 代码入口

| 位置 | 问题 |
|---|---|
| `services/web/index.html:529` | 流量面板调用 `fmtTime`，但 `TrafficPanel` 未导出 |

| `services/api/app/repository.py:257`（category_top） | `GROUP BY` 后无时间列 |

## 二、改动

### 2.1 流量页

1. `TrafficPanel` 的 `return` 补 `fmtTime: formatTime`（`app.js:1753`）。
2. `index.html:529` 的元信息改为：
   `数据窗口 {{ fmtTime(series[0].window_start) }} ~ {{ fmtTime(series[series.length - 1].window_start) }} · 最近 {{ series.length }} 个窗口`。
   起止都取 `window_start`，与总览页 `earliest_window ~ latest_window`、交易页的口径一致；
   `window_end` 是半开区间的右端（下一分钟），不拿来当“最新数据时刻”。

### 2.2 类目页：后端补 `time_range`

1. `repository.py:289` 新增 `category_window(window_limit)`：
   ```sql
   SELECT MIN(window_start) AS min_window, MAX(window_start) AS max_window
   FROM ads_realtime_category_1m
   [WHERE window_start >= DATE_SUB((SELECT MAX(window_start) FROM ads_realtime_category_1m),
                                   INTERVAL {window_limit} MINUTE)]
   ```
   过滤条件与 `category_top` 完全一致（同一 `window_limit` 语义），
   保证“窗口边界”描述的就是参与排行聚合的那批窗口。
2. `main.py` 的 `/metrics/category` 把 `repo.category_window(window_limit or None)`
   传给 `envelope(time_range=...)`；`data` 仍是原来的数组。

### 2.3 类目页：前端读信封，不改原 API

1. `app.js:625` 新增 `apiGetEnvelope()`；`runRequest()` 增加 `returnEnvelope` 开关
   （`app.js:681`），为 `true` 时返回完整 `body`，否则仍返回 `body.data`。
2. `api.categoryEnvelope(limit, windowLimit)`（`app.js:701`）走同一端点；
   `api.category` 原样保留，`OrdersPanel` 无需改动。
3. `CategoryPanel` 增加 `categoryTime` ref（`app.js:1990`），从
   `body.source.time_range` 取值；失败时清空，不保留上一次的旧窗口。
4. `index.html:608` 增加
   `数据窗口 {{ fmtTime(categoryTime.start) }} ~ {{ fmtTime(categoryTime.end) }}`；
   `CategoryPanel` 导出 `categoryTime` 与 `fmtTime`（`app.js:2119`、`app.js:2128`）。

### 2.4 兼容性

- `/metrics/category` 的 `data` 形态未变，订单页类目下拉不受影响。
- `apiGet` 的默认行为未变（仍返回 `data`），只多了一个可选开关。
- 新增查询只读 `MIN/MAX`，与排行查询同表同过滤条件，不写数据。

## 四、论文回写

`docs/thesis/REPORT_DRAFT.md` §5.6 已补「数据窗口的页面级落地」一段，说明：

- `source.time_range` 是接口自报的数据覆盖区间；类目排行因 `GROUP BY` 丢失时间列，
  因此新增 `category_window()` 在同表同过滤条件下取 `MIN/MAX(window_start)`；
- 前端用只读信封旁路（`apiGetEnvelope`）显示窗口，原 `api.category` 保持数组形态；
- 实测三处窗口：流量 `2017-12-03 23:00:00 ~ 23:59:00`、类目近 60 分钟
  `2011-12-09 11:50:00 ~ 12:50:00`、类目全部 `2009-12-01 07:45:00 ~ 2011-12-09 12:50:00`。

§6.7 的 E04 证据台账补记本次采集时间与两条窗口值。DOCX 由
`python docs/thesis/md_to_thesis_docx.py` 重建；字号、表格数、图片数由脚本断言检查。

**能写的说法**：流量页与类目页现在显示数据自身的时间范围；类目接口的
`source.time_range` 在两种窗口口径下都返回非空边界。
**不能写**：所有入口的日期口径已完全统一——订单明细页仍按日期筛选，不使用“最近 N 窗口”。

### 5.2 风险与已知边界

- 类目接口现在每次多一条 `MIN/MAX` 查询；实测总耗时 18–35 ms，仍在原量级。
- 顶栏“只读数据服务 · N 张表”来自最后完成的请求，可能与当前页 `source.tables` 不同步；
  这是既有全局状态行为，本次未改。
- 订单明细页仍按日期筛选，不显示“数据窗口”；它与“最近 N 个窗口”不是同一口径，
  不应为了统一文案强行改成窗口描述。
