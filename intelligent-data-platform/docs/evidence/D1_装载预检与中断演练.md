# D1 装载预检与中断演练：把"装错了才知道"变成"装之前就挡住"

- 证据编号：E01（输入可复现）+ E06（调度/运维的失败处置）
- 采集时间：2026-11-16 04:43–04:46（Asia/Shanghai）
- 环境：京东云 `lavm-txyjj7xzr7:/opt/data-platform`，`data-generator` 容器（Python 3.13）通过 `--profile tools` 一次性运行
- 输入：`/opt/data-platform/data-generator/data/real/` 下 8 个 CSV（与线上已装载数据同一份）
- 结论：预检在只读状态下通过 6 类检查并输出 manifest；中断演练在隔离 schema 里证明"装到一半被杀 → 重跑收敛到同一状态"。正式库全程未被写入。

## 一、定位

**现象（改造前）**：`data-generator/src/load_real_data.py` 的守卫只有"内存里查 user/product 主键重复"一条，其余风险都要等真正装载时才暴露：

- 列错位 → 写进库才发现（此时已 `TRUNCATE`）；
- 外键悬空 → MySQL 直接拒，装在第五张表时失败，前面四张已经是新数据；
- 金额三位小数 → MySQL 按 `DECIMAL(18,2)` **静默舍入**，对账按分比金额，误差会累积成分位漂移；
- 行为明细时间逆序 → Flink 水位后退，迟到事件被丢弃，表现为"实时侧少了一部分"，而日志上没有任何报错；
- 行数被裁剪过 → 无法与官方口径区分是"抽样"还是"脚本 bug"。

**触发条件**：任何一次重新装载（换窗口、换抽样子集、换脚本版本）。

**代码入口**：`load_real_data.py` `main()` 第 306–311 行的主键守卫；`load_mysql()` 的 `TRUNCATE -> 逐表 insert -> 行数比对` 序列。

**可重现性**：必然发生——中断演练里把 `--fail-in orders --fail-after-batches 2` 打开即可稳定复现"部分表已写、部分表为空"的状态。

## 二、改动

| 文件 | 改动 |
| --- | --- |
| `data-generator/src/preflight.py` | **新建**。只读预检：文件齐全与表头一致、主键唯一（7 张表）、外键覆盖（8 组父子）、金额精度 ≤ 2 位、行为明细 `event_time` 非降、GMV/退款额合计；输出 manifest（每文件 sha256/行数/字节数/金额合计）到 `--manifest` 路径 |
| `data-generator/src/drill_load.py` | **新建**。隔离 schema 中断演练：`CREATE TABLE … LIKE` 克隆结构 → 切外键自洽小样本 → 第 K 批后抛 `SimulatedCrash` → 记录部分状态 → `TRUNCATE` 后完整重跑 → 断言行数与金额等于期望 → `DROP DATABASE` |
| `tests/test_preflight_rules.py` | **新建**。15 例纯规则测试（金额精度 11 例、表头不符、金额超精度、时间逆序、缺文件） |

**关键设计取舍**：

- **预检必须只读**。它会（可能）在正式环境跑，任何建表/清表动作都不该出现在这里。所以预检不连数据库，连"外键悬空"也是**在 CSV 之间**算的。
- **演练必须换库**。中断演练会故意留下脏状态，绝不能拿 `ecommerce` 做。默认库名 `ecommerce_drill`，并且脚本在 `args.schema == cfg.mysql.database` 时直接 `SystemExit`。
- **批次边界与正式装载对齐**（每 1000 行一次 `commit`），否则演练出来的"部分状态"不是真实风险形态。
- **业务账号没有 `CREATE DATABASE` 权限**，所以建库与授权由管理员在容器外做，Python 侧 `try/except` 跳过后继续用已存在的库；删除同理。这条写进了函数注释，避免下一个人以为脚本能自己建库。

**复现命令**：

```bash
cd /opt/data-platform
# 1) 预检（只读，可随时跑）
docker compose --profile tools run --rm data-generator \
  python -m src.preflight --dir data/real --manifest /app/state/preflight_manifest.json

# 2) 管理员建演练库并授权（一次性）
docker compose exec -T mysql mysql -uroot -p"$PW" -e "\
  CREATE DATABASE IF NOT EXISTS ecommerce_drill; \
  GRANT ALL PRIVILEGES ON \`ecommerce_drill\`.* TO 'app'@'%'; FLUSH PRIVILEGES;"

# 3) 中断演练
docker compose --profile tools run --rm data-generator \
  python -m src.drill_load --dir data/real --limit 3000 --fail-in orders --fail-after-batches 2

# 4) 清理（脚本会自动删，失败时手工兜底）
docker compose exec -T mysql mysql -uroot -p"$PW" -e "DROP DATABASE IF EXISTS ecommerce_drill;"
```

**局限**：

- 预检读的是 CSV，**不校验库里现有的数据**；"库里现在对不对"属于对账（E02/E03）的问题。
- 演练样本是"前 N 张订单"，不是全量；它证明的是**流程的可重入性**，不是全量装载的耗时。
- 预检的行数检查只报数字，不与官方口径做硬断言（官方口径写在 `docs/thesis/REAL_DATA_FACTS.md`，随论文版本变化，不进代码）。

## 四、论文回写

- **3 章（需求/约束）**：把"输入可复现"具体化为四条可检查项（sha256、行数、主键唯一、外键覆盖），并说明为什么这些必须在装载前检查而不是装载后。
- **5 章（实现）**：数据接入一节补"预检 → 装载 → 中断重跑"的顺序图；写明批次边界是每 1000 行一次提交，因此崩溃粒度是"整批"而不是"整表"。
- **6 章（测试与验证）**：E01 可以直接引用上面的预检输出与 manifest；E06 引用中断演练的两张表（中断时/重跑后）。表述用"重跑收敛到同一状态"，**不要写"装载具备事务性"**——它不具备，它具备的是可重入。
- **可删的旧断言**：任何"全量装载无风险/无损"的表述。

## 五、交接

- **本批选择**：预检与演练都是新增模块，未改 `load_real_data.py` 的装载行为（生产路径零风险）；两个文件已 scp 到 `/opt/data-platform/data-generator/src/`。
- **回滚**：删掉这两个文件即可，无配置变更；演练库默认自删，若残留由管理员 `DROP DATABASE ecommerce_drill`。
- **下一个可独立继续的任务**：D3（Airflow `archive_behavior` 失败态与湖仓发布完整性）——那是交接包列的第二优先级。
- **需要裁决**：预检是否要接进 `batch-mode.sh` 或 DAG 作为**强制前置**。接的风险是每次批处理多花约 30 秒（读 875 MB 的 behavior CSV 算 sha256）；不接的风险是有人绕开预检直接装载。当前建议：只在"重新装载"的场景手动跑，不进日常批处理。
