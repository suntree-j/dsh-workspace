- 证据编号：E03（恢复期对账）+ E02（批流对账）补充
- 采集时间：2026-11-16 04:30–04:40（Asia/Shanghai）
- 环境：本地 `opt/20261116` 分支 → 京东云 `lavm-txyjj7xzr7:/opt/data-platform`（非 git，scp 单文件）
- 业务区间：`2009-12-01 07:45:00` ~ `2011-12-09 12:48:00`（latest 批次的半开区间）
- 批次：`reconcile_20261116_033539`（Spark 作业 03:35:39 写入）
- 结论：接口由"一个混合口径"拆成 **latest / live / totals** 三段，`live.state` 在 04:34:53 与 04:36:04 两次采样均为 `consistent`，两侧 40,358 窗口、GMV 与支付金额完全相等。

## 一、定位

**现象**：`/data/api/batch/reconcile` 的 `latest` 说"40,358 窗口、不一致 0、PASS"，但同一响应的 `totals` 是**两张表的全表即刻汇总**；实时链路从 earliest 重放期间（交接包记录 03:52:21 同区间实时 16,746,946.14 / 离线 17,067,427.47），页面上会出现"批次判通过、双塔对比却差 32 万"的自相矛盾。

**触发条件**：实时链路重启或整代重放期间任意时点刷新 `/data/#/batch`。

**代码入口**：

- `services/api/app/repository.py` `reconciliation()`：`totals` 两条 `SUM(...)` **不带任何区间条件**，直接读全表。
- 同一方法的 `mismatches`：`WHERE is_match = false` 后未按批次收敛（明细表以 `window_start` 为主键、无 `batch_id`，但有 `compared_at`）。
- `services/web/app.js` `compareRows`：双塔对比直接取 `rep.totals` + `rep.deltas`，与 hero 的 `latest` 不是同一口径。

**可重现性**：重放期间必然出现（实时侧偏低）；稳定后 `totals` 与 `latest` 区间值仍有 588.65 元的差（全表 17,068,016.12 vs 对账区间 17,067,427.47，来自 `TAIL_GUARD_MINUTES = 3`），所以**即使不重放，两个口径也不应并列**。

## 二、改动

| 文件 | 改动 |
| --- | --- |
| `services/api/app/repository.py` | 新增模块级 `_DT_RE` / `_dec()` / `_diff()` / `classify_reconcile_state()`；`reconciliation()` 新增 **`live`**：按 `latest` 的同一半开区间用**一条 `UNION ALL`** 同时读 `ecommerce.ads_realtime_trade_1m` 与 `lakehouse_ads.ads_batch_trade_1m`（`COUNT(*)` / `SUM(gmv)` / `SUM(payment_amount)` / `SUM(order_cnt)` / `MAX(window_start)`），再取 `SELECT NOW()` 作 `observed_at`；`mismatches` 增加 `compared_at = (SELECT MAX(compared_at) …)`；`totals` 增加 `"scope": "full_table"` 标注 |
| `services/api/app/main.py` | `/batch/reconcile` 的 `source.note` 改写：三个口径必须分开读，`realtime_behind` 不是通过 |
| `services/web/app.js` | `compareRows` 优先用 `rep.live`（同区间），缺该字段才回退 `rep.totals`；新增 `live` / `liveState` / `liveTone` / `liveStateText` / `liveScope` 并导出 |
| `services/web/index.html` | hero 内新增「同区间即时比较」横条：状态芯片 + 实时/离线两侧窗口与金额 + 区间与 `observed_at` |
| `services/web/styles.css` | 新增 `.rc-live*` 样式（chip 四态：ok / warn / bad / unknown） |
| `tests/test_reconcile_state.py` | 新建，9 个用例钉住四态判定 |

**四态语义**（`classify_reconcile_state`）：

- `consistent`：两侧窗口数与 GMV/支付金额完全相等；
- `realtime_behind`：实时侧更少或更小 → 可能正在重放/未收满，**需再采样确认，不是通过**；
- `diverged`：实时侧反而更高 → 批层缺数据或写序异常，属真实问题；
- `unknown`：任一侧取不到值。

**兼容性**：只新增字段（`live`、`mismatch_count_shown`、`totals.scope`），`latest` / `totals` / `deltas` / `mismatches` 全部保留；旧的 `/batch/reconcile` 消费方（overview 状态芯片、质量页）无需改动。并发/重跑：`live` 是只读查询，天然幂等；`mismatches` 收敛到最近一次 `compared_at` 后，多批次并存也不会串批。

## 四、论文回写

- **5 章（平台实现/对账）**：接口一节必须写成三段口径（latest / live / totals），并给出"为什么不能并列"的理由（区间 vs 全表、`TAIL_GUARD_MINUTES = 3`）。删除任何"接口直接返回批次结论即可"的表述。
- **6 章（测试与验证）**：E03 可用本批的观测时间序列作为恢复期证据：`03:52:21` 实时 16,746,946.14 → `03:55:51`、`03:57:33` 两侧 17,067,427.47 → 本批 `04:34:53`、`04:36:04` 两次采样均为 `consistent`。表述要写"恢复期实时侧偏低属预期，判据看同一区间且需再采样确认"，不写"任何时刻都相等"。
- **6 章（看板）**：双塔对比的口径要写明"按 latest 的同一半开区间"，并说明与 hero 的关系。
- **可删除的旧断言**：`docs/thesis/REPORT_DRAFT.md` 5.3.4 里"实时侧窗口比率异常…决定不修"的叙述（该缺陷已在 2026-11-11 修复，交接包 02 也点名要求改）。
