## 第 3 页 问题：同一指标两套实现（0:45）

**标题**：如果不做对账，会发生什么

**要点**：

1. 电商数据同时以"流"和"批"两种形态产生，两类数据的一致性要求不同（行为埋点不需强一致，订单支付是可对账事实）。

## 第 5 页 关键实现①：批流交叉对账（1:20）

**标题**：怎么证明两条链路算的是同一个数

**要点**：

1. 实时指标算在 **Kafka 事件**上，离线指标算在 **MySQL 业务行**上——对账前必须先证明**事件与业务行一一对应**。
2. 离线 ADS 特意做成**与实时同粒度（1 分钟窗口）**，否则无法逐条比对。
3. 对账区间截断（尾部留 3 分钟安全边界，只比"两端都已封闭"的窗口）；**单边窗口单独统计**（实测两个域都是 0 / 0）。
4. 结果：交易域 **11458 个窗口，不一致 0**，两侧 GMV **精确到分相等**（51,890,375.77）；流量域 **19643 个窗口，不一致 0**。

**建议表**：核心指标对账表（GMV / 订单量 / 支付成功 / 支付失败 / 退款共 5 行 × 实时 / 离线 / 差异 3 列，差异列全为 0）。

**口播重点**："两个引擎、两套框架、两条独立链路，同一个数"——这是全篇最硬的一句。

## 第 6 页 关键实现②：判据的两次打磨 ⭐（1:00）

> **这一页是全篇最该讲的一页。** 它证明对账工作真的在验证，而不是在凑结果。

**标题**：判据本身先被验证过两次

**要点**：

1. **第一次：离线表多一个分区列。** 自检 34/35，失败项是"字段顺序与实时表一致"。根因是 `DESCRIBE` **会把分区列一并列出**，于是 12 列被拿去和 13 列比——**断言写错，不是数据错**。改成"数据列逐列同序 + 分区列 `dt` 只在最后"，并补一条反向守卫。
2. **第二次：比率列改为按各自计数重算。** 原判据"两侧比率相等"既不增加信息、又会被除法实现细节的末位差异误报。新判据是"每一侧的比率 == 由该侧**自己的**计数按公式重算"——**不需要两侧一致就能判定谁错**。
3. 两次的方向都是**变严，不是变松**。

**建议图**：左右对照两栏（旧判据 / 新判据），配一行结论。**不要贴代码**。

**口播重点**：断言失败时，第一件事是确认"这条断言在说什么"，而不是先怀疑数据。**断言写错比没有断言更危险**——它会把人引向"数据错了"的错误结论。

**数据来源**：`docs/sprint/SPRINT_5.md` 第 9.2 节第 2 条、第 9.4 节第 1 条；`docs/sprint/SPRINT_3.md` 第 8.4 节。

## 第 7 页 关键实现③：Iceberg 迁移的三个陷阱（1:10）

**标题**：23 张表迁移，以及它教的三件事

**要点**：

1. **三段名**：迁移清单 18 → 23 张表。校验计数**两次运行各按自身范围**：**18 张表那次 60/60**、**扩到 23 张表复跑那次 70/70**（口播时若只报一个数，必须带上"当时是几张表"）。逐表核对行数与**金额 SUM**——行数相同不代表内容没坏，金额是最敏感的探针。
2. **陷阱：库名与 catalog 同名时，"建库"这句话没有唯一含义。** 报错是 `Cannot create namespace with invalid name:`，**冒号后是空的**——Spark 把一段名先当目录名，解析成"目录 + 空命名空间"。
3. **陷阱：两段名永远属于当前目录。** 只写两段名会静默落到别处，**而行数核对读的也是同一个错地方**（核对与被核对的对象一起错，两边都"一致"）。
4. **OOM 是结构问题，不是内存不够。** 703 个分区 vs 默认 200 个 shuffle 分区 + AQE 合并 → 少数 task 各持有几百个分区写入器（数据只有 2 万行）。修法是 `DISTRIBUTE BY` + 抬高分区数 + 关 AQE 合并，**不是把执行器内存调大**（那只会掩盖症状）。

**建议图**：三段名写法对比（`spark_catalog.lakehouse.ods_orders` vs `iceberg.lakehouse_iceberg.ods_orders`）。

**数据来源**：`docs/sprint/SPRINT_5.md` 第 8.1、8.2、9.6 节；`docs/DECISIONS.md` D13、D14、D15。

## 第 8 页 关键实现④：Agent 的可信性从哪来（1:10）

**标题**：可信性由架构保证，不由提示词保证

**要点（4 条，每条一个机制）**：

1. **进程边界**：Agent 进程里**没有数据库凭据**，也没有 mysql 客户端依赖——"不得拥有数据库管理员权限"想绕过也没有入口。SQL 守卫放在**服务端**，因为"放在 Agent 里等于让被约束者自己当裁判"。
2. **可核对来源**：回答附**实际执行**的 `executed_sql`（守卫会改写 LIMIT，所以必须返回改写后的那条）、命中的 `docs`（**带文件与行号**）、`tables`（**由服务端提取**，不靠调用方自报）。
3. **可数的失败与重试**：`validation.issues` / `retries` / `graph.path` 都是响应字段。**实测触发过真实反思重试**：问 1 `retries=1`（真实错误 `Unknown column 'window_start'`），问 5 `retries=2`（两次 `TABLE_NOT_ALLOWED`，如实回答"给不出来"）。
4. **拒绝即失败**：MCP 与直连两条路径终点、守卫、账号完全相同，**不做自动降级**——自动降级会让 MCP 路径在抖动后悄悄消失，而所有断言仍然全绿。

**建议表**：一行小表 —— 四类攻击 → 返回码与原因（DELETE → `NOT_SELECT`；未授权表 → `TABLE_NOT_ALLOWED`；多语句 → `MULTI_STATEMENT`；注释注入 → `COMMENT`）。

**数据来源**：`docs/sprint/SPRINT_7.md` 第 2、3.2、3.3、8 节；`SPRINT_8.md` 第 9.5 节；`SPRINT_10.md` 第 2、5.2 节；`AGENTS.md` 第 15.12 节。

## 第 10 页 验证：性能基线四类（0:50）

**标题**：四类基线，以及一个反直觉的结论

**要点**：

1. **只读接口**：点查 8.5 / 聚合 8.3 / 两表关联 11.7 ms（n=7 中位数）；服务端 `elapsed_ms` 仅 4~6 ms → **约 3~6 ms 是 HTTP + JSON 常数开销**。⚠️ **关联那 11.7 ms 需加注**：采集时 `dim_product` 为 0 行、JOIN 未真的发生；缺陷已修，同口径重跑返回 10 行、约 **7.4 ms**（表内保留原值不改历史观察值）。
2. **实时 vs 离线**：同口径聚合两侧都是 7.1 ms → **无可测量差异**（数据量 10³~10⁴ 行，未到读放大的量级）。如实记录为"无显著差异"，**不编造趋势**。

## 第 11 页 一次真实事故：现象 → 证据链 → 硬规范 ⭐（0:50）

> 这一页最容易出彩。**讲证据链，不要只讲"我犯了个错又改好了"。**

**标题**：一次原子换树同步引发的事故及其硬规范

**要点**：

1. **现象**：为绕过同步脚本的"Spark 运行中"守卫，写了一个"原子换树"同步脚本（`mv 旧树 → tar 到 .new → mv 到位 → rm -rf .old`）。因为只打包了一个子目录，`rm -rf .old` 把 **`.env`（唯一存有真实凭据的文件）、三个 venv、`airflow.env` 和三个挂载 JAR** 一起删掉了。
2. **证据链（这一页的核心）**：
   - `docker compose` 直接不可用（它靠 `.env` 做变量插值）→ 排除"服务配置问题"；
   - 报错 `DatastoreDriverNotFoundException: com.mysql.cj.jdbc.Driver was not found in the CLASSPATH` 说的是"CLASSPATH 配错了"，**而真相是那个 JAR 被删了** → **报错指向的不是根因**；
   - 磁盘上"文件丢失"表现为**一个空目录**（Docker 会把不存在的挂载点创建成目录），`ls -la` 看上去像有东西 → **判据必须用 `-f` + `-s`，不能只看 `ls`**。
3. **根因**：不是环境问题，是**一个绕开守卫的决定**。守卫拦的是"运行中的脚本被半覆盖"；原子换树防住了半覆盖，却把**子集同步**变成了**整树替换**——子集之外的机器状态不再受保护。
4. **沉淀成硬规范**：共享文件权限按**所有读者**定（`.env` 必须 `640 root:dpapi`，600 会让 Agent 起不来）；**禁止原子换树**；凭据落盘前禁止 `compose up/restart`；共享编排文件必须先落创作副本、验收核对 md5。

**建议图**：三条证据的排查路径（现象 → 排除项 → 结论），做成三段箭头。**不要贴脚本代码。**

**数据来源**：`AGENTS.md` 第 15.11 节；`docs/sprint/SPRINT_12.md` 第 8.2 节；`docs/DEVELOPMENT_LOG.md` 第 1529~1546 行。

## 第 12 页 不足与改进（主动交底，0:50）

**标题**：我知道它哪里不够

**要点（4 条，每条带改进方向）**：

1. **数据是程序生成的合成数据。** 种子 `GEN_RANDOM_SEED` 默认 `20260926`，同种子可复现，业务约束在生成期强制执行——但它**不代表真实业务分布**。改进方向：接入真实数据源需要 CDC。
2. **站点是明文 HTTP。** 曾实测启用 TLS 后公网 64/64 全部 200，但按 IP 访问只能自签、演示观感不好，因此停用；443 配置与脚本保留在仓库。改进方向：注册域名 + 备案后启用。

### 备用 C：三类指标的运算规则（容易被追问）

| 类别 | 字段 | 可以做什么 | **不可以**做什么 |
| --- | --- | --- | --- |
| 可加 | `pv` / `view_cnt` / `click_cnt` / `cart_cnt` / `favorite_cnt` / `buy_cnt` | 逐窗口比对；跨窗口、跨天直接 SUM 上卷 | — |
| 去重 | `uv` | 逐窗口比对；要天粒度就**回到明细重新去重** | **跨窗口相加**（`SUM(uv)` 不是任何有意义的量） |
| 派生 | `click_rate` / `cart_rate` / `buy_rate` | 用"合计后的分子 / 合计后的分母"重算 | 对逐窗口比率求平均 |

**支撑这个规则的两条实测**：`SUM(19644 个窗口的 uv) = 19999`（逐窗口去重的基数），而全部 20000 个事件的去重用户数 = 1200（人的基数）——**相差约 16 倍，但都正确**，它们是两个不同的定义。若把"天 UV"写成 `SUM(分钟 uv)`，会系统性偏大且看起来仍然合理（19999 < 20000 的 PV，不会有人怀疑）。

**数据来源**：`sql/metadata/metrics.md` 第 3.1 节；`docs/sprint/SPRINT_5.md` 第 9.1 节。
