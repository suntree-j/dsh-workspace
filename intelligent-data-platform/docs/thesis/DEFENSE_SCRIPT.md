## 第 3 页 · 问题（0:45 – 1:30）

先说为什么这个问题值得做。

电商的数据天然是两种形态：一类是点击、加购、下单、支付这些持续产生的事件流，要的是快；另一类是日级、月级的经营分析，要的是准和可回溯。

传统做法是建两套系统，代价是**同一个指标有两份实现**。后果是一个链条：同一个 GMV 会出现三种算法，实时说一百万、离线说九十五万，那建在它上面的 Agent **引用哪一个都是错的**，整个智能层就没有判断依据了。

所以我给自己定的目标不是"离线也能算出 GMV"，而是**证明两条链路算的是同一个数**——这是一个可以被证伪的断言：只要有一个窗口对不上，结论就不成立。

（翻页）

## 第 4 页 · 总体架构（1:30 – 3:00）

（这一页 1 分 30 秒，讲清楚"两条链路在哪里汇合"就够了，**不要逐层解释 ODS/DWD/DWS/ADS 是什么**。）

整体是五层。

最下面是数据源层：一个 Python 数据生成器往 MySQL 写五张业务表，同时往 Kafka 发四类事件。Kafka 用的是 KRaft 模式，四个 topic 各三个分区，分区键的设计是为了保证**同一订单、同一用户的事件落在同一个分区**，从而保证分区内有序。

往上是两条计算链路。

**实时链路**：Flink 用**事件时间**语义、1 分钟滚动窗口做聚合，结果写进 Doris，提供亚秒级查询。这里有一个实测出来的选择——事件时间格式用的是不带时区的字符串，因为 Flink 的 JSON 解析器不接受带时区偏移的 ISO 格式，会直接报解析失败。

**离线链路**：Spark 从 MySQL 和 Kafka 抽取，写进 Iceberg，按 ODS、DWD、DWS、ADS 四层建模，由 Airflow 每天凌晨三点调度九个任务。

**两条链路在哪里汇合**：都在 Doris 的**统一指标层**。这是整个设计的关键——离线结果也要搬进 Doris，服务层才能同时查两条链路的结果做对比。

这里有一个必须说的约束：**这台机器只有 16 GB 内存，实时链路常驻就要 13.7 GB**。所以批处理和实时链路不能同时跑，必须错峰——跑批之前先暂停 Flink 栈，释放大约 1.65 GB，跑完再恢复并自检。

最上面是服务层和智能层：十一个只读接口、六个看板页面，以及问答 Agent。Agent 取数有两条路径，直接走 HTTP，或者经过 MCP 服务，但**两条路径的终点、守卫和账号完全一样**，都没有数据库凭据。

## 第 5 页 · 关键实现① 批流交叉对账（3:00 – 4:20）

（这是第一个重点页。**"11458"和"19643"要念清楚。**）

讲第一个关键点：怎么证明两条链路算的是同一个数。

第一件事，得先解决一个前提问题：**实时指标是算在 Kafka 事件上的，离线指标是算在 MySQL 业务行上的**。要让它们能对账，必须先证明事件和业务行是一一对应的。比如支付失败事件，在 MySQL 里没有独立的"尝试时间"字段，我们明确规定**不允许**拿订单创建时间去冒充，否则对账必然错位。

第二件事，离线的 ADS 层我特意做成**和实时同一个粒度**——都是 1 分钟窗口。如果离线只出天表，那就根本没法逐条比。

第三件事是两个对账方法上的细节：对账区间要**截断**，尾部留 3 分钟安全边界，只比"两端都已经封闭"的窗口；同时**单边窗口要单独统计**——就是"只有实时有"和"只有离线有"各有多少个。实测两个域都是 0 比 0。这一条是为了让"差异为 0"有边界可核，否则"只比对两边都有的窗口"会把"某一侧缺了一批窗口"这种情况掩盖掉。

结果是：**交易域 11458 个分钟窗口，不一致 0 个**，两侧 GMV **精确到分相等**，都是 51,890,375.77。**流量域 19643 个窗口，不一致 0 个**，单边窗口 0 比 0。

订单量、支付成功笔数和金额、支付失败笔数、退款笔数和金额，五项指标的差异全都是 0。

两个引擎、两套计算框架、两条独立链路，**同一个数**。

## 第 6 页 · 关键实现② 判据的两次打磨（4:20 – 5:20）

（**这一页是全篇最该讲的一页。语速放慢，让评委听见"判据"两个字。**）

不过我想说，对账这件事**难的不是算，是判据本身**。判据我不是一次写对的，打磨过两次。

**第一次**：流量域自检出来 34 项通过、1 项失败，失败的是"字段顺序与实时表一致"。看起来像离线表结构写错了。实际根因是：`DESCRIBE` 这个命令**会把分区列一起列出来**，而实时表没有分区列，于是 12 个数据列被拿去和 13 列比。**是断言写错了，不是数据错。** 我改成"数据列逐列同序，加分区列只在最后"，并且补了一条反向守卫——除了分区列之外不能有多余字段。

**第二次**：流量域有一列比率指标。原来的判据是"两侧比率相等"。我把它换成了一个更强的独立判据：**每一侧的比率，必须等于用这一侧自己的计数按公式重算的结果**。方向是**变严，不是变松**——因为"两侧相等"这个判据不增加任何信息，判据列相等的时候比率在数学上必然相等，而且它还会被两侧除法实现细节的末位差异误报。新判据的好处是：**不需要两侧一致，就能判定是谁错。**

这两次打磨让我总结出一条：**断言失败的时候，第一件事是确认"这条断言在说什么"，而不是先怀疑数据。断言写错比没有断言更危险**——它会把你引向"数据错了"的错误结论，让你花时间去查一个根本不存在的问题。

（翻页）

## 第 7 页 · 关键实现③ Iceberg 迁移（5:20 – 6:30）

第二个关键点是 Iceberg 迁移。

迁移清单从 18 张表扩到 **23 张表**。校验跑过两次，**两个数的范围不一样**：18 张表那次是 **60 项全过**，流量域建成之后扩到 23 张表复跑是 **70 项全过**——它们不是同一个范围下的两个结果，我在报告里是按各自范围标注的。**每张表不只看行数，还核对了金额 SUM**——因为行数相同不代表内容没坏，截断或者转型出错的时候行数照样相等，金额是最敏感的探针。

迁移过程教了我三件事：

**第一，库名和 catalog 同名的时候，"建库"这句话没有唯一含义。** 报错是 `Cannot create namespace with invalid name`，**冒号后面是空的**。原因是 Spark 解析一段名的时候会先把它当目录名，于是解析成"目录 + 空命名空间"。解决办法是把 catalog 改名。

**第二，两段名永远属于当前目录。** 这是最危险的一条：只写两段名，表会静默落到别的地方——**而行数核对读的也是同一个错地方**。核对和被核对的对象一起错，两边还"一致"。所以 Iceberg 表全程写三段名。

**第三，那个 OOM 是结构问题，不是内存不够。** 报错是执行器连续 OOM、四次 `Lost executor`。根因是 703 个分区对默认 200 个 shuffle 分区，加上 AQE 又把小分区合并回去，导致少数 task 各自持有几百个分区写入器——**数据只有两万行，和数量无关**。修法是加 `DISTRIBUTE BY`、把分区数抬到 1000、关掉 AQE 合并，让一个 task 大约等于一个分区。我**没有**选择把执行器内存调大，因为那只是掩盖症状，分区数一涨还会复发。

（翻页）

## 第 8 页 · 关键实现④ Agent 的可信性（6:30 – 7:40）

第三个关键点是 Agent 的可信性从哪来。

我的答案是：**可信性由架构保证，不由提示词保证**。具体是四个机制。

**第一，进程边界。** Agent 进程里**没有数据库凭据**，也没有 mysql 客户端依赖。它只能通过 HTTP 调只读数据服务取数。所以"Agent 不得拥有数据库管理员权限"这件事，**想绕过也没有入口**。同理，SQL 安全检查我放在**服务端**，不放在 Agent 里——放在 Agent 里等于让被约束者自己当裁判。

**第二，来源可核对。** 回答里附三样东西：**实际执行**的 SQL（返回的是守卫改写后的那一条，因为守卫会补或收敛 LIMIT）、命中的口径文档（**带文件名和行号**，能当场翻到那一行核对）、以及用到的表（**由服务端提取**，不靠调用方自报）。

**第三，失败和重试是可数的。** 响应里有校验结论、重试次数、以及这次实际走过的图节点。**反思重试在实测中真的触发过**：有一个问题是第一次 SQL 写错了列名，`retries` 等于 1；另一个问题是查一张存在但未授权的表，`retries` 等于 2，两次都被守卫拒绝，它**如实回答"给不出来"**并列出被拒的表和错误原文，没有编造。

**第四，拒绝即失败。** MCP 路径和直连路径的结果是**逐字段一致**的，而且我**故意不做自动降级**——自动降级会让 MCP 这条路径在任何一次连接抖动之后悄悄消失，而所有断言还是全绿。那是最难发现的一类失效。

（翻页）

## 第 9 页 · 验证：判据 → 实测值 → 复现（7:40 – 8:40）

接下来讲验证。

我把每个结论都整理成"判据是什么、实测值多少、怎么复现"。举四个例子。

实时与离线同数，判据是逐窗口差异为 0，实测 11458 个窗口不一致 0，复现命令是 `verify-sprint-3.sh`。

归档**行数等于 Kafka 消息数**（单次验收窗口内未观察到丢失），判据是归档作业**自己数的**两个数相等，实测 20000 等于 20000，还有 703 个日期分区。这里我主动加三条限定：判据是**作业内自检**而不是独立追踪、它只是**那一次窗口内**的等式、以及这台机器的 Kafka **副本数是 1**——所以我不说无限定的"零丢失"。

迁移未改数据，判据是逐表行数加金额加表的 Provider，实测是两次运行：18 张表那次 60 比 60，扩到 23 张表复跑那次 70 比 70。

（**这一段是加分点，语速可以稍快，但"退出码 1"要念清楚。**）

我最想说的是第四类：**失败路径的证明**。一个脚本说"校验失败会退出码 1"，这句话靠读代码是证明不了的——一个无论结果都返回 0 的脚本，读起来也可能很像对的。所以我做了一个可执行的证明：故意把两条校验的期望值改成不可能成立的值，断言脚本必须返回退出码 1。实测两次演示都是 1，然后**再跑一次正常校验证明失败来自断言，而不是数据被改坏了**。

**一个从来没红过的断言，等于没有断言。**

另外所有断言都带非空守卫——比如"ADS 窗口数必须大于 0"。因为"两边都为空"也是一种完全一致，但毫无意义。

## 第 10 页 · 性能基线（8:40 – 9:30）

第四部分是性能基线，四类，全部有实测数字，方法写在报告里。

**只读接口**：点查 8.5 毫秒、聚合 8.3 毫秒、两表关联 11.7 毫秒，都是 7 次取中位数。服务端自述耗时只有 4 到 6 毫秒，也就是说**中间有 3 到 6 毫秒是 HTTP 加 JSON 编解码的常数开销**。这里有一格我要自己先说明：**两表关联那 11.7 毫秒是采集时维表为 0 行测出来的**，也就是说那次 JOIN 其实没有真的关联到数据；缺陷当天已经修好，同一口径重跑返回 10 行、中位数约 7.4 毫秒。表里我保留原来的 11.7，是为了不改历史观察值。

**实时侧和离线侧对比**：同口径聚合两边都是 7.1 毫秒，**测不出差异**。这是因为两边数据量都在万行量级，还没到读放大的程度。我**如实记录为"无显著差异"，没有编造一个趋势**。

**批量作业**：九个任务耗时合计 1992 秒，端到端大约 81 分钟。这个合计要说明口径：它取自 Airflow 的**元数据库**，是**九个任务各自 duration 字段的算术和**，所以它**不等于墙钟端到端**（中间有 48 分钟的重试等待），而且**含一次重试 attempt**。错峰暂停和恢复的固定成本是 150 秒；四个分层和归档作业占 76%——这说明要压缩时间应该从 Spark 的启动和分区数入手，而不是去优化装载和对账。

**最反直觉的是第四类**：Agent 端到端中位数 19187 毫秒，其中取数 15.4 毫秒、检索 2.9 毫秒，**数据侧只占 0.1%**；剩下 99.9% 是两次大模型调用。所以**优化 Agent 延迟只能从减少模型往返次数或者换模型入手，优化 SQL 几乎没有意义**。

这里我要主动说明一个边界：那个 99.9% 是**差值**算出来的，也就是"总量减去我们能单独量的那两段"，它**不是**对模型内部推理时间的测量，报告里明确写了不能把它说成"模型推理耗时"。另外这一项的**样本量只有 2 次**（原始日志记的是 n=2，脚本对 `/ask` 没有预热），所以它只能当量级参考，不是稳定的性能指标。

**最后，这一页所有数字有一个共同的边界，我必须说清楚**：它们全部是在**单机实验环境、单请求串行、本机回环、热缓存**的条件下测的；**我没有做任何并发测试或压力测试**——采集脚本里连一个并发原语都没有。所以**这些数字不能证明平台支持高并发，也不能当容量规划的依据**。它们能证明的只有一件事：在这台机器的单请求路径上，只读接口确实是毫秒级的。

（翻页）

## 第 11 页 · 一次真实事故（9:30 – 10:20）

（**这一页最容易出彩。重点讲证据链，不要只讲"我犯了个错又改好了"。**）

最后讲一次真实事故，因为它比一个成功的技术选型更有参考价值。

**现象**是：为了绕过一个同步脚本的"Spark 运行中"守卫，我写了一个"原子换树"的同步脚本——先把旧目录移走、解压新目录、再删掉旧目录。因为那次只打包了一个子目录，`rm -rf` 把旧目录里的一切都删了，包括 **`.env`（唯一存有真实凭据的文件）、三个虚拟环境、还有三个挂载的第三方 JAR**。

**证据链有三条**（这是我想讲的重点）：

第一条，`docker compose` 直接不可用了——因为它靠 `.env` 做变量插值。这一条就把范围从"某个服务配错了"缩小到"机器状态丢了"。

第二条，报错说 `DatastoreDriverNotFoundException`，意思是"CLASSPATH 配错了"。**但真相是那个 JAR 文件被删了。报错指向的不是根因**，顺着错误信息去查配置会一无所获。

第三条，磁盘上"文件丢失"居然表现为**一个空目录**——因为 Docker 会在挂载点文件不存在时把它创建成目录。`ls -la` 看上去像是有东西。所以**判断挂载型文件是否存在，必须用 `-f` 和 `-s`，不能只看 `ls`**。

**根因**：这不是环境问题，是**一个绕开守卫的决定**。守卫拦的是"运行中的脚本被半覆盖"，我的原子换树确实防住了半覆盖，却把**子集同步变成了整树替换**——子集之外的机器状态就不再受保护了。**绕过一个守卫的时候，必须重新论证它原本防的是什么，以及新方案有没有引入更大的风险。** 我当时没有做这一步。

**沉淀**成几条硬规范：共享文件的权限要按**所有读者**定，`.env` 必须是 640 而不是 600，因为有两个服务需要组读；**禁止任何原子换树同步**；凭据确认落盘之前**禁止**重建容器；共享编排文件必须先落副本再同步、验收时核对 md5。

## 第 12 页 · 不足（10:20 – 11:10）

（**主动交底，抢在评委之前说。每条都要带改进方向，不要说"时间不够"。**）

我知道这个系统哪里不够，说四条。

**第一，数据是程序生成的合成数据。** 有随机种子，默认 20260926，同一个种子能生成完全一样的数据，业务约束——外键关系、金额关系、时间因果——都在生成期强制执行。但它**不代表真实的业务分布**，这是最大的局限。要接真实数据源，需要引入 CDC 组件。

**第二，站点目前是明文 HTTP。** 我实测过启用 TLS 的效果，公网 64 次请求全部 200，但按 IP 访问只能用自签证书，浏览器每个会话都要点一次"继续前往"，演示观感不好，所以暂时停用，配置和脚本都留在仓库里。等注册域名、完成备案之后再启用。

**第三，实时侧有一个窗口的点击率是错的。** 那个窗口浏览 2 次、点击 1 次，点击率应该是 0.5，但实时链路落库的是 0；离线侧同一个窗口算出来是 0.5，是对的。**这一条要说准：它是"已定位、已留证的真实缺陷"，不是"未解决"，也不是"环境问题"。** 我用纯算术 1/2 等于 0.5 这个第三方判据定责，确认离线侧自洽、实时侧只有这 1 个矛盾窗口；然后把判据改严——从"两侧比率相等"改成"每一侧的比率必须等于用它自己的计数重算"；再把矛盾窗口数落盘成一等结论。**我选择不修，也经负责人复核维持**：修它要重部署 Flink 作业，而 Kafka 里那两万条行为事件还在，重放会覆盖实时侧全部一万九千多个窗口——重放成本远大于这个缺陷的影响。**没有加容差，也没有把证据删掉。**

**第四，有一处结构债没还。** 两个脚本各有一份相同的阶段分发表，新增阶段要改两处。它是**可维护性债，不是正确性缺陷**——因为两份都有"兜底分支必须失败"的写法，漏加分支会大声失败，不会静默跳过。

其余的限制，比如告警未接入、MinIO 用 root 凭据、没有做并发压测，报告里有一张完整的表。
