# 开题材料重做 · 需求说明（Prompt 母版）

> 用途：这份文件只描述**要求**，不含任何实现细节。把它连同项目现状一起交给任何执行者（人或模型），
> 都能据此重做《开题报告》与《开题答辩 PPT》。
> 配套文件：`开题重做_Codex提示词.md`（可直接粘贴给 Codex 的执行版）。

---

## 一、这份材料是什么

湖南工商大学 2027 届本科毕业设计**开题**材料，包含两份：

| 材料 | 性质 | 什么时候用 |
| --- | --- | --- |
| 附件2《开题报告》 | 学生填写的表格，学院归档 | 开题答辩前打印、指导教师签字 |
| 开题答辩 PPT | 现场陈述 5 分钟 | 答辩当天投屏 |

## 二、最重要的定位（这是上一版被否掉的原因）

**开题 = 立项论证，项目还没开始做。**

上一版把"已经做出来的原型"和"跑出来的数字"写进了开题材料，方向错了。开题要回答的是：

1. 这个问题**为什么值得做**（现状痛点、已有方案缺什么）；
2. 我**打算怎么做**（技术选型、系统分层、模块划分、开发顺序）；
3. 这些技术**各自解决哪一段**问题；
4. 凭什么认为**做得成**（可行性、数据可得、工具成熟、时间够）。

**不回答**"我已经做成了什么"。

## 三、必须遵守的硬约束

### 3.1 全文时态与口径

- 一律用**"拟 / 将 / 计划 / 打算 / 预计"**。
- **禁止**出现：已完成、已实现、已跑通、实测、验证为、数据表明、跑出、当前系统、目前已有……这类完成时表述。
- **禁止**出现任何运行结果数字：订单量、GMV、窗口数、不一致数、校验条数、Iceberg 表数、行为条数、耗时、性能指标。
- 允许出现的数字只有三类：① 学号 / 年份 / 版本号；② 公开数据集的**官方规模与许可**（属数据集属性，不是本项目成果，且须写明"拟使用"）；③ 通用的技术参数（如"1 分钟滚动窗口"这类设计参数）。

### 3.2 内容重心

- 重心在**技术介绍与设计思路**：用了哪些技术、每项技术负责哪一段、为什么不用另一种。
- **不要**把篇幅花在"对账判据表怎么定""比率列为什么不参与判定"这类实现层细节上；
  这类内容最多用一两句话点到"会做一致性校验"，不在开题阶段展开。
- 不要写成"项目总结报告"或"验收报告"。

### 3.3 语言风格

- 平实陈述，不喊口号；不用"赋能/闭环/抓手/打通"这类空词。
- 少用破折号与分号堆叠；一句一个意思，长句拆短。
- 不写"本文/本课题"开头的排比段；每段有具体信息量。
- 不出现 Markdown 记号（`**`、反引号），Word 里必须是正常文本。

## 四、《开题报告》的内容要求

表格为 8 行 × 9 列（学校 2024 修订版模板），需要填写的是三格正文：

### 4.1 选题价值（约 500–700 字）

- `1. 问题研究`：3 段。① 现状：数据平台通常实时、离线两套；② 痛点：两套各自实现一遍业务逻辑，指标对不上只能人工排查；③ 已有方案的边界：Lambda 解决互不干扰、湖仓解决存储统一，但都没回答"两边算出来是否一致"，由此引出本题。
- `2. 拟解决的关键问题`：3 条，每条 2–3 句。建议围绕：① 双链路如何共用同一份指标定义；② 离线与实时两条链路如何组织与衔接；③ 怎样把"结果可信"变成可执行的检查。

### 4.2 文献综述（约 2,900–3,100 字，编号体例）

```
1 绪论
1.1 研究背景与意义
1.2 国内外研究现状及发展趋势
    1.2.1 批处理与流处理引擎
    1.2.2 湖仓一体与开放表格式
    1.2.3 数据分析平台与可视化
    1.2.4 大语言模型与智能问数
    1.2.5 研究趋势小结
1.3 拟采用的关键技术概述
    1.3.1 数据采集与消息队列（Kafka）
    1.3.2 实时计算（Flink）
    1.3.3 分析型数据库（Doris）
    1.3.4 离线计算与湖仓存储（Spark / Iceberg / MinIO）
    1.3.5 服务与前端（FastAPI / Vue）
    1.3.6 智能问答（LangGraph / MCP / 检索）
1.4 研究内容与论文结构安排
附：参考文献（16 条）
```

- `1.3` 是这份材料的主体之一：每小节讲清"这项技术是什么、在项目中承担哪一段、为什么选它而不是另一种"。
- 正文引用用**上标** `[n]`，与末尾参考文献一一对应；参考文献不得出现未被引用的条目。
- 参考文献 16 条：外文期刊与会议 7 篇、中文期刊 4 篇、技术规范与官方文档 3 份、公开数据集 2 套；按 GB/T 7714 著录。
  **每条都必须真实存在**，卷期页码可核对；不得编造。

### 4.3 研究方法与思路（约 700–900 字，步骤式）

```
1. 数据准备与语义映射
2. 系统总体设计（采集 / 存储 / 计算 / 服务 四段分层）
3. 实时链路设计
4. 离线链路设计
5. 数据质量与一致性校验（点到为止，不展开判据表）
6. 服务层与智能问答设计
7. 开发计划与验证方式
8. 论文结构或写作提纲
```

- 每条写"做什么 + 用什么技术 + 产出什么"，不写"已经做到什么"。
- 第 8 条给出七章结构即可。

## 五、开题答辩 PPT 的内容要求

- 16:9，**9–11 页**，5 分钟讲完；不设章节过渡页（时间不够）。
- 建议页面：

| 页 | 内容 |
| --- | --- |
| 1 | 封面：校名·学院 / 题目 / 答辩人·学号·专业班级 / 指导教师 |
| 2 | 目录（5 章） |
| 3 | 选题背景与意义：同一个指标，两条链路，两个数 |
| 4 | 研究内容：本课题要做的三件事 |
| 5 | 项目总体设计：四段分层（采集 → 计算 → 存储 → 服务）架构图 |
| 6 | 关键技术选型：每层用什么、为什么不用另一种 |
| 7 | 技术栈总览（组件 + 版本 + 在项目中的位置） |
| 8 | 研究计划：四阶段 + 每阶段的交付与验证方式 |
| 9 | 预期成果与边界（能做的 / 做不到的都写清楚） |
| 10 | 致谢 |

- **禁止**出现任何运行结果数字卡片、禁止"已完成/已跑通"标题（如"前期原型预研""已完成的验证"）。
- 每页只讲一件事，标题即结论；正文用短句，不用长段落。
- 视觉：白底、单色强调（深蓝）、无阴影、无渐变、无装饰图片；字号不小于 18pt（投屏可读）。

## 六、验收标准（可逐条打勾）

- [ ] 全文零"已完成 / 已实现 / 已跑通 / 实测 / 数据表明"类表述。
- [ ] 全文零运行结果数字（订单量、GMV、窗口数、校验条数、表数、耗时）。
- [ ] 文献综述字数在 2,900–3,100 之间；选题价值 500–700；研究方法 700–900。
- [ ] 参考文献 16 条，正文每条都有对应上标引用，无"列而未引"。
- [ ] 表格结构与学校模板一致（8 行 × 9 列，行标签不改）。
- [ ] Word 打开无内容被裁切（长行可跨页）、无 Markdown 残留、无乱码。
- [ ] 打印后页数：开题报告 ≤ 6 页、任务书 1 页。
- [ ] PPT 无结果数字、无过渡页、页数 9–11、每页标题是结论而非栏目名。
- [ ] 5 分钟稿实测语速下不超过 4 分 40 秒。

## 七、可直接引用的项目事实（写"拟采用"时用）

以下是可以写进开题材料的**选型事实**，但要写成"拟采用"：

- 版本：MySQL 8.4 / Kafka 4.2 / Flink 1.20 / Doris 4.1 / Spark 3.5 / Iceberg 1.10 / Hive Metastore 3.1 / Airflow 3.3 / MinIO / FastAPI / Vue 3 + ECharts / LangGraph / MCP。**不写"最新版"**。
- 数据：拟使用两个公开真实数据集——交易域 UCI Online Retail II（约 107 万条原始交易记录，CC BY 4.0），流量域天池淘宝用户行为（约 1 亿条行为记录，CC BY-SA-NC 4.0，拟按用户抽样使用）。可写官方规模，**不写本项目已入库存了多少**。
- 结构：四段分层（采集 / 计算 / 存储 / 服务）；两条链路（实时 Flink→Doris、离线 Spark 四层→Iceberg→回灌 Doris）；一个一致性校验作业；服务层只读接口 + 看板 + 问答 Agent（Agent 无数据库凭据，经工具与 SQL 校验取数）。

## 八、禁止写进开题材料的内容（清单）

- 任何"我已经把两条链路跑通、对账零不一致"的陈述。
- 任何"某次运行得出 X 个窗口、Y 元 GMV"的数字。
- 任何"本系统当前支持/当前已上线"的表述。
- 把原型截图当作"系统成果"展示（若要放图，须标注为"设计示意图"）。
- 承诺具体指标（如"保证零不一致""达到生产可用"）。
