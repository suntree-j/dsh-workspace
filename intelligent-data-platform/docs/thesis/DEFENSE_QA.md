## 一、数据与可信性

### Q1. 数据是真实的吗？为什么用合成数据？

**要点**

- **直说：全部是程序生成的合成数据**，不含真实业务分布；生成器在 `data-generator/`，同时扮演"业务写入方"（写 MySQL）与"埋点方"（写 Kafka）。
- **为什么用**：本课题要回答的是"两条链路算的是不是同一个数"，这要求**事实源完全可控**——每一笔订单/支付/退款在 MySQL 与 Kafka 里的对应关系必须能逐条核对；真实数据拿不到这种确定性。
- **代价如实说**：它不代表真实业务分布，也无法验证模型在真实分布下的表现——这是本设计**最大的一条限制**。
- **关键机制**：`generate_events` **不重新随机生成一套订单**，而是读 `state/dataset_snapshot.json`（即真实写进 MySQL 的那批数据），因此事件与业务行必然对应。

**若被追问**

- 被问"那你这算不算脱离实际"：正面回答——**本课题的研究对象是"口径一致性"，不是"真实数据分布下的表现"**；前者可以在合成数据上被严格验证，后者需要真实数据源（要引入 CDC）才谈得上，属独立课题。
- 依据：`docs/data-source-design.md` 第 1、4.3、7 节；`docs/thesis/DATA_AND_LIMITATIONS.md` 第一部分第 1、6.6 节。

### Q2. 合成数据凭什么可信？

**要点**

- **可复现**：`GEN_RANDOM_SEED` 默认 `20260926`，`random.Random(seed)` 与 `Faker.seed_instance(seed)` 用同一随机源 → 同一种子生成**同一份**数据集。
- **业务约束在生成期强制**（不是事后校验）：外键归属（订单的 `user_id`/`product_id` 必须来自 `user`/`product`；`payment.order_id`、`refund.order_id` 必须来自 `orders`）、金额关系（`price × quantity ≈ amount`，折扣按概率）、时间因果（`register_time ≤ create_time ≤ pay_time ≤ refund_time`）、漏斗单调（VIEW > CLICK > CART > BUY）。
- **事件与业务行一一对应**通过快照传递保证，而不是"各随机一套"。
- **正因为这三条，"11458 个窗口不一致 0"才是一个可复核的结论**——否则换台机器、换一天跑，窗口数、GMV、漏斗计数全都会变。

**若被追问**

- 被问具体规模：用户 1200 / 商品 600 / 订单 6000 / 支付 5406（成功 5287、失败 119）/ 退款 254 / 行为事件 20000。**一条口径提醒**：**表内行数 = distinct `event_id` 基数 ≠ 链路处理量**（该 topic latest 合计曾达 580000 = 29 × 20000，Doris 侧 UNIQUE KEY + merge-on-write 去重后才是表内的 20000）——别把"20000 行"读成"这条链路一共只处理了 2 万条"。
- 被问"金额怎么保证不漂"：全程 `decimal.Decimal`，`_q2()` 四舍五入到 2 位；项目规范**禁止用 float 做金额累加**。
- 依据：`data-generator/src/config.py` 第 105~144 行；`data-generator/src/dataset.py`；`docs/thesis/DATA_AND_LIMITATIONS.md` 第一部分第 3、4、6 节。

### Q3. 数据规模是不是太小了？

**要点**

- **如实说：这是开发与验证规模，不是生产规模**。量级在 10³~10⁴ 行（ADS 交易窗口 11459 行、离线天表 626 行、明细 6000 行）。
- **本课题要验证的是口径一致性，不是吞吐能力**：判据是"同一窗口两侧的值是否相同"，这个判据与数据量级无关。
- **性能章节主动写了这个前提**：两侧数据量同量级且都在单 BE 内存/本地盘上，**远没到读放大的程度**，因此"离线更快/更慢"这类结论在这个规模下**测不出来**——如实记录为"无可测量差异（7.1 ms vs 7.1 ms）"，**不编造趋势**。
- 这个规模下**没有**做的对比（Iceberg vs Doris 内表查询延迟、大数据量下实时 vs 离线）已登记为未采集项。

**若被追问**

- 被问"那你的性能结论有什么意义"：意义在于**基线**——没有基线就谈优化，等于把"感觉快了"当结论；而且基线里最有价值的结论（Agent 端到端 99.9% 在外部 LLM 往返、优化 SQL 几乎无意义）与数据规模无关。
- 依据：`docs/PERFORMANCE.md` 第 0、2.1、7 节；`docs/thesis/DATA_AND_LIMITATIONS.md` D 组。

### Q4. 行为事件到底是 20000 还是 40000？

**要点**（★ 本项在收口阶段**已被定案**，按 `DATA_AND_LIMITATIONS.md` E2 的现行口径答）

- **当前值 = 20000**，有**两条独立只读观测**支撑：① Kafka 源 topic `behavior_event` 的 latest 合计 = 6506+6592+6902 = **20000**（earliest 全 0、未被 retention 清理）；② Doris `COUNT(*)` = 20000 且 `COUNT(DISTINCT event_id)` = 20000。
- **40000 的唯一出处**是 `SPRINT_3.md` 第 2 节的事实核查表（注明"与 MySQL 1:1"），**没有观测时间**，而且**流量域在 MySQL 根本没有源表**（这正是 Sprint 3 自述、Sprint 4 才归档补齐的缺口）→ **判为当时的观测误差**，该行已改写并加审计注。
- **必须同时说清的"历史侧"**：`2026-09-26 13:18` topic 重建**之前**的真实状态**已不可考**（需要 Kafka topic 重建历史或 Doris 审计日志，当前不可得）——这是"**来源不可考**"，**不是"两种口径都对"**。
- **一条容易答错的口径**：**表内行数 = distinct `event_id` 基数 ≠ 链路处理量**（该 topic 的 latest 合计曾达 580000 = 29 × 20000；Doris 侧 UNIQUE KEY + merge-on-write 去重后才是表内的 20000）。所以"20000"是**去重后的表内行数**，不能被读成"这条链路一共只处理了 2 万条"。
- **关键一点：这不影响对账结论**——流量域对账的判据是分钟窗口的 `uv` / `pv` / **5 个行为计数（共 7 列）**（19643 个窗口、不一致 0、单边 0/0），**不是**实时 DWD 的行数。

**若被追问**

- 被问"那你论文里写哪个"：写**当前值 20000 + 判为观测误差的依据 + 历史侧不可考**，并保留"40000 的出处"这一条沿革（不删证据，但不再把它并列成"两个都成立"）。
- 被问"为什么行数不能当处理量"：见上一条口径说明；若被问"29 轮怎么来的"，如实说那是从 topic latest 合计反推的**线索**，本轮收口未逐轮取证，**属未采集**。

### Q5. 数据质量怎么保证？25 条校验具体查什么？

**要点**

- **组织方式**：一个清单文件 `infrastructure/quality/checks.conf`（每条含域/严重级/引擎/SQL/算子/阈值/说明/排查提示）+ 一个执行引擎 + 每条校验一个 SQL 文件（**必须返回恰好一个标量**）+ 一个可调度总入口。
- **25 条覆盖 7 类**：行数非空守卫、主键唯一、关键字段非空、枚举合法、漏斗单调、层间一致、金额关系、新鲜度；实测 Doris 侧 **24 通过 / 0 失败 / 1 跳过**（跳过的是 spark 引擎项，需 `--with-lake` 显式驱动）。
- **分两个引擎是有意的内存纪律**：`doris` 引擎走 FE 的 MySQL 协议、**不起 Spark**，可以在实时链路运行时随便跑；`spark` 引擎要读湖仓上的 Iceberg 表，需一次性 `spark-sql` 容器（驱动约 1 GB），因此**默认不跑**，受内存闸门约束。
- **失败路径是可执行的证明，不是一句声明**：`--proof-fail` 故意把两条校验的期望值改成不可能成立的值（`999999999999`、`-1`），断言必须返回退出码 1，实测两次都是 1，**然后恢复再跑一次**证明失败来自断言而不是数据被改坏。
- **一条实测教训**：新鲜度阈值第一版定 26h，实测数据事件时间最晚到 `T 日 13:16`，而按日调度的批处理在 `T+1 凌晨` 才算进 ADS，稳态滞后 **31.8h**——四条校验全红。最终定 **48h**（漏跑一整天会变 50~56h，必然报警），并把"稳态滞后 31.8h"写进配置注释。**一条恒红的校验比没有校验更糟。**

**若被追问**

- 被问"为什么把阈值留在 SQL 里而不是 YAML"：因为 SQL 是**可审计**的，比 YAML 里的表达式更容易逐条讲清楚；代价是**告警未接入**（下一条）。
- 依据：`docs/sprint/SPRINT_11.md` 第 3.1、4.1、7.6、10.1 节；`AGENTS.md` 第 15.11 节。

### Q6. 你怎么保证不是"跑通了就算"？

**要点**

- **验收脚本的退出码有意义**：分步 `[OK]/[FAIL]` + 统计 + 失败 `exit 1`；健康检查类脚本**禁止**"无论结果都返回 0"。
- **测试必须真实执行**：禁止只检查文件是否存在；冒烟测试必须校验数据内容（字段、行数、关系），不只是连通性。
- **失败路径可执行证明**（最抗质疑的一条）：`run-quality-checks.sh --proof-fail` 实测两次退出码 1。**一个从来没红过的断言，等于没有断言。**
- **防空集合假通过**：3 条行数非空守卫 + 1 条"ADS 窗口数 > 0"；MCP 两路径一致性比对之前先加非空守卫（"两边都为空"也是一种"一致"，但毫无意义）。
- **反面案例本身就是证据**：本项目反复出现的失效模式是"**成功信号不可信**"——命令返回成功、构建报成功、自检全绿，都不能替代回到目标状态去验证。

**若被追问**

- 被问"测试全绿说明什么"：说明**在环境处于目标状态时**测试通过——同一份全量测试在事故当天曾以四种面目出现（`306 passed/47 skipped` → `331/22` → `346/7 failed` → `353/0/0`），**每一次都看起来像代码问题**，实际全部是环境中间态。
- 依据：`AGENTS.md` 第 4.3、8 章、第 15.8、15.12 节；`docs/sprint/SPRINT_12.md` 第 8.4.1 节。

## 二、批流一致性（含审计边界）

> **这一组是全场重点。** 每题都涉及"主张 > 证据"的风险，答案必须**自带边界**。

### Q7. 你怎么证明两条链路算的是同一个数？

**要点**

- **前提一：事件与业务行一一对应**。实时指标算在 Kafka 事件上，离线指标算在 MySQL 业务行上；映射逐条列明（`ORDER_CREATED` ↔ `orders` 1 行且 `event_time = create_time`；`PAYMENT_SUCCESS` ↔ `payment` 行且 `pay_time IS NOT NULL`；`REFUND_CREATED` ↔ `refund` 1 行）。其中 `PAYMENT_FAILED` 的尝试时间在业务表里**没有独立字段**，明确规定**不允许**用 `create_time` 冒充。
- **前提二：粒度相同**。离线 ADS 特意输出 1 分钟粒度（`ads_batch_trade_1m`），与实时表同粒度、同字段名、同类型、同顺序。
- **前提三：口径同一份**。两侧都按 `sql/metadata/metrics.md` 计算；可加指标无事件补 0、比率指标分母为 0 留 `NULL`。
- **比对方式**：按 `window_start` 做 **FULL OUTER JOIN**（不是 INNER JOIN——用 INNER JOIN 会把"整行缺失"这类最严重的差异悄悄过滤掉），逐窗口比对，差异逐列落盘。
- **结果（带范围说）**：交易域 **11458 个窗口、不一致 0**，两侧 GMV 精确到分相等（51,890,375.77）；流量域 **19643 个窗口、不一致 0、单边窗口 0/0**。

**若被追问**

- 被问"这证明了什么、没证明什么"：证明的是**这两条链路在已发生的数据上给出同一组指标值**；**不能**证明任何单个数在业务上"正确"（那由与 MySQL 事实源的独立核对覆盖）。
- 被问"你怎么知道判据本身是对的"：见 Q15（判据打磨过两次，方向都是变严）。
- 依据：`docs/sprint/SPRINT_3.md` 第 3.2、7 节；`SPRINT_5.md` 第 9.2 节；`docs/thesis/EVIDENCE_MATRIX.md` 第 3 节。

### Q8. "11458 个窗口不一致 0"这句话能成立的范围是什么？（★ 高概率被追问）

**要点**

- **可成立的有界表述**（照这个说，不要加码）：
  > "在两侧数据范围求交、尾部留出 3 分钟安全边界后的**对账区间**内，对实时与离线产出的 1 分钟粒度指标表按 `window_start` 做全外连接，逐窗口比对交易域 **7 个可加指标 + 1 个去重指标**（去重指标两侧采用同一近似去重语义），在**缺失侧补 0** 的统一口径下，全部窗口的可加指标差值为 0。该结论**不覆盖对账区间之外**的数据，也**不包含两侧派生比率列**的逐窗口比对。"
- **不能从中推出的五件事**：① 两侧窗口集合相同（交易域无此断言）；② 两侧比率一致（比率不在判据内）；③ 整个数据集一致（区间外含最后 3 分钟明确未比）；④ 实时链路数据正确（流量域**已实测**有 1 个缺陷）；⑤ 生产环境成立（结论建立在合成数据集上）。
- **判据是"补零后数值相等"**：两侧缺失一律 `COALESCE(...,0)`，所以 `NULL` 与真实 `0` 不可区分——`is_match = true` 的语义是"**补零后数值相等**"，不是"两侧都真实产出了该窗口"。
- **8 个判据列的准确说法是"7 个可加 + 1 个去重"**（`order_user_cnt` 的实现是 `COUNT(DISTINCT user_id)`），**不能说"8 个可加指标"**。

**若被追问**

- 被问"那这个结论还剩多少分量"：分量在**逐窗口**而不是**总数**——总量相等推不出逐窗口相等，而逐窗口相等是更强的结论；并且它是**两个引擎、两套计算框架、两条独立链路**各自算出来的。
- 被问"补零会不会把真差异吃掉"：会存在理论漏洞——"一侧缺窗口 + 另一侧 8 个指标全为 0"会被判为 match；实际数据下"每分钟成交全为 0"的窗口不应存在，所以这是**理论漏洞而非已发生的缺陷**，但必须写进限制。
- 依据：`.tmp/audit-reconcile.md` 第 3.2、7 节；`docs/thesis/EVIDENCE_MATRIX.md` C-08、§3.4。

### Q9. 为什么会有 5504 个"两侧都是 0"的窗口？它们算有效证据吗？（★ 审计新增）

**要点**

- **事实**：交易域 11458 个对账窗口里，**5504 个（48.03%）两侧 GMV 均为 0**，属于**平凡一致**；真正承载判别力的是 **5954 个有业务量的窗口（51.97%）**。
- **为什么会有**：1 分钟窗口是固定骨架——只要窗口内发生过订单、支付、退款中的任一类事件，该窗口就有一行；而不同业务流的事件时间天然错位（支付发生在下单之后的另一分钟），交易本身又是分钟级稀疏的，于是大量窗口的两侧取值同时为 0。
- **它们算不算证据**：**不能把它们当独立证据**。报告口径必须写成"11458 个窗口中 5954 个有业务量、逐窗口一致；另有 5504 个窗口两侧均为 0（平凡一致）"，**不能**写成"11458 个窗口全部独立验证一致"。
- 反过来也要说清：**平凡一致不等于"没有价值"**——它至少证明两侧在"无事件窗口"上的**行是否产生、是否补 0、补 0 是否一致**这三件事上口径相同；但它证明不了任何有业务量场景下的等价性。

**若被追问**

- 被问"那你怎么不多生成点数据让窗口都有业务量"：那是数据规模问题（Q3），属开发规模；而且**稀疏窗口本身就是电商分钟级事实的真实形态**，把它改稠密反而偏离场景。
- 依据：`docs/thesis/EVIDENCE_MATRIX.md` 第 3.1 节；`sql/metadata/metrics.md` 第 2.1 节（空值约定）。

### Q10. 交易域和流量域的断言强度一样吗？

**要点**

- **不一样，必须分开说**：
  - **流量域**有两条显式硬断言——"仅实时侧有的窗口数 = 0"与"仅离线侧有的窗口数 = 0"（实测 0/0）。
  - **交易域没有**这两条断言，最接近的是"实时侧窗口数 ≥ 离线侧窗口数 × **90%**"的**覆盖率守卫**（注意是 90%，不是 100%）。
- 所以在交易域，"单边窗口 = 0"是 `mismatched_windows = 0` 的**推论**，而不是独立断言；在 5504 个零-零窗口的背景下，这个推论在**理论边界情形**下不成立。
- **这是两个域之间真实的断言强度不对称**，论文里不能把两者当成同一强度合并陈述。
- 另外还有一条差别：**交易域的验收脚本层比作业层更松**（验收层没有非空守卫/覆盖率/单边窗口断言，且取"最新批次"而非"本次批次"）——审计已把它列为待补项。

**若被追问**

- 被问"那你打算怎么办"：两条改进方向——① 给交易域补上与流量域同款的两条单边窗口断言；② 验收脚本改按本次 `batch_id` 取数，并补"窗口数 > 0"守卫。**补断言不改历史数字**，属收口阶段的加固项。
- 依据：`.tmp/audit-reconcile.md` 第 1、3 节；`docs/thesis/EVIDENCE_MATRIX.md` P1-1、P1-4。

### Q11. 为什么会有 0/0 窗口（静默窗口）？这算不算掩盖了问题？

**要点**

- **先区分两种"0/0"**：
  1. **两侧都是 0（平凡一致）**——Q9 的 5504 个，是数据稀疏造成的，不是掩盖；处置是"不把它当独立证据"，并用覆盖率与单边窗口统计把边界显式化。
  2. **"只比对两边都有的窗口"式陷阱**——这个陷阱**已经被防住**：判据用 `FULL OUTER JOIN`，单边窗口会保留成"不一致"行；汇总表记录 `realtime_only_windows` / `batch_only_windows`（流量域实测 0/0），让"差异为 0"有边界可核。
- **为什么必须显式统计单边窗口**：否则"某一侧缺了一批窗口"会被静默掩盖——两边都缺同一批窗口时，逐窗口比对照样全绿。
- **交易域仍有一处未闭合**：缺"单边窗口 = 0"的硬断言（见 Q10），因此我在报告里把交易域结论写成"区间内逐窗口指标一致"，而**不是**"两侧窗口集合相同"。

**若被追问**

- 被问"你怎么证明没有静默漏行"：诚实答案**分域回答**——流量域有硬断言（0/0）；交易域只有 90% 覆盖率守卫 + 补零比较，**不能**宣称窗口集合相同。
- 依据：`docs/sprint/SPRINT_5.md` 第 9.2 节；`docs/thesis/EVIDENCE_MATRIX.md` §3.3、§3.4。

### Q12. `click_rate` 那个缺陷到底怎么回事？错在哪一侧？（★ 必答）

**要点**

- **现象**：窗口 `2026-03-21 19:23:00`——实时侧 `view_cnt=2 / click_cnt=1`，但 `click_rate` 落库为 **0.0000**；按口径公式 `1/2` 应为 **0.5000**。离线侧同窗口算出 **0.5000**，是对的。
- **五步判定（先定因，再定判据）**：① 打印双方原值，差 0.5000；② 看差值量级——差在**小数点后第一位**，不是末位 → **排除浮点/舍入**，所以**不能加容差**；③ 用**第三方判据**定责：`1/2 = 0.5` 是纯算术，不需要比较两侧 → 离线侧 0 个矛盾窗口、实时侧 1 个；④ 找旁证——实时侧 `click_rate` 全表取值只有 `{0.0000, NULL, 1.0000}`，而全表满足 `0 < click_cnt < view_cnt` 的**分数窗口恰好只有这 1 个**；⑤ 对照回归——交易域同一判据 11459 个窗口 0 矛盾。
- **影响范围已量化**：7 个对账判据列在全部 19643 个窗口逐窗口一致 → **不影响任何已发布口径的指标数值**，只影响实时侧 `click_rate` 这一个派生列的一行。
- **定性必须说准**：它是"**已定位、已用第三方判据定责、判据已改严、证据已落盘、经成本评估后决定不修**"的真实缺陷，**不是**"未解决"，也**不是**"环境问题"。

**若被追问**

- 被问机制层面的原因：**标注为待确认**——Flink SQL Gateway 的 REST 接口未响应、`sql-client.sh` 在本机依赖配置下会挂住，**未能单独隔离验证**；结论不依赖机制解释。
- 依据：`docs/sprint/SPRINT_5.md` 第 9.3 节；`sql/metadata/metrics.md` 第 3.3 节；`docs/DECISIONS.md` ⏳10。

### Q13. 为什么不修它？（★ 必答，考的是成本判断）

**要点**

- **修它的代价**：缺陷在实时链路（Flink 作业）。`behavior_event` 的全部 20000 条消息**仍在 Kafka 里**（earliest = 0），重部署会把它们**从 earliest 全量重放**，覆盖实时侧全部 19644 个窗口——那是实时链路的一次全量重建。

**若被追问**

### Q14. 比率列为什么不在判据里？这不是放宽容差吗？

**要点**

- **不是放宽容差，是判据换型**：7 个计数列逐窗口相等 ⟹ 由计数派生的比率在数学上**必然**相等；所以把比率排除出主判据**不损失信息**，反而换上了更强的一条：**每一侧的比率必须等于用它自己的计数按公式重算的值**（自洽性判据）。
- **为什么新判据更强**：它**不需要两侧一致就能判定是谁错**，而且"两侧一起错成同一个值"这种缺陷两侧比对抓不到、自洽性判据能抓到（本项目**就抓到了一个**）。
- **代价必须一起说**：① 实时的自洽性矛盾窗口数**不进入 `is_pass`、不阻断作业退出码**（作者原话的理由是：写成会失败的 check 会让离线作业替实时链路的缺陷"背锅"）；② 交易域的派生比率列**根本没进对账**（连留证都没有）。
- 所以准确表述是：**"两侧计数逐窗口一致"被证明；"两侧比率逐窗口一致"不是判据，只有 `diff_*_rate` 留证列**。

**若被追问**

- 被问"文件头注释写着'等于零才算真正全部一致'怎么解释"：那是**文档与代码冲突**——按"代码 > 文档"的证据优先级，以代码为准；该注释表述不成立，已记录待订正。
- 依据：`.tmp/audit-reconcile.md` 第 5.2~5.5 节；`docs/thesis/EVIDENCE_MATRIX.md` §3.3。

### Q15. 判据被打磨过几次？你从对账这件事学到什么？

**要点**

- **两次打磨，方向都是"变严"**：
  1. **离线表多一个分区列**：`traffic-ads` 自检 34/35，唯一失败项是"字段顺序与实时表一致"。根因是 `DESCRIBE` **会把分区列一并列出**，12 个数据列被拿去和 13 列比较——**是断言写错了，不是数据错**。修法改成"数据列逐列同序 + 分区列只在最后"，并补一条"除分区列外无多余字段"的反向守卫。
  2. **比率列按各自计数重算**：见 Q14，从"两侧比率相等"换成更强的独立判据。
- **教训**：**断言失败时，第一件事是确认"这条断言在说什么"，而不是先怀疑数据。断言写错比没有断言更危险**——它会把人引向"数据错了"的错误结论，浪费时间去查一个并不存在的问题。
- **同类案例至少四处**：`COUNT(DISTINCT)` 是近似算法不能拿来做相等断言；`SUM(1d.order_user_cnt) == DWD 全局去重` 这条断言本身是错的（去重计数不可加）；`awk '$1=="amount"'` 取不到类型；归档自检"在空表上空洞地通过"。

**若被追问**

- 被问"能不能举个'判据先错、数据后被证明对'的量化例子"：类目 `1d` 行数 vs `1m` 行数（2834 vs 5998）——看起来像"离线少算了一半数据"，实际数据完全正确，是断言用的函数不准（`COUNT(DISTINCT)` 近似）与粒度不同所致。
- 依据：`docs/sprint/SPRINT_5.md` 第 9.4 节；`SPRINT_3.md` 第 8.3、8.4 节。

## 三、Lakehouse 与 Iceberg

### Q16. 为什么用 Iceberg？Parquet 外部表不行吗？它到底解决什么问题？

**要点**

- **矛盾**：Parquet 外部表（`EXTERNAL TABLE ... STORED AS PARQUET`）能用，但缺三样：**没有 ACID**（写入中途失败会留下半份数据，只能靠"重跑覆盖"兜底，而那要求每次整分区重写）、**没有 schema 演进**（源表加字段只能改 DDL，历史数据与新数据的一致性靠人管）、**没有时间旅行**（无法回答"昨天的表长什么样"，出问题也无法回滚到某个快照）。
- **候选与否决**：REST Catalog（要多一个常驻进程，内存不允许）、Hadoop Catalog（用文件系统当目录、无中心元数据，无法与既有 HMS 表共存）；最终选 **HiveCatalog**，因为机器上已有 Hive Metastore 3.1.3，Sprint 2 的 Parquet 外部表也在它里面——**两种表格式共用同一个目录，迁移期可以逐表对照**。
- **代价**：引入过程中遇到一次 Java 字节码版本冲突，版本从任务书写的 1.11.0 **降到 1.10.2**（1.11.0 的 class 文件是 major 61 即 Java 17，而 Spark 镜像的 JRE 是 Java 11）。
- **明确不引入**：Flink-Iceberg 连接器——没有"流式写湖"的需求，**不为了"看起来完整"而加**。

**若被追问**

- 被问"1.11.0 的官方支持范围不是含 Java 11 吗"：**"官方支持在 Java 11 上运行"与"其发布的字节码要求 Java 17"是两件不同的事**——前者是兼容性声明，后者是构建目标；教训是"不猜版本"要防的不只是版本号，还包括**支持范围**。
- 依据：`docs/sprint/SPRINT_5.md` 第 1、1.1、2.3.1、3.1、8.4 节。

### Q17. Lakehouse 与传统 Hive 数仓的区别是什么？

**要点**

- **传统 Hive 的形态**：表 = 目录 + 文件（Parquet/ORC）+ Metastore 里的 schema 记录；**表的"身份"由目录位置决定**，提交语义弱（写完文件才算，失败留残留），分区与 schema 变更靠人管。
- **Lakehouse（本项目用 Iceberg 做表格式）**：把"表"的语义从目录搬进**元数据层**——快照、manifest、schema、分区 spec 都是**可原子提交**的元数据；因此同一份 Parquet 数据获得了 ACID 提交、schema 演进与时间旅行。
- **本项目的落地形态**：Parquet 外部表（`spark_catalog.lakehouse.*`）与 Iceberg 表（`iceberg.lakehouse_iceberg.*`）**并存**，迁移期逐表对照，出问题能立刻退回——这是"可回滚"的具体含义。
- **一条必须带的限定**：Iceberg 的**快照可见性与时间旅行只验证到"可用"**（`verify-sprint-5.sh` 断言快照数 > 0、`VERSION AS OF` 最早快照可查且行数与当前一致，**仅 1 张表**），**没有在业务流程中实际使用**过"回滚到某个快照"。

**若被追问**

- 被问"那你这算不算真正的 Lakehouse"：本项目的贡献在**表格式迁移 + 迁移验证**这一段；"湖仓融合"的完整形态（统一 catalog、流式入湖、时间旅行用于生产回滚）没有做到，属展望。
- 依据：`docs/sprint/SPRINT_5.md` 第 1、3.1、8.1 节；`docs/thesis/EVIDENCE_MATRIX.md` §4.2 K 行。

### Q18. Iceberg 迁移验证到什么程度？（★ 审计收窄过，务必按这个说）

**要点**

- **逐表核对的是三个维度**：① 表目录身份（`DESCRIBE EXTENDED` 的 `Provider == iceberg`，取不到值也算失败）；② 行数（`COUNT(*)` 整数精确相等，无容差）；③ **6 个金额列**（`gmv` / `amount` / `payment_amount` / `refund_amount` / `avg_order_amount` / `total_amount`）的**整表合计**（`CAST(SUM AS STRING)` 等值，`DECIMAL` 精确比较）。
- **加上清单完整性**：作业末尾断言"Iceberg 库表数 == 迁移清单表数"；验收脚本另有**逐个表名核对**（23 张全在）与**反向核对**（库里没有清单之外的表）——反向那条比"数量 == 23"更强。
- **在这三个维度上未发现差异**。**不能**说"没有改变数据"（无限定）——全部证据都是**聚合量与表身份**，**没有任何一条断言触及行内容**。
- **未验证的维度有 11 条**（列在报告里）：字符串字段内容、时间字段（含时区/精度/类型映射）、`NULL` 与空串（`SUM()` 忽略 NULL，所以"NULL→0"金额判据抓不到）、decimal 精度与舍入、分区布局与分区值、schema 等价性（列顺序/可空性，且 `CREATE TABLE IF NOT EXISTS` 在表已存在时会静默复用旧定义）、重复行与唯一性、快照与元数据正确性、**回滚可行性**（无演练）、压缩编码与表格式版本（"Iceberg v2 / snappy"是**配置与建表属性**，没有读回断言）、行级完整性。
- **一句话边界**：能证明的是"**表在那儿、行数对得上、6 个金额列的总和对得上**"；**不能**证明任何一行、任何非金额字段、任何分区的内容一致。

**若被追问**

- 被问"为什么不做逐行比对"：双向 `EXCEPT ALL` 或有序哈希比对是可行方法，但 23 张表全做需要 Spark 会话与额外时间，而当时内存是硬约束；这是**未做**，不是"做了没发现"——两者必须区分。
- 依据：`.tmp/audit-iceberg.md` §1.1、§2、§3 问题 2；`docs/thesis/EVIDENCE_MATRIX.md` C-10、C-11、§4.3。

### Q19. `60/60` 与 `70/70` 是怎么回事？为什么有两个数？

**要点**

- **它们不是同一判据在同一次运行下的两个结果，而是两次运行的清单范围不同**：
  - **60/60**：范围 **18 张表**（当时流量域尚未建模），阶段 4 首次成功迁移；出处是 `SPRINT_5.md` 第 8.1 节的原文行 `✅ [check] ===== 60/60 通过 =====`。
  - **70/70**：范围 **23 张表**（18 张 + 5 张流量域表），流量域分层建成后复跑。
- **构成（已独立复算）**：`60 = 18 Provider + 18 行数 + 23 金额列 + 1 库表数`；`70 = 23 + 23 + 23 + 1`。
- **差值 70 − 60 = 10 = 5 张新表 × 2 项（Provider + 行数）**——5 张流量域表**一个金额列都不在核对清单里**，所以金额条数两次都是 23。这也说明：**23 张表那次并没有比 18 张表那次多验任何"新维度"**。
- **证据等级不同，必须标注**：`60/60` 有原始 `[check]` 输出行，且四个组成部分可由代码 + DDL 复算；`70/70` **只有一句汇总额，没有原始逐项细目**——所以它只作"口径解释"，**不当作那次运行的实测细目**引用。
- **处理原则**：两个数字**都保留、各自按自己的范围标注**，不合并、不取平均、不互相替代——删掉其中一个等于丢掉一次真实验收。

**若被追问**

- 被问"为什么 `70/70` 没有细目"：仓库没记录；要补强只能**做只读取证**（检索历史日志里的那次 `[check] ===== 70/70` 输出），**不得为了验证一个数字重跑流水线**。
- 依据：`.tmp/audit-iceberg.md` §1.4、§3 问题 1；`docs/thesis/DATA_AND_LIMITATIONS.md` E1。

### Q20. 能回滚吗？时间旅行用过吗？

**要点**

- **"能退回"指的是并存**：迁移期间两版并存（Parquet 外部表 `spark_catalog.lakehouse.*` + Iceberg 表 `iceberg.lakehouse_iceberg.*`），任一侧出问题可以停用另一侧，**不需要恢复数据**。
- **Doris 侧不受影响**：实时链路始终在 Doris；离线结果装载进 `lakehouse_ads`，`--stage load` 可单独重跑。
- **真正的限制（主动说）**：Iceberg 的快照/时间旅行**只验证到"可用"**（快照数 > 0；`VERSION AS OF` 最早快照行数 == 当前快照，**仅 1 张表**），**没有**做过"删库重建"式的回滚演练，也**没有**"源表未被改动"的断言——代码层面能读出的只是"源库只被读、没被写"。
- **一处真实反例（已修）**：装载脚本曾经是"先 `TRUNCATE` 再 `INSERT`"，在湖仓不可用时留下**被清空但没装载**的服务层——这是**没有回滚路径**的破坏性顺序。已修：清空前先探测源端（S3 路径可读且至少一行），不满足就**保留现有数据并失败退出**。

**若被追问**

- 被问"为什么这个顺序危险"：`TRUNCATE` 与随后的 `INSERT` 虽然**各自原子**，但**两者之间不是原子的**；第二步失败时系统停在一个**比失败前更差的状态**——不是"装载没更新"，而是"数据没了"。对服务层（看板、接口、Agent 都读它）尤其致命。
- 依据：`docs/sprint/SPRINT_5.md` 第 3.2 节；`docs/sprint/SPRINT_11.md` 第 10.3 节；`docs/DECISIONS.md` ⏳12。

### Q21. 为什么用 MinIO 而不是 HDFS？

**要点**

- **这是一处被资源条件约束的设计变更，不是实现失败**：原设计的湖仓存储写的是 HDFS，实际改用 **MinIO/S3A**，原因是**内存不足**（`AGENTS.md` 第 15 节 Sprint 2 行明确标注）。
- **具体的帐**：本机 16 GB，实时链路常驻约 13.7 GB，可用常在 2.4~4.3 GB 波动；HDFS 要跑 NameNode + DataNode（JVM 常驻），而 MinIO 是单进程、S3 兼容，能用 **S3A 协议**被 Spark 直接读写。
- **代价如实说**：与原始设计文档的表述不一致（已在 AGENTS 与 Sprint 文档中标注偏差）；同时带来两个衍生限制——① `*.parquet` **不递归匹配**，必须写 `**/*.parquet`；② 对象存储凭据用的是 MinIO **root 账号**，且密钥通过 `spark-submit --conf` 传递，**任何能登录的用户 `ps` 就能看到明文**（未做最小权限账号）。
- **换来的是**：与既有 Hadoop 生态（Hive Metastore、Spark S3A）无缝衔接，且不新增常驻内存大户。

**若被追问**

- 被问"那 HDFS 的优势（本地性、追加写）丢了怎么办"：在本项目的数据量级（10³~10⁴ 行）与单机部署下，本地性收益可忽略；Iceberg 的提交语义由元数据层保证，不依赖 HDFS 的 rename 原子性。
- 依据：`AGENTS.md` 第 15 节 Sprint 2 行；`docs/DECISIONS.md` ⏳4；`docs/thesis/DATA_AND_LIMITATIONS.md` A4、B18。

### Q22. 迁移为什么"不原地改"？为什么 Iceberg 的 DDL 不落盘 `sql/`？

**要点**

- **不原地改的理由是可回滚**：Iceberg 的 `CREATE TABLE ... USING iceberg` 与 Hive 的 `CREATE EXTERNAL TABLE ... STORED AS PARQUET` 是**两种表**，同名替换会覆盖元数据、**且无法回滚**；因此 Iceberg 表用不同的库名建，迁移期逐表对照行数与金额。
- **DDL 不落盘的偏差如实记录**：项目规范要求"所有 DDL 必须存入 `sql/`"，这里改为**从源表 schema 推导**——理由是手写 18 张表的 DDL 会与源表定义**分叉**，而分叉只有在迁移之后才会被发现；schema 推导保证"两边定义同源"，且 `CREATE TABLE` 语句会打印出来可逐条核对。
- **权威定义在哪**：Iceberg 表的权威定义在 Metastore 里，`SHOW CREATE TABLE` 随时可取。
- **这条偏差的代价要说清**：它是"构造性保证"而不是"迁移后断言"——没有任何断言读回目标表 schema 与源比对，且 `CREATE TABLE IF NOT EXISTS` 在表已存在时会**静默复用旧定义**（而 `INSERT OVERWRITE` 是位置映射）。所以**不能说"schema 等价性已验证"**。

**若被追问**

- 被问"最危险的静默路径是哪个"：`partition_columns()` 解析失败 → 建出**无分区表**，而行数、金额、Provider、库表数**四项照样全绿**；对策是补一条"分区表必须有分区列"的断言（当前缺失）。
- 依据：`docs/sprint/SPRINT_5.md` 第 3.2、8.4 节；`.tmp/audit-iceberg.md` §1.3、§2 V5/V6。

## 四、技术选型：为什么用它、为什么不用它

> 每题按"**矛盾 → 候选 → 否决理由 → 代价**"四句答。

### Q23. 为什么用 Kafka？

**要点**

- **矛盾**：实时与离线必须共用**同一个事件入口**，否则"两条链路算的是同一个数"从一开始就不成立。
- **能力取舍**：用 **KRaft 模式**（4.2.1），**不部署 ZooKeeper**——少一个常驻组件；4 个 topic（`order_event` / `payment_event` / `refund_event` / `behavior_event`）各 3 分区、**副本 1**。
- **分区键有明确目的**：订单类事件用 `order_id` 作键、行为事件用 `user_id` 作键，保证同一订单或同一用户的事件落入同一分区，从而保证**分区内有序**。
- **代价**：副本 1 = 无高可用（开发环境定位，明确写在限制里）；`earliest-offset` 支持重放，这既是能力也是成本——**重放会把事件重新累加进窗口**，所以修一个实时侧缺陷要承担全量重放的风险（见 Q13）。

**若被追问**

- 被问"重复生产事件会怎样"：实测出现过 PV 合计 39987 vs 事件 20000（近 2 倍），根因是 SQL Gateway 为 session 模式、**重启 `flink-jobs` 容器不会取消旧作业**，旧作业把重放事件累加到了旧窗口状态。已修：新增 `scripts/cancel-flink-jobs.sh` 并在提交脚本启动时自动清场，健康检查增加"Flink 作业唯一性"检查项。**根治方案（按 `event_id` 去重）未实施。**
- 依据：`sql/metadata/kafka_topics.md` 第 4 节；`docs/sprint/SPRINT_1_VERIFICATION_STATUS.md` 第 5 节。

### Q24. 为什么用 Flink？为什么用事件时间而不是处理时间？

**要点**

- **矛盾的实质**：实时侧要"快速出数"，但**它还要能和离线逐窗口对齐**——如果实时侧按处理时间切窗口，同一批事件重放时会落到不同窗口，离线侧无论如何都无法与之逐窗口对齐。
- **所以选事件时间 + 1 分钟滚动窗口（TUMBLE）**：口径文件里写得很直接——**不用处理时间，保证乱序/重放结果一致**。这是后续逐窗口对账能够成立的前提。
- **一次实测得出的格式约束**：事件时间字段格式是 `yyyy-MM-dd HH:mm:ss.SSS`，不是 ISO-8601 带时区偏移的写法——Flink 的 JSON 格式解析器不接受后者，实测报 `Fail to deserialize at field: event_time`。**这是实测后的选择，不是风格偏好。**
- **代价**：Flink 栈是本机最大的内存占用方（常驻约 13.7 GB），因此批处理必须错峰、跑批前要暂停它。

**若被追问**

- 被问"为什么用 SQL 而不是 DataStream API"：本项目是清洗 + 窗口聚合，SQL + SQL Gateway 的形态更适合"可读、可复现、可交付"的目标；代价是 session 模式带来的作业残留问题（已用 `cancel-flink-jobs.sh` + 唯一性检查处置）。
- 依据：`sql/metadata/metrics.md` 第 1 节；`docs/data-source-design.md` 第 4.4、5.1 节。

---

### Q25. 为什么用 Doris？

**要点**

- **矛盾**：实时与离线必须落在**同一个查询层**，服务层与 Agent 才能并排对比两条链路的结果——这是"能对账"的工程前提，不只是"能查"。
- **Doris 同时满足两件看似矛盾的事**：① 承接**实时写入**——Routine Load + **UNIQUE KEY + merge-on-write**，同一窗口的多次中间态收敛为最新值（这也是"批处理期间暂停 Flink、恢复后从已提交位点续跑不重复计数"的基础）；② 承接**离线批量导入**——`S3()` 表函数直读 Parquet，一条 SQL 解决，**不引入 Stream Load 那种"读 S3 → POST"的额外 loader 进程**。
- **候选与否决**：ClickHouse 属规范中"未经批准禁止引入"的清单内组件，且引入它并不能解决"实时与离线是不是同一个数"这个问题——那只是把问题换个地方存在。
- **代价**：单 BE、FE 单点，**查询层无高可用**（开发环境定位，论文说明生产差异）；`*.parquet` 必须写 `**/*.parquet`。

**若被追问**

- 被问"UNIQUE KEY 幂等意味着什么"：意味着重复写入同一窗口**不会**产生重复行——这是错峰模式能成立的关键性质，否则"暂停期间事件堆在 Kafka、恢复后重放"就会造成重复计数。
- 依据：`docs/data-source-design.md` 第 5.1 节；`docs/sprint/SPRINT_3.md` 第 4.2 节；`AGENTS.md` 第 2.3 节。

### Q26. 为什么离线用 Spark？为什么不用 Flink 做批？

**要点**

- **离线要做的事**：MySQL 抽取 → Parquet(S3A) → Hive/Iceberg 四层建模（ODS→DWD→DWS→ADS）→ 对账 → 装载进 Doris；这些是**批式、可重跑、带作业内自校验**的任务。
- **选 Spark 3.5.7 的理由**：① 与 **Iceberg 1.10.2 + HiveCatalog** 的集成成熟（迁移作业就是 Spark SQL）；② **批读 Kafka 归档**（行为事件）有官方连接器；③ 它是**容器化的一次性作业、不常驻**——用完就释放内存，这与"16 GB 单机"的约束相容。
- **为什么不用 Flink 做批**：实时侧已经有一整套 Flink 常驻栈，再让它承担批量重算会与实时作业抢资源；而且**Flink-Iceberg 连接器被明确不引入**（没有流式写湖的需求）。
- **代价**：Spark 驱动跑在宿主机（client 模式）约 1.5 GB，是打穿内存那次事故的直接肇因——所以有内存闸门与错峰模式。

**若被追问**

- 被问"为什么用 PySpark 脚本 + `spark.sql()` 而不是纯 `.sql` 文件"：需要在作业内做**自校验**（每层跑完立即断言行数关系，不一致就以非 0 退出）；纯 SQL 交给 `spark-sql -f` 跑只能"跑完不报错"，**无法回答"算得对不对"**。
- 依据：`docs/sprint/SPRINT_3.md` 第 4.1 节；`SPRINT_4.md` 第 6.1 节。

---

### Q27. 为什么不用 CDC（Flink CDC / Canal）？

**要点**

- **如实说：没有做，是已知限制**。MySQL → Kafka 靠**生成器双写**，未用 Flink CDC / Canal。
- **为什么当时不做**：本项目没有真实业务库，生成器本身就是"业务系统替身"；引入 CDC 需要新增组件（属"未经批准禁止引入"的技术栈范畴）与额外常驻内存，而收益（更真实的增量捕获语义）对"口径一致性"这个研究目标不是必需。
- **代价很清楚**：① 双写意味着**一致性由生成器保证**（靠 `dataset_snapshot.json` 传递，不是数据库日志级的保证）；② 接真实数据源时，CDC 是**必须补的一环**——已列入展望。
- **反过来说**：正因为不依赖 CDC，事件与业务行的对应关系是**可设计、可核对**的，这让逐窗口对账在合成数据上能严格成立。

**若被追问**

- 被问"没有 CDC 你怎么保证不漏事件"：归档阶段的判据是**归档作业内的自检**（先数 Kafka 消息数、再数写入行数），本次验收窗口内为 20000 == 20000、703 个 `dt` 分区、16/16 作业内自检全过——**该等式只覆盖那一次验收窗口**，不覆盖验收之后的增量事件，且该环境 **Kafka 副本数为 1**，因此只说"**本次验收窗口内未观察到丢失**"，**不说无限定的"不会丢/不丢数据"**。另外：**表内行数 = distinct `event_id` 基数 ≠ 链路处理量**（该 topic latest 合计曾达 580000 = 29 × 20000，Doris 侧 UNIQUE KEY upsert 去重后仍是 20000）——引用时别把行数当吞吐。
- 依据：`docs/data-source-design.md` 第 7 节；`AGENTS.md` 第 15.8 节；`docs/thesis/DATA_AND_LIMITATIONS.md` A5、B1。

### Q28. 为什么用 Airflow？为什么不用 K8s / CeleryExecutor？

**要点**

- **矛盾**：离线流水线原本是**手工触发**，需要"按依赖调度 + 每层可见 + 独立重试"。
- **Executor 选 LocalExecutor**：CeleryExecutor 需要 Redis 或 RabbitMQ 做 broker，**两者都被技术栈禁令排除**；KubernetesExecutor 需要 K8s，同样被排除。本机 4 核、单机部署，**LocalExecutor 是唯一不引入新组件又能并发的选择**。
- **元数据库用 MySQL 而非 PostgreSQL**：Airflow 官方"首选"是 PostgreSQL，但项目规范明确禁止未经批准引入 PostgreSQL；而 MySQL 8.4 是 Airflow 明确支持的后端，**服务器上已经有这个 MySQL 8.4.11**——为零成本满足需求而引入一个被规范禁止的新组件，是把"技术选型"当成"照抄官方推荐"。
- **不部署 triggerer**：它只为 deferrable operator 服务，本项目全是短时 shell/Spark 任务；在可用内存仅约 2.5 GB 的前提下少一个常驻进程是实打实的收益——**这是有意的取舍，不是漏装**。
- **代价**：DAG 的每个 stage 都是独立任务（好处是可见性与重试，代价是任务数变多）；Airflow 与实时链路抢内存，批处理期间必须暂停实时链路。

**若被追问**

- 被问"为什么服务层不进 K8s"：数据层用 Docker Compose、服务层直装宿主机（apt + systemd）是本项目贯穿始终的取舍；对 Airflow 还有一条**决定性理由**——它要调的就是人手工跑的那些脚本，**调度应该复用人工入口，而不是平行实现一套**，否则"DAG 跑错、手工跑对"这类分叉永远说不清。
- 依据：`docs/sprint/SPRINT_4.md` 第 2.2、3.1 节；`docs/DECISIONS.md` D1~D4。

### Q29. 服务层为什么用 FastAPI 而不是 Spring Boot？

**要点**

- **先说清规范**：项目规范把服务层写成"**FastAPI / Spring Boot + Vue**"——**两者都在允许范围内**，这不是"违规绕过"的问题，而是取舍问题。
- **取舍（属设计论证，仓库里没有 A/B 实测记录）**：① 服务层是"一个只读查询进程"，FastAPI + uvicorn 的形态更直接；② **同语言收益**：与数据生成器、Spark 作业的自校验脚本、Agent、Airflow 的 Python 生态同源，venv 与依赖管理只有一套（代价已经暴露过一次：Airflow 与数据服务的 FastAPI 版本**硬冲突**，所以 Airflow 单独用 `.venv-airflow`）；③ **内存账**：本机 16 GB 里 JVM 已被 Flink/Spark 占用大半，再起一个 JVM 服务要重新算内存。
- **代价如实说**：Python 侧的接口层性能与类型安全弱于 JVM 方案；而且服务层直装宿主机意味着换机器要多跑几个安装脚本（已全部脚本化并保证幂等）。

**若被追问**

- 被问"那你为什么不用 Java 写 Agent 那部分"：Agent 的依赖面（LangGraph、MCP Python SDK、openai SDK）在 Python 侧最成熟，而**它被设计成不持有数据库凭据、只经 HTTP 取数**，所以语言边界与权限边界是两件事、互不影响。
- 依据：`AGENTS.md` 第 1、2.1、3 章；`docs/DECISIONS.md` D1、D3。

### Q30. 检索为什么用词法而不是向量？为什么不用 Milvus？（★ 必答）

**要点**

- **三条可核实的事实约束**（不是偏好）：① DeepSeek 官方 API 只提供对话补全、**没有 embeddings 端点**（`/v1/embeddings` 返回 404）；② **本机放不下本地 embedding 模型**（4 核 / 16 GB，实时链路常驻约 13.7 GB，可用约 4.3 GB）；③ **向量库属项目规范明确禁止未经批准引入的技术栈**（Milvus / Elasticsearch）。
- **若坚持向量检索**，就必须再引入一个外部供应商与 Key，或引入一个跑不动的本地模型——**两条路都更差**。
- **词法检索在本项目是"够用"而不是妥协**：语料只有几十篇（实测 65 篇）；提问高度依赖关键词（`GMV`、`UV`、`复购率`、`ads_batch_trade_1m`、`payment_success_rate`），正是 BM25 最擅长的精确词项匹配；**命中理由可解释**（能说清"因为命中了 `gmv` 与同义词扩展 `卖了多少钱→GMV`"），而向量相似度给不出这种理由——而本项目的回答本来就要给来源。
- **准确的技术描述**：**BM25 词法检索**（`k1=1.2`、`b=0.75`，含 idf 与文档长度归一化）+ **CJK bigram 自实现分词**（不引入 `jieba`）+ **显式同义词表**（JSON 配置，可审查、可增删、可测试）。**本项目未使用向量检索或 embedding。**
- **代价与对策已登记**：语义相近但用词不同的提问召回不到 → 靠同义词表覆盖；中文没有空格、词边界不明 → 自实现分词；将来要换向量后端 → 只替换 `Retriever.retrieve(query) -> docs` 这一个实现类。

**若被追问**

- 被问"那这还能叫 RAG 吗"："RAG"作为**架构角色**（检索增强生成）成立，"词法检索"作为**实现**成立；要避免的是把 RAG 默认读成"向量检索路线"。文档里写清这是 BM25，**不声称语义检索**——**诚实描述比夸大更安全**。
- 被问具体实证：正例——问「最近一周卖了多少钱」（**不含 GMV 字样**）命中 `metric:gmv | sql/metadata/metrics.md:33`；**负例**——问「今天天气怎么样适合钓鱼吗」命中为空（只有正例的话，"把所有词都映射一遍"的坏配置也能全绿）。
- 依据：`docs/sprint/SPRINT_9.md` 第 2.1、2.2、2.3、9.3 节；`.tmp/audit-agent.md` §C。

### Q31. 为什么用 LangGraph？单轮工具调用不行吗？

**要点**

- **单轮循环有三处结构性问题**：① 没有显式的**规划**产物（模型第一轮就可能直接写 SQL，口径查询变成"看心情"，且没有可审查的规划留下）；② 没有独立的**校验**步骤（查询返回 HTTP 200 就等于"这步过了"，没人检查结果是否为空、分母是否为 0）；③ **重试不是一等公民**（靠模型自己看到错误文本后"愿意"再试，轮次用尽就强制收尾，无法回答"到底重试了几次、为什么停"）。
- **落地的图**：`retrieve → plan →（规划成功）execute → validate →（有阻塞性问题且还有额度）reflect → plan → …… → summarize → END`；节点/边/上界经 `GET /graph` 对外可读（实测 **6 节点、8 条边**、三重上界）。
- **两个关键设计**：① `reflect` 之后回到 **plan** 而不是 `execute`——错误信息通常意味着**计划本身错了**，回到 execute 只是把同一条错 SQL 重放一遍，**那是重试，不是重新规划**；② **终止性有三重上界**（重试额度默认 2 / 工具调用总轮次默认 6 / 总耗时默认 120s），**收尾调用不携带 `tools`**，否则模型还能继续发起调用、图停不下来。
- **与前一阶段是复用而不是重写**：4 个工具与 `ToolBox` 原样复用、守卫与只读账号不动、原单轮实现保留作对照与回归基线。
- **代价**：多一个编排框架依赖（`langgraph 1.1.0`），且**每次反思重试 = 多一次规划 LLM 调用**——这是延迟的主要放大器。

**若被追问**

- 被问"警告会不会触发重试"：不会。只有**阻塞性问题**（不以 `[警告]` 前缀开头）才触发 `reflect`；`row_count == 0`、结果被截断、含 `null` 这类只要求**如实说明**，不重试。
- 依据：`docs/sprint/SPRINT_8.md` 第 1、3.1、3.3、3.4、9.3 节。

### Q32. 为什么用 MCP？它是不是又开了一条绕过守卫的路？

**要点**

- **定位是本项目的一条设计核心**：MCP 被定位为"**同一份只读能力的另一种暴露方式**"，**不是第二条取数通道**。
- **为什么必须这样定位**：如果 MCP 变成"另一条能取数的路"，那"不得绕过 sqlguard"这条铁律立刻就被绕过了——**因为绕过的方式恰恰是"再实现一遍"**。
- **落地方式**：两条路径（直连 HTTP / 经 MCP）的**终点、守卫、账号是同一个**（`POST /data/api/query` + `sqlguard` + `agent_ro`），差别只在"谁来发起那次 HTTP"；MCP 服务的依赖里**没有任何数据库驱动**，systemd 单元**没有** `EnvironmentFile=.env`。
- **实证**：同一 SQL 经 MCP 与经直连 HTTP 的结果**逐字段相同**、`executed_sql` 也相同（比对前先加非空守卫，避免"两边都空"的假通过）；经 MCP 发 DELETE 的真实返回是 `is_error=False` + `structured_content={"ok":false,"error":{"code":"NOT_SELECT"}}`，底层 HTTP 400 同码——**拒绝语义经协议透传后未丢**。
- **权限最小化**：暴露 **4 个只读工具**，与 Agent 的取数工具逐名相等；没有写工具、没有任意 HTTP 出口、没有文件读写。
- **为什么不做"能连 MCP 就用 MCP"的自动降级**：自动降级会让 MCP 路径在任何一次连接抖动后**悄悄消失**，而所有断言仍然全绿——那是最难发现的一类失效。因此路径由 `AGENT_DATA_PATH` 显式决定。

**若被追问**

- 被问"那 MCP 到底带来了什么"：把"权限最小化"从一句口号变成**可枚举、可审查的事实**（服务器声明它提供哪些工具，客户端可以 `list_tools()` 读出来）；以及失败语义可透传。
- **追加一句边界**：验收脚本里"两条路径 tables 一致"的断言**不覆盖逗号连接**——两侧都不识别逗号后的表，所以断言会一起"绿"（见 Q35；这也是修复清单里要求把该 SQL 补进这条断言的原因）。
- 依据：`docs/sprint/SPRINT_10.md` 第 2、3、5.2、9.2 节；`AGENTS.md` 第 15.12 节。

## 五、Agent 可信性与安全边界

### Q33. Agent 怎么保证不胡说？

**要点**

- **来源可核对**：回答附三样东西——**实际执行**的 `executed_sql`（守卫会改写 LIMIT，所以必须返回改写后的那一条）、命中的 `docs`（**带文件名与行号**，能当场翻到那一行核对）、以及 `tables`（**由服务端从 SQL 里提取**，不靠调用方自报；若让调用方自报读了哪些表，血缘字段就失去可信度）。
- **失败即失败**：查询失败必须返回真实错误，**严禁回退到编造数据或经验值**；MCP 不可达时工具返回失败结果，**不**自动回退直连。
- **口径有出处**：检索节点**每问必跑**（不是"让模型自己决定要不要查"）；如果语料里确实没有某个口径（例如"复购率"），要求**如实说明语料中没有**，不得编造公式。
- **过程可观测**：`validation` / `retries` / `graph.path` 都是响应字段，能看出它走了哪些节点、重试了几次。
- **实测两条**：问「复购率怎么算」→ 如实回答"口径文档里没有复购率的定义"并给出核查过程；问「用 `ads_traffic_1d` 查 PV/UV」→ 那是**真实存在但不在白名单里**的表，Agent 如实说明"未授权"并给出错误原文，**而不是假装没有这张表**。

**若被追问**

- 被问"它会不会直接编一个数"：这是"不得伪造查询结果"这条铁律的落点——所有数字都必须来自 `executed_sql` 的执行结果；服务端返回的血缘与口径定义随响应一起返回，可逐条核对。
- 依据：`docs/sprint/SPRINT_7.md` 第 1.1、3.3 节；`SPRINT_8.md` 第 9.5 节；`AGENTS.md` 第 10.1 节。

### Q34. Agent 怎么保证不能越权取数？

**要点**

- **进程边界即权限边界**：Agent 进程里**没有数据库凭据**，也**没有 mysql 客户端依赖**（依赖只有 6 项：`fastapi` / `uvicorn` / `openai` / `httpx` / `langgraph` / `mcp`），它只能经 HTTP 调只读数据服务取数——**"不得拥有数据库管理员权限"由架构保证，而不是靠代码自觉**。
- **四重证据**：① 无任何数据库驱动依赖；② 代码里没有直连（唯一出口是配置里的 `DATA_API_BASE`）；③ 配置读取的键白名单不含任何数据库键；④ systemd 以非 root 用户运行且做了基础加固，**没有** `EnvironmentFile`（库口令不进进程环境）。
- **SQL 安全检查放在服务端**：放在 Agent 里等于**让被约束者自己当裁判**。
- **数据库侧是独立的第二道**：专用只读账号 `agent_ro` 只有 `SELECT_PRIV`，写操作被 Doris 拒绝（实测 `Access denied; you need (CREATE)`）。
- **端口纪律**：数据服务 `127.0.0.1:8000`、Agent `127.0.0.1:8100`、MCP `127.0.0.1:8200` 均只绑回环，只应由 Nginx 反代访问。

**若被追问**

- **必须主动说的边界**：准确表述是"**Agent 进程不持有可用的数据库凭据，其全部取数必须经过 SQL 守卫与只读账号；守卫对显式声明的数据源（`FROM`/`JOIN`）强制表级白名单**"。**不能**说"Agent 读不到白名单外的任何表"（见 Q35：**P0-1 逗号连接绕过表级白名单：已修复并线上复验通过**，同批探针对照 14:56:19 → 15:13:24）。
- 另一条措辞边界：Agent 进程**内存里确实会短暂持有** `.env` 的全量键值（读文件时未按键白名单过滤），但**没有读点、没有驱动**，所以是"读到但用不了"——**不可**说"Agent 进程从不接触 `.env` 中的库口令"。
- 依据：`.tmp/audit-agent.md` §A1、A2；`docs/thesis/EVIDENCE_MATRIX.md` C-01、C-02。

### Q35. SQL 守卫怎么防绕过？逗号连接那条现在是什么状态？（★ 最高概率被追问）

**要点（按"五层 → 实证 → 缺口 → 状态"四段答）**

- **守卫是 5 层顺序检查**：① 必须以 `SELECT` 开头（不接受 `WITH`/`SHOW`/`EXPLAIN`）；② 拒绝分号多语句与 4 类注释（`--` / `/*` / `*/` / `#`）；③ **26 个禁用关键字**（DML/DDL/DCL + `into outfile` / `into dumpfile` / `load_file` / `benchmark` / `sleep`）；④ **表白名单**（16 张业务表 + 2 张元数据表 = 18 张）；⑤ **强制 LIMIT**（三种写法分别收敛，没有就补）。
- **已实证被拒的**：写/管理类语句、多语句、注释注入、元数据探测（`union` + `information_schema` 组合，**顺序无关**——这条曾有"按语序匹配"的缺口，已修）、显式未授权表、文件读写与 DoS 函数；另外强制 LIMIT 实测（请求 5 行 → `executed_sql` 带 `LIMIT 5`、`row_count=5`）。
- **已修复的缺口（必须主动说、且要说准）**：守卫**原来**的表名提取只认显式 `FROM` / `JOIN`，**逗号连接（隐式 CROSS JOIN）后面的表既不进白名单校验、也不进血缘**——因为**提取与校验共用同一个正则**，"没识别到"就等于"没校验"+"血缘漏报"（该提取逻辑已重做，见本问的 P0-1 状态）。
  - **已线上复现**（只读 `POST /query` 三组对照）：① 显式 `FROM ecommerce.test_connection` → 被拒 `TABLE_NOT_ALLOWED`（对照组，证明该表确在白名单外）；② `FROM dwd_trade_order_detail a, ecommerce.test_connection b` → **放行、`row_count=3`、返回真实数据，血缘只报 `['dwd_trade_order_detail']`**；③ 显式 JOIN 白名单内两表 → 放行且血缘正确。
  - **为什么曾经严重**：凡 `agent_ro` 在 Doris 上有 `SELECT_PRIV` 的表（`ecommerce.*` 整库、`lakehouse_ads.*`、`information_schema.*`）当时都**可**用逗号连接读出，**包括白名单外的同库表**；而且血缘漏报会让"两路径 tables 一致"这类既有断言**一起变绿**，**发现不了它**——这正是它被定为最高级别缺陷的原因。
- **P0-1 状态（★ 按主控裁定的唯一说法讲）**：
  > **P0-1（逗号连接绕过表级白名单）：已修复并线上复验通过。** 链路：代码根因定位（`_TABLE_RE` 只认 `FROM|JOIN`，且校验与血缘共用该正则）→ 纯函数探针 → **线上复现**（2026-09-27 14:56:19：同一张表仅因写在逗号后即从 `REJECT` 变 `ALLOW`、`row_count=3` 读出真实数据，且血缘漏报）→ 先补对抗用例（含**反向防过度拦截**用例）→ 改守卫（FROM/JOIN 子句内按表清单结构推进、逗号仅当前面已是表项时才算分隔符、校验与血缘同源）→ 服务器重启 → **同批探针复验**（2026-09-27 15:13:24：绕过被拦为 `REJECT TABLE_NOT_ALLOWED`；白名单内 JOIN 仍 `ALLOW` 且血缘正确 —— **无过度拦截**）。

  **★ 同批探针的修复前 / 修复后对照表（全过程最有说服力的证据，被追问就翻它）**

  | 探针（只读 `POST /query`） | 修复前 14:56:19 | 修复后 15:13:24 |
  | --- | --- | --- |
  | 显式 `FROM ecommerce.test_connection`（白名单外表） | REJECT `TABLE_NOT_ALLOWED` | REJECT `TABLE_NOT_ALLOWED` |
  | **逗号连接** `…dwd_trade_order_detail a, ecommerce.test_connection b` | **ALLOW + `row_count=3` + 返回真实数据**，血缘只报一张表 | **REJECT `TABLE_NOT_ALLOWED`**（绕过被拦） |
  | 逗号连接（纯常量写法） | REJECT | REJECT |

  修复落地证据：`sqlguard.py` md5 `fab72ca2606abb3d882ad771b2421941`、mtime 15:05（修复落地并重启生效）；观测时间 2026-09-27 15:13:24 CST（只读 `POST`）。
  - **定性/定级**：定性是**权限边界不完整**，不是守卫崩溃；定级为最高级别缺陷（它曾使"Agent 只能读到白名单内的表"这一主张**不成立**）。
  - **为什么"先用例、后改守卫"**：反向用例盯的是"**逗号不是表名**"——列分隔的逗号、`GROUP BY` / `ORDER BY` / 函数参数里的逗号都不许被误判，否则所有多列查询都会被误拒；**那不是更安全，那是把功能打坏**。

- **因此措辞收窄为**（照这个说）："**守卫对显式声明的数据源（`FROM`/`JOIN`）强制表级白名单**"。

**若被追问**

- 被问"为什么 `agent_ro` 是整库授权"：`install-web.sh` 给的是 `ecommerce.*` + `information_schema.*`，`load-batch-to-doris.sh` 追加 `lakehouse_ads.*`——**"守卫白名单"与"数据库授权"两层之间存在落差**，这正是该缺口能读出白名单外同库表的原因；加固方向是把授权也收到表级。
- 被问"还有别的没覆盖的吗"：还有三类**规则有效但无对抗用例**（`export`/`import`/`replace`/`rename`/`backup`/`restore`/`kill`/`shutdown` 这 8 个关键字、子查询内的越权 `FROM`、非句尾的 LIMIT）——探针实测规则**当前有效**，缺的是**回归保护**；另有 LIMIT 正则锚定句尾导致 UNION 前序各支不受 `max_limit` 约束（行数上限而非权限问题）。

### Q37. 反思重试是真触发过，还是代码里写着？

**要点**

- **分成三层答，不能合并成一句**：**能力存在** → **测试触发过** → **线上使用分布未采集**。
- **能力存在**：`reflect` 节点、`retries` 计数（只在真正要重规划时自增）、三重终止上界（重试额度 / 工具轮次 / 总超时）都在代码里；重试额度默认 **2**。
- **测试触发过，两层都有**：① 单元测试断言**完整图路径**（`retrieve → plan → execute → validate → reflect → plan → execute → validate → summarize`）与"错误原文真的进了第二次规划上下文"——但那是 **mock 替身**（预设 LLM 消息与工具结果，不发 HTTP、不连库）；② **线上验收脚本**用"查一张存在但未授权的表"制造**必然失败**，读真实响应断言执行轨迹含 `reflect` 与 `plan`、且失败码命中 `TABLE_NOT_ALLOWED`。
- **数字必须说准**：线上验收脚本断言的是 **`retries ≥ 1`**，**不是 `= 2`**；`= 2` 只出现在 mock 单元测试里。
- **未采集**：**线上问答的平均重试次数/重试率没有统计**——验收里的失败是脚本**主动构造**的问法，不是用户自然提问。
- **一次额外发现**：性能采集那一次 `/ask` 的 `retries=1`，说明那 19.2 秒里**含一次重试的代价**，不是一个"干净单轮"的延迟。

**若被追问**

- 被问"为什么回到 plan 而不是 execute"：见 Q31——错误信息通常意味着计划错了；回到 execute 是重放不是重规划。实测第二版计划会明确写出"上一版失败原因读明白了……属于猜测，踩坑了"并改变做法。
- 依据：`.tmp/audit-agent.md` §B1~B3；`docs/thesis/EVIDENCE_MATRIX.md` C-05、C-06。

### Q38. MCP 与直连"逐字段一致"的口径和边界是什么？

**要点**

- **口径**：同一 SQL 经两条路径的结果，比对的是**规范化后的 `rows` 逐字段** + `executed_sql`——**不是字节级报文**；且比对**之前先加非空守卫**（"两边都为空"也是一种"一致"，但毫无意义）。
- **结论**：`verify-sprint-10.sh` **84/0/0**；结果逐字段相同、`executed_sql` 相同。
- **边界一**：验收脚本里"两条路径 `tables` 一致"的断言**不覆盖逗号连接**（两侧都不识别逗号后的表）→ 对 Q35 的缺口会**一起变绿**，因此**不能**用这条断言证明血缘正确；修复清单已要求把这条 SQL 补进去。
- **边界二**：样本是验收脚本**主动构造**的用例集合，不是随机流量；没有做接口层模糊测试。
- **一条设计取舍**：非取数工具（如检索、规划协议）**不走 MCP**——它们本来就不是取数能力，塞进去会让"最小能力集合"这个说法失真。

### Q40. 性能怎么样？有没有做并发测试？（★ 必答，必须带边界）

**要点**

- **先给可成立的一句话**：
  > "在当前**单机实验环境**（腾讯云 4 核 / 16 GB、`127.0.0.1` 回环、无并发压力、单请求串行、只读接口每项 **n=7** 取中位数且数据处于**热缓存**状态）下，只读接口点查 / 聚合 / 两表关联中位数为 **8.5 / 8.3 / 11.7 ms**、`GET /overview` **53.8 ms**。"

### Q41. Agent 一次问答要 19 秒，是不是你们平台太慢？

**要点**

- **同一份证据恰恰证明相反**：数据侧只占 **0.1%**（检索 2.9 ms + 取数 15.4 ms = 18.3 ms），**99.9% 在外部 LLM 服务往返**。
- 所以 **19.2 秒既不是数据平台的能力，也不是数据平台的瓶颈**——**必须显式否定**"这 19 秒是数据平台查询耗时"这个读法。
- **优化方向只有一个**：减少 LLM 往返次数或换更快的模型；**优化 SQL 与索引在 Agent 端到端延迟上几乎没有意义**（这是本基线最有价值的结论）。
- **诚实边界**：那个 99.9% 是用**差值法**算的（`总量 − 检索 − 取数`），**不是**对模型内部推理时间的测量；它包含两次 API 调用的网络往返 + 服务端推理 + token 生成，**不得**表述为"模型推理耗时"。
- **一条放大器**：每一次反思重试 = 多一次规划 LLM 调用；那次采集 `retries=1`，说明 19.2 秒里含一次重试的代价。

**若被追问**

- 被问"那数据平台到底快在哪"：SQL 层很快——点查/聚合/关联都在 8~12 ms（客户端实测），服务端自述 `elapsed_ms` 只有 4~6 ms，**约 3~6 ms 的差值是 HTTP + JSON 编解码的常数开销**。
- 被问"为什么不自己做推理"：本机放不下模型（实时链路已占 13.7 GB），且 DeepSeek 官方 API 只提供对话补全端点。
- 依据：`docs/PERFORMANCE.md` 第 1.3、4.2、4.3 节。

### Q42. 批量作业为什么要 81 分钟？

**要点**

- **固定成本 149.8 s**：`pause_realtime`（18.5）+ `restore_realtime`（131.3）——错峰模式暂停/恢复 Flink 栈并自检的开销，**与数据量无关**。
- **真正的耗时大头是四个分层/归档作业**：`archive`(363) + `dwd`(304) + `dws`(400) + `ads`(447) = **1514 s，占 9 个任务耗时合计的 76%**——这是 Spark 作业的**启动与 shuffle 成本**（本机单 worker、driver 768m）。
- **装载与对账其实很便宜**：`load_to_doris` 128.8 s（`S3()` TVF 直读 Parquet）、`reconcile` 138.8 s；两项加起来不到 270 s。
- **所以判据很清楚**：要压缩端到端时间，应当从**分层作业的 Spark 启动与分区数**入手，**而不是**去优化装载或对账。
- **两个数必须一起给**："9 个任务耗时合计 1992.3 s"与"端到端约 81 分钟"**不相等**——中间有 48 分钟的重试/等待窗口（该 run 的 `ads_layers` 有多次 attempt）。只报小的那个会误导。

**若被追问**

- 被问"能不能并行"：Airflow 里 `ods_extract` 与 `archive_behavior` 是并行的（数据源不同），但**其余按依赖串行**，且 `max_active_runs=1`——**不允许两次批处理重叠**（重叠必然打穿内存）。
- 依据：`docs/PERFORMANCE.md` 第 3.1、3.3 节；`docs/sprint/SPRINT_4.md` 第 5.1 节。

### Q43. 16 GB 内存怎么同时跑实时和离线？闸门拦过东西吗？

**要点**

- **不是"要"，是"只能"**：本项目只有这一台服务器（4 核 / 16 GB），实时链路常驻约 13.7 GB。
- **做法是错峰而不是并行**：`batch-mode.sh` = 暂停 Flink 栈 → **内存闸门检查**（可用 < 3000 MB 直接拒绝启动）→ 跑离线流水线 → 恢复 Flink 栈并跑健康检查自检。实测暂停实时链路可释放约 **1.65 GB**（2282 → 3935 MB）。
- **四层防护**：① 拒绝启动（可用 < 3000 MB 直接拒绝；已有 Spark 作业时拒绝叠加）；② 错峰执行；③ 限制上限（驱动/执行器各 768m，`spark-submit` 容器补 `mem_limit`）；④ 4 GB swap 兜底（swappiness=10，**故意不写 fstab**，因为 Doris BE 不允许在有 swap 的机器上启动）。
- **闸门真的拦过**：实测**主动拒绝过一次批处理**（当时可用 2258 MB）——**拒绝而不是硬跑**，这正是"闸门按设计工作"的证据。
- **为什么没调低闸门**：调低闸门是把保护拆掉，**错峰才是正解**。
- **代价**：批处理期间实时链路暂停，看板曲线会延后追上（**数据不丢**——Flink 从已提交位点续跑，重复部分由 Doris UNIQUE KEY 幂等覆盖）；这也是调度时间选凌晨 03:00 的原因。

**若被追问**

- 被问"暂停期间的事件怎么办"：继续堆在 Kafka；恢复后从已提交位点续跑；重复部分被 UNIQUE KEY + merge-on-write 覆盖。
- 依据：`docs/sprint/SPRINT_3.md` 第 4.4、8.1 节；`AGENTS.md` 第 15.5、15.8 节；`docs/DECISIONS.md` D11。

### Q44. 出过事故吗？

**要点**

- **两次，性质不同，都在报告里单列。**
- **第一次：批处理打穿内存，整机失联。** 服务器几分钟内完全失去响应（SSH 建不了会话、ICMP 无响应、nginx 与 FastAPI 全部超时），只能从云控制台强制重启。三层原因叠加：实时链路常驻 13.7 GB 只剩约 2.0 GB；Spark 驱动跑在宿主机（client 模式）约 2 GB 正好把余量吃干；**宿主机没有 swap**，内核无处回收页面，于是内存压力不是"变慢"而是**整机假死**。先出现的症状其实是 Doris BE 拒绝所有查询（`MEM_ALLOC_FAILED`），那才是第一现场。**数据无损失**（重启后容器自动恢复，health-check 11/11）。处置就是上面那四层防护。
- **第二次：原子换树同步把机器状态删了。** 为绕过同步脚本的"Spark 运行中"守卫，写了 `mv 旧树 → 解压 .new → mv 到位 → rm -rf .old`；因为只打包了一个子目录，`rm -rf` 把 **`.env`（唯一存有真实凭据的文件）、三个 venv、`airflow/airflow.env`、三个 compose 挂载的第三方 JAR** 一起删掉。
- **三条证据链（这是重点）**：① `docker compose` 直接不可用（它靠 `.env` 做变量插值）→ 范围从"某个服务配错了"缩小到"机器状态丢了"；② 报错是 `DatastoreDriverNotFoundException: ... was not found in the CLASSPATH`——说的是"CLASSPATH 配错了"，**真相是那个 JAR 被删了**——**报错指向的不是根因**；③ 磁盘上"文件丢失"表现为**一个空目录**（Docker 会在挂载点文件不存在时把它创建成目录），`ls -la` 看上去像有东西 → **判断挂载型文件是否存在必须用 `-f` + `-s`**。
- **根因**：**不是环境问题，是一个绕开守卫的决定**。守卫拦的是"运行中的脚本被半覆盖"；原子换树防住了半覆盖，却把**子集同步变成了整树替换**——子集之外的机器状态不再受保护。
- **沉淀的硬规范**：共享文件权限按**所有读者**定（`.env` 必须 `640 root:dpapi`，600 会让 Agent 起不来，且**故障现场与改动现场不在一起**）；**禁止任何原子换树同步**；凭据确认落盘前**禁止**重建容器；共享编排文件必须先落创作副本再同步、验收核对 md5。

**若被追问**

- 被问"这件事和验收有什么关系"：它说明**"测试全绿"只有在环境处于目标状态时才有意义**——事故当天同一份全量测试曾出现四种结果（含 7 条失败），**每一次都看起来像代码问题**，实际全部是环境中间态。
- 依据：`docs/sprint/SPRINT_3.md` 第 8.1 节；`AGENTS.md` 第 15.11 节；`docs/sprint/SPRINT_12.md` 第 8.2、8.4.1 节。

### Q46. 真正的工程亮点是什么？

**要点（三条，都要有可核对的证据）**

1. **把"批流一体"做成了可证伪的断言，并公开了判据的打磨过程**：交易域 11458 个窗口、流量域 19643 个窗口逐窗口比对，不一致 0；更重要的是给出了判据的两次打磨（分区列导致的"假失败"、比率列从"两侧相等"改为"每侧按自己计数重算"）——**判据本身必须先被验证**。
2. **在 16 GB 单机上同时承载实时与离线**：错峰批处理 + 3000 MB 内存闸门；闸门曾主动拒绝一次批处理（可用 2258 MB）——**把资源约束写进自动化闸门，而不是靠人记得**。
3. **把 Agent 的可信性做成了架构属性而不是提示词属性**：四件事——**进程边界**（Agent 进程无数据库凭据、无驱动依赖）、**可核对来源**（`executed_sql` / 带行号的 `docs` / 服务端提取的 `tables`）、**可数的失败与重试**（`validation` / `retries` / `graph.path` 都是响应字段，重试路径被真实触发）、**拒绝即失败**（守卫 + 只读账号两道拒绝；MCP 不做自动降级，避免"路径悄悄消失而断言仍全绿"）。
- **一条方法层面的亮点**：**失败路径的可执行证明**——`--proof-fail` 故意改坏期望值，断言必须退出码 1，实测两次都是 1，恢复后再跑一次证明失败来自断言。**一个从来没红过的断言，等于没有断言。**

**若被追问**

- 被问"还有吗"：把**同名不同范围**的数字按各自范围保留（`60/60` 与 `70/70`、`11458` 与 `11459`、**pytest `353`（修复前时点）与 `381`（修复后时点）、`verify-sprint-12.sh` `32/0/0`（修复前）与 `42/0/0`（修复后）**）——**不为"看起来一致"而丢掉一次真实验收**，这本身就是工程素养的体现。注意区分两类："同名不同范围"要**两个都保留**（并带时点）；而 `20000` 与 `40000` 属**另一类**（一个是当前事实、一个是判为错误的当时观测值），按 Q4 的口径答，**不要并列成"两个都成立"**。
- 依据：`docs/thesis/REPORT_DRAFT.md` 第 7.2 节；`AGENTS.md` 第 15.8、15.11 节；`docs/thesis/DATA_AND_LIMITATIONS.md` E 组。

### Q47. 如果要生产化，下一步做什么？

**要点（按"必须先做的加固"与"需要新条件的扩展"分两组）**

- **加固（有明确路径、不依赖新条件）**：① **P0-1 的后续**（**已修复并线上复验通过**，同批探针对照 14:56:19 → 15:13:24；下一步是把该 SQL 补进 MCP 两路径一致性断言，作为回归保护），并把 `agent_ro` 的授权从整库收到表级（"守卫白名单"与"数据库授权"两层之间的落差正是该缺口曾能读出白名单外同库表的原因）；② 给交易域补"单边窗口 = 0"断言、验收脚本改按本次批次取数；③ 对象存储最小权限（为 `lakehouse` 桶建专用 MinIO 用户，密钥改走 `credential.provider` 或环境变量注入）；④ 数据服务错误码区分 **400 / 503**（现在 Doris 的语句错误被统一包成 503，会让 Agent 把"我 SQL 写错了"误读成"仓库不可用"）；⑤ 结构债方案 B（只读的防漂移断言，零行为变更）。
- **扩展（需要新条件）**：① **告警接入**（Grafana 数据源与面板已就绪，成本主要在阈值设计）；② 接**真实数据源**（需引入 CDC）；③ **并发/压力测试**（需另开一台机器）；④ 公网链路延迟采集；⑤ Iceberg 时间旅行的实际使用（批处理前后对比、出错回滚）；⑥ 会话记忆与成本核算（当前每次提问独立、未统计花费）。
- **一句话总述**：**当前是"单机实验环境下、以证据闭环为目标"的交付，不是上线交付**——缺的东西是具体可列的（无 CDC、单副本无高可用、磁盘无冗余、接口无鉴权、明文 HTTP、无告警、无并发容量结论、实时与离线抢同一台机器）。

**若被追问**

- 被问"如果要上生产，第一件事做什么"：**先把"接口无鉴权 + 明文 HTTP + Airflow 用官方标注仅供开发测试的认证方案"这三件事一起解决**——它们是目前最直接的风险面；其余是容量与可用性课题。
- 依据：`docs/DECISIONS.md` 第三节与 ⏳2/⏳3/⏳4/⏳8/⏳12/⏳13；`docs/sprint/SPRINT_11.md` 第 10 节；`docs/PERFORMANCE.md` 第 7 节。

### Q48. 如果重做一遍，你会怎么改？

**要点**

- **判据先写测试再写作业**：本项目的多次返工都源于"判据本身没被验证过"（`DESCRIBE` 的分区列、`COUNT(DISTINCT)` 近似、`SUM(单日去重)` 不可加）——**把判据当作被测对象来写**会更早发现问题。
- **权限边界收敛成"一处定义、两处消费"**：白名单、Agent 数据地图、数据库授权目前是三处，逗号连接缺口正是"守卫白名单"与"数据库授权"之间的落差；应让授权也收到表级，并让三者由同一份配置派生。
- **机器状态显式化**：把 `.env`、venv、挂载 JAR 这类"不可重建的机器状态"在仓库里列成清单，并让部署脚本启动时自检——而不是等事故之后才知道它们存在。
- **结构上先收敛入口**：把阶段分发做成单一实现（现在两个脚本各有一份 `case`，已经因此踩过"改一处漏一处"的坑）。
- **监控从一开始就带告警**：现在是"只抓取与展示"，问题不会主动通知。

**若被追问**

- 被问"最想改哪一条"：**判据先写测试**——它成本最低、收益最直接，而且本项目所有"看起来很真的假故障"都出在这一类。
- 依据：`docs/sprint/SPRINT_5.md` 第 9.4 节；`docs/DECISIONS.md` 第四节；`docs/sprint/SPRINT_12.md` 第 4.1~4.3 节。

## 附录 A：绝对不能说的话（现场速查）

```text
❌「我们实现了数据赋能，形成了完整闭环」              ← 没有信息量
❌「性能提升了 30%」                                  ← 谁的 30%？怎么测的？
❌「数据是真实的」                                    ← 是合成的，直说
❌「这个没有缺点」                                    ← 每个选型都有代价
❌「大概能处理百万级数据」                            ← 实测是万行量级
❌「模型推理用了 19 秒」                              ← 那是差值，不是推理耗时
❌「两套系统没有任何差异」                            ← 有 1 个窗口的比率列缺陷，主动说
❌「11458 个窗口全部独立验证一致」                    ← 其中 5504 个是两侧为 0 的平凡一致
❌「Iceberg 迁移没有改变数据」                        ← 只验了表身份/行数/6 个金额列整表合计
❌「Agent 读不到白名单外的任何表」/「没有别的绕过办法」  ← 已被 P0-1 否证过一次（逗号连接，现**已修复并线上复验通过**）；这类全称断言不可穷尽验证
❌「平台已经可以上生产」                              ← 无并发测试、单副本、无鉴权、明文 HTTP
❌「我们用了向量检索做 RAG」                          ← 是 BM25 词法检索，未引入向量库
❌「做得还不够完善，时间比较紧」                      ← 空话，要具体到机制
```

## 附录 B：被问到"没做过的东西"时的统一答法

```text
第 1 句：直说没做（"并发测试没有做" / "这个数据我没有采集"）。
第 2 句：给客观原因（内存不允许 / 需要另开一台机器 / 需要 Spark 会话会与实时链路抢内存）。
第 3 句：给影响范围（"因此我的性能结论只覆盖单机、单请求、回环口径"）。
第 4 句：给"要做得需要什么"（一条具体的路径或判据）。
★ 不要用"时间不够"当原因，也不要把"没测"说成"测了没发现"。
```
