## 讲之前：先记住这张全景表

| 层 | 你在做什么 | 技术 | 一句话 |
|---|---|---|---|
| 数据源 | 用两个公开真实数据集当业务系统 | UCI Online Retail II、天池 UserBehavior | 不编数据，来源可查 |

| 离线 | 分层重算同一批指标 | Spark 3.5 → Parquet/MinIO → Hive Metastore 3.1 → Iceberg 1.10 → Doris | 按天精确重算 |
| 对账 | 两条链路逐窗口比 | Spark SQL FULL OUTER JOIN | 把「一致」变成可执行的检查 |
| 质量 | 25 条校验，失败就拦截 | SQL 判据 + 配置清单 + 退出码 | 数据不对就不往下游写 |

| 调度运维 | 错峰跑批、监控告警 | Airflow 3.3、Prometheus + Grafana | 机器 4 核 16 GB 也能跑 |

**版本一律钉死**（无 `latest`）：这是可复现的前提，也是答辩时容易被夸的点——「换台机器照着重跑，结果一样」。

## 第一讲 · 总纲：这个项目到底在解决什么

**一句话**：同一个业务指标，实时链路和离线链路各算一遍，我们**用程序证明它们相等**，而不是靠人对着两个看板数。

**为什么这是个问题**（讲给老师听的版本）：
> 电商数据天然两种形态——订单/支付/退款是必须精确对账的业务事实，点击/浏览是海量允许近似的事件。于是几乎所有公司都建了两套链路：离线用 Spark 按天跑，实时用 Flink 按分钟算。两套代码、两套存储、不同的人维护。同一个「销售额」在两张报表上出现两个数时，谁对？只能人工排查。业界的两个答案——Lambda 架构（拆开、互不干扰）和湖仓一体（存储统一、多引擎可读）——都没有回答「这两个数是不是同一个数」。

**本课题的回答**：三条
1. **一份口径**：所有指标的名称、聚合方式、时间窗口、判据列，只在 `sql/metadata/metrics.md` 定义，两侧实现都从它派生；
2. **逐窗口对账**：按 `window_start` 做 FULL OUTER JOIN，逐指标比对，不一致定位到具体某一分钟、某一列；
3. **判据本身也要被检验**：对账脚本要先能证明它会失败（构造反例），否则「全绿」可能只是脚本没在检查。

**可能被追问**
- 「这不就是数据比对吗？」→ 比对是手段；难点在**判据怎么定**（哪些列可比、比率列算不算、尾部未封窗怎么处理、单边缺失算不算失败），这些决定公开资料里都散落在实现细节中。
- 「你为什么不用一个引擎全做？」→ 单引擎能统一「计算怎么执行」，统一不了「两次独立计算出同一个数」；而且批流两种负载的资源特性不同。

## 第二讲 · 数据底座：两个真实数据集怎么变成「业务系统」

**解决什么问题**：没有真实业务库，就没有真实的事件流。早期版本用程序生成合成数据，被质疑「数据恰好相等是设计出来的」，所以这一版**全部换成公开真实数据集**。

**用了什么**
- 交易域：**UCI Online Retail II**（DOI `10.24432/C5CG6D`，CC BY 4.0），2009-12-01~2011-12-09，1,067,371 行原始明细。
- 流量域：**天池淘宝 UserBehavior**（CC BY-SA-NC 4.0），2017-11-25~12-03，100,150,807 条；按用户抽 10 万 → 入库 **10,098,974 条**。
- 脚本：`scripts/real-data/build_uci_dataset.py`、`build_tianchi_dataset.py`（建集）、`data-generator/src/load_real_data.py`（装载）。

**关键机制**
1. **字段语义映射**，不是简单改名：UCI 的发票 → 订单，`C` 前缀发票 → 退款，StockCode → 商品，Customer ID → 用户；天池的 `pv/cart/fav/buy` → 浏览/加购/收藏/购买（**源数据没有 CLICK**）。
2. **两个数据集互不重叠**：用户、商品、时间、国家都不重合。所以定位成**两个并列业务域**，靠主键偏移区分（交易域 id < 1,000 万，流量域 ≥ 1,000 万），不做跨域漏斗。
3. **清洗规则写进脚本、版本固定**：只保留有客户标识的行（原始 22.77% 缺失）、剔除 `POST/AMAZONFEE` 这类会计科目、11 组关键词派生类目、退款按 `(user_id, product_id)` 找窗口内最早订单关联（源数据 C 发票与普通发票号匹配率 **0/8,292**，无法按发票号关联）。
4. **不给编造的业务属性**：缺的字段用「未知」「UNKNOWN」或由 ID 派生的占位名，并在论文里声明——这比填假值更诚实。

**落到库里**：MySQL 5 表 `user / product / orders / payment / refund`（776,575 订单、GMV 17,068,016.12）；Kafka 4 topic `order_event / payment_event / refund_event / behavior_event`。

**可能被追问**
- 「真实数据为什么可信？」→ 三类证据：来源可查（DOI/官网）、规则脚本化（可被第三方重跑）、金额不漂（`quantity × price = amount` **776,575/776,575 精确相等**）。
- 「为什么不用全量 1 亿条？」→ 4 核 16 GB 的资源边界；抽样规则固定、可放大重放，论文里如实写明「约 10.1%」。

## 第三讲 · 实时链路：Kafka → Flink → Doris

**解决什么问题**：业务要「刚发生的事立刻能看到」。

**用了什么**：Kafka 4.2（4 个业务 topic，3 分区）+ Flink 1.20.1 SQL（8 个作业）+ Doris 4.1.4（UNIQUE KEY 表）+ Routine Load。

**数据怎么走**（`infrastructure/flink/sql/`，5 个文件）
1. `01_source_tables.sql` 建 4 张 Kafka 源表：`WATERMARK FOR event_time AS event_time - INTERVAL '5' SECOND`，`scan.startup.mode = 'earliest-offset'`；
2. `04_dwd_jobs.sql` 4 个作业写明细：`sink_dwd_trade_order_detail` 等；
3. `05_metric_jobs.sql` 4 个作业算指标：`TUMBLE(TABLE src_*, DESCRIPTOR(event_time), INTERVAL '1' MINUTE)`，输出 `ads_realtime_trade_1m / ads_realtime_traffic_1m / dws_traffic_overview_1m / ads_realtime_category_1m`；
4. 指标写回 Kafka 的 4 个 topic，再由 **Doris Routine Load**（`sql/doris/13_routine_load.sh`，8 个作业）装进 Doris。

**为什么这么选**
- **按事件时间开窗，不按处理时间**：数据晚到、重放、补数都还能算对；这也是历史数据（2011 年 / 2017 年）能重跑的前提。
- **Flink 只做算子、不直连 Doris**：中间隔一层 Kafka，Doris 挂掉不影响 Flink，还能回放；Doris 侧用 Routine Load 自带重试与位点管理。
- **UNIQUE KEY + MERGE ON WRITE**：同一窗口的多次更新只留最新版本。

**踩过并写进论文的坑（这是加分项，不是减分项）**
1. **整数除法**：`CAST(SUM(a)/SUM(b) AS DECIMAL(10,4))` 里两个 BIGINT 先做整数除法，比率全变成 0/1/2。判据抓出 1,302 个窗口自相矛盾，改成先把操作数转 `DECIMAL(20,4)` 再除。
2. **多代重放**：`--restore-only` 让 Flink 从 earliest 重放，同一窗口产生多代更新，Doris 侧后写覆盖先写，取到中间版本 → 实时 GMV 少 18%。修法：重置时清空 topic 让重放只有一代。
3. **TaskManager 堆太小**：`.env` 里 `FLINK_TASKMANAGER_MEMORY=2048m` 覆盖 compose 默认值，8 个 slot 每个约 200 MB，跑到 496 万条 OOM；改 6144m 并把 `managed.fraction` 降到 0.1。
4. **FE 堆被 fe.conf 覆盖**：镜像里 `JAVA_OPTS_FOR_JDK_17` 写死 8192m，容器环境变量无效 → FE 占 6.3 GB、Routine Load 报 `MEM_LIMIT_EXCEEDED`；挂只读 `infrastructure/doris/fe.conf` 限到 2048m。

**可能被追问**
- 「Flink 能保证精确一次吗？」→ 作业内是精确一次；跨系统这一段我们靠对账兜底，而不是声称端到端精确一次。
- 「重放会不会重复计数？」→ 会，所以指标窗口是**幂等覆盖**（UNIQUE KEY），不是累加。

## 第四讲 · 离线链路：Spark 四层建模 + 湖仓

**解决什么问题**：按天/按全量精确重算同一批指标，并且**可回溯**——三个月后要能复现「那天为什么是 17,068,016.12」。

**用了什么**：Spark 3.5.7 SQL + Parquet on MinIO（S3A）+ Hive Metastore 3.1.3 + Iceberg 1.10.2。

**四层建模**（`sql/hive/01~05`，`infrastructure/spark/sql/*`）
| 层 | 做什么 | 举例 |
|---|---|---|
| ODS | 原样落地，不做业务加工 | `ods_orders` 776,575 |
| DWD | 清洗 + 维度补全，一行一事 | `dwd_trade_order_detail` |
| DWS | 按主题聚合（天粒度） | `dws_trade_overview_1d` 604 天 |
| ADS | 可直接被接口消费的指标表 | `ads_batch_trade_1m` 40,360 |

**两条关键路径**
1. **抽取**：`extract_mysql_to_lake.py` 用 JDBC 把 MySQL 5 表抽成 Parquet；`archive_behavior_events.py` 把 Kafka 行为事件归档。
2. **迁移**：`migrate_parquet_to_iceberg.py` 把 Parquet 表迁到 Iceberg（`iceberg.lakehouse_iceberg`，**23 张表**），Parquet 上仍留 Hive 表。

**为什么要 Iceberg，不能只用 Parquet + Hive？**
- Hive 表是「目录 + 文件」的约定，没有事务：写一半失败会留下半份数据，多引擎并发读写没有隔离。
- Iceberg 用 manifest 管快照：ACID、模式演进、时间旅行、行级删除（v2）。「批层结果的唯一存储」才站得住。

**可能被追问**
- 「湖仓在你这里是真用了还是摆设？」→ 23 张表迁过去了，且访问路径确实是 Iceberg（`Provider == iceberg`、v2/snappy），不是只建了个库名。
- 「为什么不直接把 Spark 结果写回 MySQL？」→ 数据量和查询形态都不合适；Doris 才是服务层的读库。

## 第五讲 · 对账引擎：这个项目的核心

**解决什么问题**：把「两条链路结果一致」从一句声明，变成**每分钟、每个指标都可执行、可定位**的检查。

**怎么比**（`infrastructure/spark/jobs/reconcile_batch_realtime.py`、`reconcile_traffic_batch_realtime.py`）
1. 取对账区间：两侧 `MAX(window_start)` 取较小值，再减固定缓冲（`TAIL_GUARD_MINUTES = 3`）——**尾部还没封的窗口不参与**，否则会把「数据还没到齐」误判成「不一致」。
2. `FULL OUTER JOIN` on `window_start`，缺失一侧补 0 → 单边窗口、双侧窗口、零值窗口都能分类。
3. 逐列比对，写两类结果：明细表 `ads_reconcile_trade_1m`（一行一窗口，`is_match`）+ 汇总表 `ads_reconcile_summary`（区间、窗口数、不一致数、两侧合计、`is_pass`）。

**判据怎么定**（`04_reconcile.sql` / `08_traffic_reconcile.sql`）
- 交易域 **8 列**：`gmv / order_cnt / order_user_cnt / payment_cnt / payment_amount / payment_fail_cnt / refund_cnt / refund_amount`（其中 `order_user_cnt` 是去重计数，不是可加量）。
- 流量域 **7 列**：`uv / pv / view_cnt / cart_cnt / favorite_cnt / buy_cnt / click_cnt`。
- **比率列不进判据**：`click_rate / cart_rate / buy_rate / avg_order_amount / refund_rate` 是由计数派生的，分母为 0 时无定义，算进「是否通过」会制造假失败。
- **零值窗口算一致**：两侧都为 0 的窗口（交易域 6,088 个，15.08%）不是失败。

**实测结论（当前版本）**
| 域 | 对账区间 | 窗口 | 不一致 | 且 |
|---|---|---|---|---|
| 交易 | 2009-12-01 07:45 ~ 2011-12-09 12:48 | 40,358 | **0** | 两侧 GMV **17,067,427.47** 精确到分相等 |
| 流量 | 2017-11-25 00:00 ~ 2017-12-03 23:57 | 12,957 | **0** | 两侧 PV **10,096,157** 相等，单边 0/0 |

> 对账区间比全量略小，是因为尾部缓冲；差额 588.65 元可逐窗口对上——**能解释的差异**。

**可能被追问**
- 「0 不一致是不是因为判据太松？」→ 我们做过反向验证：故意让一条校验失败，脚本以非 0 退出；也构造过「分母为 0」的窗口，确认比率列不参与判定。
- 「为什么不加容差？」→ 金额按分存，两侧都是同一种定点数；加容差会把真实偏差藏起来。

## 第六讲 · 数据质量：25 条判据与「失败即阻断」

**解决什么问题**：数据错了要**当场拦住**，而不是等看板上出现怪数才发现。

**用了什么**：`infrastructure/quality/checks.conf`（声明式清单，25 条）+ `checks/*.sql`（每条一个 SQL 判据）+ `scripts/run-quality-checks.sh`（执行器，支持 `--with-lake`、`--proof-fail`）。

**机制**
1. **配置化**：每条校验有 id / 标题 / 域（交易/流量/湖仓/治理）/ 引擎（Doris 或 Spark）。
2. **失败即非 0 退出**：`run-quality-checks.sh` 有任何一条 FAIL 就 `exit 1`，批处理流水线在 `archive` 阶段就会停下，不继续写下游。
3. **覆盖四类**：主键唯一、非空、行数与层间一致、枚举合法、金额关系（`payment ≤ order`、`refund ≤ payment`）、漏斗单调、推进滞后。
4. **`--with-lake`** 才跑「DWD == ODS 逐表相等」这类需要读 Iceberg 的判据（25/25 全过）。
5. **前端同源**：`services/web/app.js` 的 `QUALITY_GROUPS` 与 `checks.conf` 逐字对齐，有测试 `tests/test_frontend_quality_manifest.py` 守着——**改了判据忘了改看板会红**。

**踩过的坑**
- 早期新鲜度判据写「滞后 ≤ 48h」，换成 2011/2017 年的真实数据后**恒假**；改成「批层 vs 流层的最新窗口差」——比较两个口径的推进，而不是和系统时钟比。
- 漏斗判据写死四级 `VIEW>CLICK>CART>BUY`，而天池没有 CLICK → 改成「`VIEW > CART > BUY`，CLICK 存在时必须严格居中」，用一条 SQL 兼容两种数据。

**可能被追问**
- 「25 条是不是凑数？」→ 每条都对应一个曾经真实发生的故障类型（如 DWD 与 ADS 行数不一致、金额不守恒、窗口重复）。
- 「怎么证明判据本身有效？」→ `--proof-fail` 构造失败用例，验证脚本真的会红。

## 第七讲 · 数据服务 API：只读、白名单、可解释

**解决什么问题**：把数仓里的数安全地给出去，且**不能让调用方拼 SQL 打到不该打的表**。

**用了什么**：FastAPI 0.141 + PyMySQL + Pydantic + 只读账号 `agent_ro`（`sql/doris/20_readonly_user.sql`）。

**关键机制**
1. **结构**：`services/api/app/main.py` 暴露 `/overview`、`/metrics/trade|traffic|category`、`/funnel`、`/orders`、`/batch/overview`、`/batch/reconcile`、`/meta/metrics`、`/meta/tables`、`/query`、`/health`；统一 `{data, meta}` 信封（`envelope.py`）。
2. **SQL 守卫**（`sqlguard.py`）：只允许 `SELECT`；用**结构性扫描**提取 FROM/JOIN 后的表名（处理括号、子查询、逗号连接），对照白名单；拒绝 `UNION` 注入、多语句、注释绕过。有一条**对抗测试** `tests/test_sql_guard_adversarial.py` 专攻逗号连接绕过（`FROM dim_user a, ecommerce.ods_user b` 曾被放行，已修）。
3. **窗口上限**：`window_limit` 有 `ge=0, le=20160`（14 天）约束，防止一次拉全表。
4. **只用只读账号**：即使 SQL 守卫被绕过，数据库层面也没有写权限。

**可能被追问**
- 「为什么不用 ORM？」→ 这里查询是「按窗口聚合 + LIMIT」，SQL 可控性比 ORM 更重要；而且守卫必须看到真实 SQL 文本。
- 「白名单怎么维护？」→ 表清单与 `sql/metadata/metrics.md` 的「可用表」一致，改表必须同时改两处（有测试守）。

## 第八讲 · Agent：为什么它「不会编数」

这是被问得最多的一层，讲清三件事就够：**它没有数据库凭据、它每一步都留痕、它在拿不到数据时会说拿不到**。

**用了什么**：LangGraph 1.1（状态机）+ DeepSeek（只做规划与总结）+ BM25 词法检索 + MCP 工具协议。

**六个节点**（`services/agent/app/graph.py`）
```
retrieve → plan → execute → validate → ┬→ summarize → END
                        ↑              └→ reflect ─┘（回到 plan，重试）
```
1. **retrieve**：把用户问题在「口径文档 + 表结构」语料里检索。语料来自 `sql/metadata/metrics.md`（指标定义与约定）、`kafka_topics.md`（事件格式）、`knowledge/layering.md`（分层），加上 Doris 里的实时表清单；检索是 **BM25（k1=1.2, b=0.75）+ 中文二元切分 + 同义词表**（`knowledge/synonyms.json`），刻意**不用向量检索**——口径这种精确词表，词法更稳、零额外依赖。
2. **plan**：LLM 根据检索到的口径生成「查询计划」：要取哪些列、怎么写 SQL、调用哪个工具（JSON）。
3. **execute**：经 **MCP** 或直连只读接口执行（`AGENT_MCP_TRANSPORT` 是**显式开关**，不自动降级——验收要能回答「这一次到底走了哪条路」）。
4. **validate**：检查返回是否为空、是否报错（如 `1105 Unknown column`）、列是否齐全。
5. **reflect**：失败时把**真实错误信息**喂回去重新规划（不是重试同一条 SQL）——这是「会自我纠错」的机制。
6. **summarize**：只依据**真实执行结果**写回答，并附「数据来源」与 SQL。

**三重上界**：`max_retries`（默认 2）、`max_tool_rounds`（工具轮次）、`total_timeout`（总超时）。超界就返回「暂时查不到」，**不猜数**。

**实测证据（答辩可讲）**
- 问「哪个类目的 GMV 最高？」→ 12.5 秒、3 次工具调用、给出真实表（文具纸品 176,760.25 元、41.68%）。
- 问「最近一周每天的 GMV 是多少？」→ **如实拒答**：日志显示先查 `ads_batch_trade_1d` 报「没有 `window_start` 列」，改查 1m 表 `row_count = 0`，于是回答「暂时查不到数据，不能给出数字」。这条比答对更能说明它不编数。

**安全边界**：Agent 进程**没有数据库账号密码**；它只能经 HTTP 调只读服务，服务侧还有 SQL 守卫；模型输出只作解释，**不参与取数**。

**可能被追问**
- 「为什么不用向量检索 / RAG？」→ 语料是结构化口径（指标名、列名、窗口规则），BM25 + 同义词足够；向量会把「退款率」和「退款金额」混在一起，反而降低精确度，还引入嵌入模型依赖。
- 「LLM 幻觉怎么办？」→ 三道：只允许它规划不许它算数、SQL 必须过守卫、汇总只能引用执行结果。
- 「MCP 是必须的吗？」→ 不是，它是**可切换的取数通道**；保留两种是为了验证「工具协议层」这件事，而不是为了炫技。

## 第九讲 · 前端看板：10 个页面怎么组织

**解决什么问题**：让人用眼睛就能判断「数可信吗」。

**用了什么**：Vue 3.5（全局构建版）+ ECharts 5.6 + 原生 JS，**零构建**（无 npm 打包，`index.html` + `app.js` + `styles.css` 三个文件，`vendor/` 由脚本下载）。

**为什么零构建**：部署就是 `scp` 三个文件，服务器上不需要 Node；对一个只在答辩时被访问的系统，构建链是纯负担。

**10 个页面**（`services/web/app.js` 的 `ROUTES`）
`overview` 总览 · `realtime` 实时链路 · `trade` 交易分析 · `traffic` 流量分析 · `category` 类目销售 · `orders` 订单明细 · `batch` 离线与对账 · `ask` 数据问答 · `quality` 数据质量 · `metrics` 指标口径（+ `monitor` 外链 Grafana）。

分五组：概览 / 实时分析 / 离线与可信 / AI / 治理——**这个分组本身就在讲方法论**（先看总览，再看两条链路，最后看「可不可信」）。

**几个真做过的细节**
- 实时链路的「滞后」会显示「历史数据集 · 按原始事件时间保留，滞后不适用」——因为数据是 2011/2017 年的，写「滞后 785 万分钟」是错的。
- 无 CLICK 数据时，漏斗自动降为三级并在标题里注明，不显示一个恒为 0 的点击率。
- 漏斗总量取**服务端全量聚合**（`window_limit=20160`），不拿最近 60 个窗口求和——否则「全量浏览 904 万」和「近 60 窗口 124 万」会互相矛盾。

**可能被追问**
- 「为什么不用 Element Plus / Vite？」→ 依赖越少越经得起「换台机器能不能跑」的检验；样式与组件都是一次性需求。
- 「前端怎么保证数不假？」→ 前端不算指标，只渲染接口返回；口径与判据都在后端与数据层。

## 第十讲 · 调度与运维：4 核 16 GB 怎么跑下 14 个容器

**解决什么问题**：整套栈放一台 4 核 16 GB 的机器上，还要能重复跑。

**用了什么**：Airflow 3.3（DAG `airflow/dags/offline_lakehouse_pipeline.py`）+ `scripts/batch-mode.sh`（错峰）+ Docker Compose（14 容器）+ systemd + nginx。

**机制**
1. **错峰**：批处理要先 `--pause-only` 停掉 Flink 的 4 个容器腾内存（可用内存 2 GB → 3.6 GB，批处理闸门是 3000 MB），跑完 `--restore-only` 拉回来。
2. **DAG 里也这么做**：`pause_realtime` 任务调 `batch-mode.sh --pause-only`，`restore_realtime` 用 `trigger_rule="all_done"` 保证**失败也会恢复**。
3. **监控**：Prometheus + Grafana，`health-check.sh` 检 8 个 Flink 作业、8 个 Routine Load、HTTP 路由。
4. **部署分层**：数据层用 Compose（Doris/Kafka/Flink/MinIO/MySQL/Hive/Spark/Prometheus/Grafana），服务层用 systemd（api/agent/mcp/airflow），入口 nginx（`/data/` 静态、`/data/api/`、`/data/agent/`）。

**踩过的坑**
- `flink-taskmanager` 没有 healthcheck，`docker inspect .State.Health` 恒为空 → 恢复脚本每次白等 120 秒；改成「有 healthcheck 用 health，没有就用 running」。
- 静态 IP 冲突：`doris-be` 固定 `172.28.0.11`，被后启动的 `flink-sql-gateway` 抢走 → 必须按顺序起。
- Kafka 下游 topic 没设 retention，每次重放翻倍，**把磁盘写满**（50.7 GB）；补 `retention.ms=6h / retention.bytes=2GB`。

**可能被追问**
- 「这算不算高可用？」→ 不算，单机部署，如实写进限制；我们主张的是「可复现」不是「高可用」。

## 第十一讲 · 怎么验收：脚本，而不是口头

**解决什么问题**：怎么让别人相信「你说的都对」——用**可执行的脚本**。

**体系**（`scripts/verify-sprint-0.sh` … `verify-sprint-12.sh`，共 12 个）
- 每个 sprint 一个验收脚本，全部可独立重跑，输出 `通过/失败/跳过` 三类计数。
- 关键脚本带**反向验证**：`verify-sprint-11.sh` 有 `--proof-fail`，构造失败用例证明它真的会红。
- 数据类断言不用 `|| 0` 兜底（早期 `verify-sprint-3.sh` 用 `${out:-0}` 把失败变成 0，形成假通过，已修）。

**当前实跑**：6 个脚本全绿；7–12 号分别是 49/71/59/84/61/42 项全过；质量校验 25/25；对账两侧 0 不一致。

**可能被追问**
- 「这些脚本是你写的，自己验自己？」→ 所以要有反向验证（构造必失败用例）+ 第三方判据（用纯算术 `2÷1=2` 判断谁是错的，而不是看代码）。

## 第十二讲 · 三分钟怎么讲完（口播骨架）

1. **问题**（30 秒）：同一个指标两条链路两个数，谁对？Lambda 和湖仓都只解决了一半。
2. **做了什么**（45 秒）：两个公开真实数据集 → MySQL + Kafka → 实时 Flink 按分钟算、离线 Spark 按四层算 → 一份口径 → 逐窗口对账 → 看板与问答 Agent。
3. **怎么证明**（45 秒）：交易域 40,358 个窗口、流量域 12,957 个窗口，不一致 0；两侧 GMV 精确到分相等；25 条质量校验全过；Iceberg 23 张表且 DWD 与 ODS 逐表相等。
4. **边界**（30 秒）：单机、非高可用、两域不重叠、流量域是抽样；0 不一致是跑出来的结果，不是前提。
5. **计划**（30 秒）：四阶段（选题与需求 → 实时链路收敛 → 离线建模与对账 → 服务层与论文）。
