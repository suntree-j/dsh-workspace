## 2. 逐段脚本

### 0:00–0:45 · 项目背景与问题（口播，约 150 字）

**操作**：停在 PPT 封面/问题页，不点任何东西。

**说什么**（语速放慢，这是全场唯一一次机会把问题说清）：

> "电商数据同时是两种形态：事件流要快，经营分析要准。传统做法建两套系统，代价是同一指标两份实现。
> 我用一句话说清我要回答的问题——**同一条业务事实，走实时链路和走离线链路，算出来的指标是不是同一个数？**
> 如果实时说 100 万、离线说 95 万，那建在它上面的问答 Agent 引用哪一个都是错的。
> 所以我的目标不是'离线也能算出 GMV'，而是**证明两条链路算的是同一个数**——这是一个可以被证伪的断言：只要有一个窗口对不上，结论就不成立。"

**一句话结论**：**我把"批流一体"从一句设计原则，变成了一个可以被证伪的断言。**

### 0:45–2:00 · 实时链路：MySQL → Kafka → Flink → Doris（75 s）

**操作（按顺序，每步 10~15 s）**

| # | 操作 | 看什么 |
| --- | --- | --- |
| 1 | 浏览器：`http://36.151.150.140/data/` → 点「总览」 | 顶部交易 KPI 的 **GMV**、窗口新鲜度、类目 Top5 |
| 2 | 切到「交易分析」 | GMV / 客单价 / 支付成功率 / 退款率四条趋势线 |
| 3 | 切到「流量分析」 | UV / PV 与行为漏斗（VIEW > CLICK > CART > BUY） |
| 4 | 终端：`curl -s -X POST http://127.0.0.1/data/api/query -H 'Content-Type: application/json' -d '{"sql":"SELECT COUNT(*) AS w, SUM(gmv) AS gmv FROM ecommerce.ads_realtime_trade_1m","limit":5}'` | `gmv = 51890375.77`；同一条还可看响应 `source.tables` 与 `source.metric_definitions` |
| 5 | 口头报链路状态（不必点） | 8 个 Flink sink 作业各 1 个实例；8 个 Doris Routine Load 全部 RUNNING、`errorRows=0`；`health-check.sh` 11/11 |

**说什么**：

> "实时链路是 Kafka → Flink → Doris。两个设计点值得说：
> 第一，Flink 用**事件时间**语义、1 分钟滚动窗口，**不用处理时间**——因为它要保证乱序和重放得到同样的结果，这也是后面能逐窗口对账的前提。
> 第二，Doris 侧用 UNIQUE KEY + merge-on-write 承接 Flink 写出，同一窗口的多次中间态会收敛为最新值，所以批处理期间暂停 Flink、恢复后从已提交位点续跑**不会造成重复计数**。
> 现在这个 GMV：**51,890,375.77**，与事实源 MySQL 是**精确到分相等**的。"

**一句话结论**：**秒级指标已经落地，并且在总账上与事实源 MySQL 精确到分相等。**

> ⚠️ 别说"实时链路数据完全正确"。流量域**已知**有 1 个窗口的比率列缺陷（下一段主动说）。

### 2:00–3:00 · 批流一致性：窗口级比较（60 s ★ 本场最重要的一段）

**操作**

| # | 操作 | 看什么 |
| --- | --- | --- |
| 1 | 页面：点「离线与对账」 | 页面上「实时 / 离线逐窗口对账结论」区块：**对账窗口数 11458、不一致 0、两侧 GMV 相等** |
| 2 | 终端（可选，一条命令取证）：`bash scripts/spark-sql.sh -e 'SELECT * FROM lakehouse.ads_reconcile_summary;'` | 汇总行：窗口数、不一致数、两侧合计。<br>⚠️ 这条会起一个一次性 Spark 容器（驱动约 1 GB）。<br>★ **默认走零内存替代；只有在 `free -m` 显示可用 > 3500 MB 时才现场跑 Spark** |
| 3 | 终端（零内存，**默认方案**）：`curl -s http://127.0.0.1/data/api/batch/reconcile` | 对账接口的 JSON（性能基线：该接口中位数 21.4 ms） |

**说什么**（★ 这一段的三句话必须说出来）：

> "**第一，我比的不是总数，是逐分钟窗口。**
> 交易域 11458 个分钟窗口，逐窗口比对，不一致 0；两侧 GMV 精确到分相等，都是 51,890,375.77。
> 流量域 19643 个窗口，7 个判据列逐窗口一致，不一致 0，而且**单边窗口单独统计是 0 比 0**——就是"只有实时有"和"只有离线有"各 0 个。这一条比"差异为 0"更重要：否则"只比两边都有的窗口"会把"某一侧缺了一批窗口"这件事掩盖掉。
>
> **第二，这 11458 个窗口里，有 5504 个是两侧 GMV 都为 0 的窗口**，占 48.03%。
> 它们属于**平凡一致**，我不把它们当独立证据——真正承载判别力的是 **5954 个有业务量的窗口**（占 51.97%）。
> 另外我要说清这句话的边界：判据是"缺失侧补 0 后数值相等"，所以 `mismatched_windows = 0` **不严格等价于**"两侧窗口集合相同"；
> 而且交易域**没有**"单边窗口 = 0"这条断言（流量域有），只有"实时侧窗口数 ≥ 离线侧 × 90%"的覆盖率守卫。这些边界都写进了报告。
>
> **第三，我主动交代一个未归零的发现：流量域有 1 个窗口的比率列与它自己的计数矛盾。**
> 窗口 `2026-03-21 19:23:00`：实时侧 `view_cnt=2 / click_cnt=1`，`click_rate` 落库是 **0.0000**，按口径公式 1/2 应为 **0.5000**；离线侧同一个窗口算出来是 **0.5000**，是对的。
> 我用纯算术 `1/2 = 0.5` 这个**第三方判据**定了责——差异不在"两侧算法不同"，而在实时侧那一行自相矛盾。
> 处置是三个动作：**判据改严**（从"两侧比率相等"改成"每一侧的比率必须等于用它自己的计数重算"）、**矛盾窗口数落盘为一等结论**（`realtime_rate_anomaly_windows = 1`）、**写进已知限制**。
> 它**不进入 `is_pass`、不阻断作业退出码**，所以"0 mismatch"和"实时侧存在一个已知缺陷"这两句话是**同时成立**的，必须一起说。
> **我没有加容差，也没有把证据删掉。**"

**一句话结论**：**在两侧数据范围求交、尾部留 3 分钟安全边界的对账区间内，两条独立链路在 1 分钟窗口粒度上给出同一组指标值——交易域 11458 个窗口、流量域 19643 个窗口，不一致 0；其中 5954 个窗口有业务量、承载判别力；另有 1 个实时侧比率列的已知缺陷被如实留证。**

> ★ **本页的内存纪律**：**默认走零内存替代**——留底原文行（第 1、2 项）+ 页面「离线与对账」+（若需要一条命令）`curl -s http://127.0.0.1/data/api/batch/reconcile`。
> **只有在 `free -m` 显示可用 > 3500 MB 时，才现场跑 Spark。** 演示现场最怕的是**为了秀一条命令把实时链路挤掉**（内存闸门 3000 MB 是硬规范，不是建议值）。

**说什么**：

> "离线链路是 Spark 从 MySQL 和 Kafka 抽取，写 Parquet，再迁到 **Iceberg**，表目录走 **Hive Metastore**，存储落在 **MinIO**（S3A 协议）。
> 为什么上 Iceberg：Parquet 外部表缺三样——没有 ACID、没有 schema 演进、没有时间旅行。
> 迁移清单从 **18 张表扩到 23 张表**，校验跑过两次，**两个数字的范围不一样**：
> 18 张表那次是 **60/60**；流量域建成之后扩到 23 张表复跑是 **70/70**。
> 它们**不是同一判据在同一次运行下的两个结果**，我在报告里是按各自范围标注的，不合并也不取平均。
> **我要说清验证到什么程度**：逐表核对的是**三个维度**——表目录身份（`DESCRIBE EXTENDED` 的 `Provider == iceberg`）、行数（`COUNT(*)`）、以及 6 个金额列的**整表合计**（`gmv` / `amount` / `payment_amount` / `refund_amount` / `avg_order_amount` / `total_amount`，DECIMAL 精确比较、无容差）。
> 这三个维度上**未发现差异**。它**不能**证明逐行一致、不能证明字符串或时间字段内容一致、不能证明分区布局一致、也**没有**做过回滚演练——这些未验证维度我列了 11 条在报告里。
> 另外有一条我要主动说：`70/70` 只有一句汇总额，**没有原始逐项细目**；`60/60` 的构成是可核对的：18 表身份 + 18 行数 + 23 金额列 + 1 库表数。"

**一句话结论**：**Parquet → Iceberg 迁移覆盖 23 张表；在表身份、行数、6 个金额列整表合计三个维度上未发现差异（两次运行的校验计数分别为 60/60 与 70/70，范围不同），其余维度未验证。**

### 4:00–5:30 · Agent：问题 → Retrieval → Tool → SQL → Guard → 校验 → Reflection → 回答（90 s）

**操作**

| # | 操作 | 看什么 |
| --- | --- | --- |
| 1 | 页面：点「数据问答」 | 输入框 + 回答卡片 |
| 2 | 输入 **主问**：`最近一周卖了多少钱？` | 回答正文给出 **GMV** 与**支付金额**两个数，并解释口径差异；<br>响应里 `tables` / `executed_sql` / `docs` 三项齐全 |
| 3 | 展开回答下方"来源"区 | `docs` 带**文件名与行号**（如 `sql/metadata/metrics.md:33`）；`executed_sql` 是**守卫改写后实际执行的那一条**（带 LIMIT） |
| 4 | 输入 **备用问**：`复购率怎么算？口径文档里有定义吗？` | 期望：**如实回答"口径文档里没有复购率的定义"**，并给出核查过程——这是"不胡说"最直接的证据 |
| 5 | 终端（可选）：`curl -s http://127.0.0.1:8100/graph` | 图结构：**6 个节点、8 条边**、三重上界（重试额度 / 工具轮次 / 总超时） |
| 6 | 终端（可选）：`curl -s http://127.0.0.1:8100/tools` | Agent 能力面：**4 个取数/元数据工具**（可枚举、可审查） |

**说什么**（按图的顺序讲，一条 8 秒）：

> "Agent 走的是图，不是单轮循环：**retrieve → plan → execute → validate →（有阻塞性问题就）reflect → plan → …… → summarize**。
> 四个必须说的设计：
> 一，**检索是每问必跑的确定性前置步骤**，不是"让模型自己决定要不要查"——因为不稳定的口径引用正是要消除的问题。
> 二，**守卫在服务端**，不在 Agent 里；放在 Agent 里等于让被约束者自己当裁判。
> 三，**反思之后回到 plan，不是回到 execute**——错误信息通常意味着计划本身错了，回到 execute 只是把同一条错 SQL 重放一遍，那是重试不是重新规划。
> 四，**回答必须能核对**：`tables` 由服务端从 SQL 里提取（不靠调用方自报）、`executed_sql` 是实际执行的那一条、`docs` 带文件与行号，能当场翻到那一行。
> 关于反思重试我说准一点：**能力存在**（额度默认 2），**路径被真实触发过**——线上验收脚本断言的是 `retries ≥ 1` 且执行轨迹里出现 `reflect` 与 `plan`；`= 2` 这个具体值只出现在 mock 单元测试里。**线上平均重试次数我没有统计，属未采集。**"

**一句话结论**：**Agent 的可信性来自架构而不是提示词：进程里没有数据库凭据，检索每问必跑，守卫在服务端，回答附可逐条核对的 `tables` / `executed_sql` / `docs`。**

> "MCP 这一段的设计核心是：**它不是一条新的取数通道，而是同一份只读能力的另一种暴露方式。**

## 3. 如果演示时某一步挂了怎么办

### 3.1 先判据，再处置：是**环境问题**还是**功能问题**？

| 编号 | 现象 | 判据（决定性的一条） | 归类 | 处置 |
| --- | --- | --- | --- | --- |
| E1 | 页面/接口 502 或转圈 | 看响应头有没有 `Server: nginx/1.24.0`。**没有 → 不是 nginx 发的** → 请求在到达服务器之前被中间设备改写 | **环境**（典型原因：挂了 VPN/代理） | 关掉 VPN/代理重试一次；仍不行 → 走降级预案 A |
| E2 | Agent 报"未配置 LLM"或超时 | `curl -s http://127.0.0.1:8100/health` 看 `llm.configured`；若为 true 而超时 → 外部 LLM 往返（占端到端 99.9%） | **环境**（外部服务/网络） | 直接换备用问句；或切到"讲留底回答"（预案 A） |
| E3 | 页面 200，但指标显示 `—` 或 0 | 用只读接口对照一行：`SELECT COUNT(*) FROM ecommerce.dim_product`。**若维表为 0 行**，任何 JOIN 维表的查询会**静默返回 0 行**（HTTP 200 + `row_count=0`） | **数据问题**（不是接口问题） | 直说"这张维表的数据装载有问题，类目维度这类问题现在答不出来"——**如实说比圆场得分** |
| E4 | 排序/过滤后页面为空 | 面板默认时间范围 `now-90d`，而本机数据是一次性生成的历史数据 | **口径/默认值问题** | 把时间范围拉到全量 |
| E5 | 命令被内存闸门拒绝启动 | 输出里出现"可用内存 < 3000 MB，拒绝启动"（闸门阈值 3000 MB；曾以可用 2258 MB 主动拒绝过一次批处理） | **设计行为，不是故障** | 当场说明"闸门按设计工作"；改用零内存的留底证据 |

| E7 | Airflow / Grafana 登录不进 | 前者用官方标注"仅供开发测试"的 SimpleAuthManager；后者数据源与面板全部 provisioning、匿名只读 | **配置/认证** | 跳过登录，只讲结论与留底截图 |
