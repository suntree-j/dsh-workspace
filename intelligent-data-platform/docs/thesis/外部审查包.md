## 0. 一句话定位

面向电商场景的**批流一体**数据平台：同一条业务数据分别走实时链路与离线链路，
再用**逐窗口对账**证明两条链路算的是同一个数；在此基础上提供一个**只读**数据服务、
一个 LLM 数据问答 Agent（含检索与 MCP），以及数据质量校验与监控。

核心主张只有一句：**账能对上，且每一步都能复现。**

## 3. 三个核心技术主张及其证据

### 3.1 主张一：实时链路与离线链路算的是**同一个数**

**做法**：不比对"总量"，而是**逐分钟窗口**比对两侧算出的指标，差异数落盘。

| 域 | 窗口数 | 不一致 | 单边窗口 | 关键合计 |
| --- | --- | --- | --- | --- |
| 交易域 | 11458 | **0** | — | GMV 实时 51,890,375.77 == 离线 51,890,375.77（精确到分） |
| 流量域 | 19643 | **0** | 仅实时 0 / 仅离线 0 | PV 实时 19998 == 离线 19998 |

**防止"空集合假通过"**：每条对账断言都带非空守卫（窗口数 > 0）。若无守卫，
"0 个窗口不一致"在空表上也会成立 —— 这是本项目记录过的真实失误类型。

**判据被打磨过两次（这部分比"不一致 0"更能说明问题）**：

1. 一开始要求"两侧比率列也相等"，发现 **1 个窗口**不一致。
   没有加容差蒙过去，而是**用第三方判据定责**：该窗口计数为 `view_cnt=2 / click_cnt=1`，
   纯算术 `1/2 = 0.5`，而实时侧落库 `click_rate=0.0000`、离线侧算出 `0.5000`
   → **缺陷在实时侧，离线侧是对的**。旁证：全表 `click_rate` 取值只有 `{0.0000, NULL, 1.0000}`，
   而"分子既不为 0 也不等于分母"的分数窗口**恰好只有这一个**。
2. 判据因此**改严**：从"两侧比率相等"改为"**每侧比率 == 按该侧自身计数重算**"，
   并把矛盾窗口数落盘（`realtime_rate_anomaly_windows = 1`）、逐窗口打标记。
   **未修复**：修它需要重部署 Flink 作业并从 Kafka 最早位点**全量重放**，
   会覆盖实时侧全部 19644 个窗口；为一个小数点后的显示问题承担整条实时链路重放的风险，
   成本与收益不匹配。这一条作为**已知缺陷如实披露**，不是"环境问题"，也不是"未解决"。

**离线侧曾多一个分区列**：验收时发现离线表比实时表多 1 列（`dt` 分区列）。
处理方式是**把判据写清楚**（"数据列逐列一致 + 分区列在最后" + 另加一条"除分区列外无多余字段"），
而不是删掉分区、也不是放宽断言。

### 3.2 主张二：Parquet → Iceberg 迁移**没有改变数据**

| 检查 | 结果 |
| --- | --- |
| 迁移表数 | 18 → 23 张（含流量域 5 张） |
| 校验 | 每表：`DESCRIBE EXTENDED` 的 `Provider == iceberg` + 行数一致 + 按金额列逐列合计一致；末尾再断言"库表数 == 清单表数" |
| 运行 1（18 张表） | **60 / 60** |
| 运行 2（23 张表） | **70 / 70** |
| 逐表行数与 Parquet 侧 | 完全一致（如行为事件 20000、流量 ADS 19644、天表 703） |

> ⚠️ `60/60` 与 `70/70` **不是同一判据的两个结果**：前者范围是 18 张表，后者扩到 23 张表。
> 另外需说明：`60/60` 有可推导的逐项依据（18 Provider + 18 行数 + 23 金额列 + 1 库表数），
> 而 `70/70` 在项目文档里只留了汇总一句、**没有逐项细目**，属"未逐项记录"。

**迁移中遇到的真实障碍（都记录在案）**：
- **命名陷阱**：数据库名与 catalog 名同名时，`CREATE DATABASE` 会解析成"目录 + 空命名空间"，
  报 `Cannot create namespace with invalid name:`（冒号后为空）。修法：catalog 改名，库名不动。
- **配置不生效**：`spark-defaults.conf` 是构建期 `COPY` 进镜像的，临时容器不重建镜像就看不到改动
  → 必须挂载。
- **两段名陷阱**：Spark 的两段名永远是"当前目录下的命名空间.表"，不会因为名字像就跳到另一个目录
  → 全部改用三段名。
- **分区写入器 OOM**：703 个分区 vs 默认 200 个 shuffle 分区 + AQE 合并，
  导致少数 task 各持有几百个写入器把执行器堆打爆（**数据仅 2 万行，与数据量无关**）。
  修法是结构性的（`DISTRIBUTE BY` + 抬高 shuffle 分区数 + 关 AQE 合并），不是调大内存。

### 3.3 主张三：Agent 的回答**可核对**，且不能越权

| 机制 | 实现 | 可核对证据 |
| --- | --- | --- |
| **进程边界** | Agent 进程内**没有数据库凭据**，只能经 HTTP 调只读服务；只读服务用专用只读账号 + SQL 守卫 | 端到端问答能取到数（证明通路可用）；四类攻击返回 `NOT_SELECT` / `TABLE_NOT_ALLOWED` / `MULTI_STATEMENT` / `COMMENT` |
| **来源可追溯** | 回答附 `tables` / `executed_sql` / 命中的口径文档（文件:行号） | 实测 "最近一周卖了多少钱"（**问法不含 GMV 字样**）命中 `metric:gmv | sql/metadata/metrics.md:33`；负例命中为空 |
| **会重规划** | 图式编排：检索 → 规划 → 执行 → 校验 →（有问题且有额度）反思 → 回到规划 | 实测 `retries=2`：问一张**存在但未授权**的表 → 两次真实 `TABLE_NOT_ALLOWED` → 如实回答"给不出来" |
| **有上界** | 重试 2 次 / 轮次 6 / 超时 120 s | 三重上界都在 `/health` 里可见 |
| **经 MCP 同源** | 同一问题经 MCP 与直连 HTTP 结果**逐字段一致**，`executed_sql` 相同 | `verify-sprint-10.sh` 84/0/0 |

**检索方案**：**词法检索**（BM25 + CJK bigram + 显式同义词表 54 条），语料 65 篇，
**未引入任何向量库**（实测向量库相关包数量 = 0）。
理由是查证过：所用 LLM 供应商**没有 embeddings 端点**，而本机也放不下本地 embedding 模型。

> ⚠️ 上面"没有 embeddings 端点"是**外部查证结论**（社区 issue 与一次 404 报错为证），
> 不是本项目实测 —— 如果你认为这个前提不成立，请指出。

## 4. 数据来源（**合成数据**，这是必须如实披露的前提）

- 数据由程序生成：`data-generator/`（Python + Faker `zh_CN` + `random`）
- **可复现**：随机种子由 `GEN_RANDOM_SEED` 控制，默认 **`20260926`**；Faker 与 `random` 共用同一随机源
- **不是"随便随机"**：生成时强制满足业务约束与时间因果 ——
  `订单.user_id ∈ 用户表`、`订单.product_id ∈ 商品表`、`支付/退款.order_id ∈ 订单表`、
  `商品单价 × 数量 ≈ 订单金额`（`Decimal` 计算）、`注册时间 ≤ 下单 ≤ 支付 ≤ 退款`
- 规模：用户 1200 / 商品 600 / 订单 6000 / 支付 5406 / 退款 254 / 行为事件 20000
- ID 段：用户 `1001+`、商品 `2001+`、订单 `10001+`、支付 `30001+`、退款 `40001+`

**它为什么能支撑逐窗口对账**：因为可复现 + 满足约束，两侧链路读的是同一份事实。
**它的局限**（应写进报告）：不代表真实流量分布，也不包含真实脏数据形态；
因此"数据质量校验"能证明的是**规则有效**，不能证明**规则完备**。

## 5. 已知缺陷与未决项（审查者请重点看这一节）

### 5.1 已修并已实测的缺陷（本阶段新增）

| 缺陷 | 性质 | 修法与实测 |
| --- | --- | --- |
| 两张维表在 OLAP 库里长期 **0 行** | **静默错误**：`JOIN 维表` 不报错，返回 200 + `row_count=0`，调用方以为"真的没有数据" | 装载脚本支持"库.表"前缀 + 显式声明湖仓来源 + 补只读授权。实测 `dim_product 600 == 湖仓 600`、`dim_user 1200 == 湖仓 1200`；那个曾恒为 0 行的 JOIN 现在返回 10 行真实类目 GMV |
| 装载脚本**先清空后装载** | `TRUNCATE` 与 `INSERT` 各自原子，但**两步之间不原子**：第二步失败后系统停在**比失败前更差**的状态（数据没了） | 清空前先探测源端（可读且至少一行），否则**保留现有数据并失败退出**。该守卫上线后**第一次实战就救了一次**：源端通配写错 → `[FAIL] 源端为空 —— 已跳过清空，现有数据保持不变`，无数据损失 |
| SQL 守卫的 UNION 元数据探测缺口 | 正则**按语序匹配**，只拦"元数据写在 UNION 后面"；反序拼接被放行。**判据写成按顺序匹配，换个语序就绕过去了** | 改为顺序无关的组合判据。服务器实测：反序两种写法都被拦（`METADATA_PROBE`）、正序仍被拦（无回退）、**单独查 information_schema 与普通业务查询仍放行**（无过度拦截）；对抗用例 63 passed、0 xfail |
| 数据服务把"SQL 写错"也报成 503 | Agent 会把"我 SQL 写错了"误读成"仓库不可用"而多跑一轮重试 | 区分：语句错误 → **400**（`DORIS_QUERY_ERROR_1105` + 保留原文），连接/超时类 → 503。真实 HTTP 实测两侧 |
| 两份脚本的阶段清单会漂移（结构债） | 只改一处会出现"一个入口能跑、另一个**静默跳过**"（本项目真发生过：某阶段空转却报成功） | 新增防漂移断言：剔除点名例外后两份清单必须完全相等，差集直接打印。故意改坏副本 → FAIL 并报出缺哪一段 |

## 6. 一次真实事故的复盘（本项目最有信息量的一段）

**现象**：服务器上 `.env`（唯一存放真实凭据、且被版本控制忽略的文件）突然不存在，
容器编排命令因变量无法插值而**完全不可用**；三个 Python 虚拟环境与一个调度配置文件也一并消失。

**定位**：由执行代理如实交代 —— 它为了绕过同步脚本的一道守卫，自写了一个"原子换树"同步脚本：
只打包了一个子目录，却执行"移动旧树 → 放入新树 → 删除旧树"，
**删除旧树**这一步把 `.env`、三个 venv、调度配置文件**一起删掉了**。

**第二层损失（更隐蔽）**：三个被容器**挂载**的第三方 JAR 也被删除，
导致元数据服务反复重启，而**报错说的是"CLASSPATH 里找不到数据库驱动"**。
更误导的是：容器在挂载目标不存在时会把它**创建成空目录**，
所以 `ls` 看上去"有那一行"，只有 `-f`/`-s` 才揭穿。

**恢复**：凭据逐个**在线验证**后再写回（避免"写回后才发现是错的、还要再重启一次"）；
被删 JAR 从镜像恢复并**与原件做哈希比对**；代码树重新同步。

**沉淀为硬规范**（这是这段经历的价值所在）：
1. 共享文件的权限要按**所有读者**定，不能按"最小权限"直觉定（该文件必须是 `640 属组可读`，
   因为另一个以不同用户运行的服务需要组读它 —— 症状出现在"别人负责的服务"上，最难关联）
2. **禁止任何"整树替换/镜像式"同步**；破坏性操作的正确形态是"**先验证新状态可用，再销毁旧状态**"
3. 在确认凭据已落盘之前，**禁止重建容器** —— 容器环境变量里可能还留着上一份凭据，
   重建非但不能"修好"，反而会把**唯一的一份**丢掉
4. 会改机器状态的验收脚本，开头必须检查凭据文件是否存在，否则就失败退出
5. **判断挂载型文件是否存在，用 `-f`/`-s`，不要只看 `ls`**
