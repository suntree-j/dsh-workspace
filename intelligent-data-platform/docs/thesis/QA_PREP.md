## 一、数据与可信性

### Q1. 数据是真实的还是生成的？为什么用合成数据？

- **直说是合成的**。生成器在 `data-generator/`，逐条业务约束在生成期强制执行。
- **为什么**：本课题要研究的是"两条链路算的是不是同一个数"，这需要**事实源完全可控**——每一笔订单、支付、退款在 MySQL 与 Kafka 里的对应关系必须能逐条核对。真实数据拿不到这种确定性。
- **代价如实说**：合成数据不代表真实业务分布，这是本设计最大的局限。
- **依据**：`docs/data-source-design.md` 第 1、7 节；`data-generator/src/dataset.py` 模块头注释。

### Q2. 合成数据凭什么说结果可信？

三点：

1. **可复现**：`GEN_RANDOM_SEED` 默认 `20260926`，同一种子生成完全相同的数据集（`data-generator/src/config.py` 第 140 行）。
2. **业务约束在生成期强制**：外键关系（`orders.user_id ∈ user`、`payment.order_id ∈ orders` 等）、金额关系（`price × quantity ≈ amount`）、时间因果（`register_time ≤ create_time ≤ pay_time ≤ refund_time`）、漏斗单调（`VIEW > CLICK > CART > BUY`），且事件是基于**真实写进 MySQL 的那批数据**生成的（通过 `state/dataset_snapshot.json` 传递），不允许产生与业务库不一致的事件。
3. **正因为可复现 + 满足约束，才支撑得起逐窗口对账**：如果数据每次都不一样，或者事件与业务行对不上，"11458 个窗口不一致 0"这个结论就无法复现。
- **依据**：`data-generator/src/dataset.py`；`docs/data-source-design.md` 第 4.3、6 节；`AGENTS.md` 第 8.2 节。

### Q3. 有哪些约束是生成时强制保证的？

| 约束 | 位置 |
| --- | --- |
| 订单 `user_id` 必须来自 `user` | `dataset.py` `generate_orders()` |
| 订单 `product_id` 必须来自 `product` | 同上 |
| `payment.order_id` 必须来自 `orders` | `generate_payments()`（只对已支付订单生成支付记录） |
| `refund.order_id` 必须来自 `orders` | `generate_refunds()` |
| `product.price × quantity ≈ order.amount` | `generate_orders()`（含按概率打折） |
| `register_time ≤ order.create_time ≤ order.pay_time ≤ refund.refund_time` | 各生成函数 + `generate_orders()` 的时间越界处理 |
| 退款只对支付成功的订单、`refund_amount ≤ order.amount`、`refund_time ≥ payment_time` | `generate_refunds()` |
| 漏斗逐级收窄 | `GenerateConfig.behavior_funnel` 权重（VIEW 1.00 / CLICK 0.55 / CART 0.20 / FAVORITE 0.10 / BUY 0.06） |
| 金额用 `Decimal` 且四舍五入到 2 位 | `_q2()`；`AGENTS.md` 第 4.2 节禁止用 float 做金额累加 |

- **一个细节**：支付记录是按"已支付订单"枚举生成的，`payment_id` 连续，而"支付失败"是其中 2% 的记录。因此 `payment` 行数略多于真实成功笔数（5406 行里 5287 成功、119 失败）。
- **依据**：`data-generator/src/dataset.py`；`docs/sprint/SPRINT_3.md` 第 7.2 节。

### Q5. 生成数据的时间跨度是多少？为什么重要？

- 订单时间范围 `2024-10-25 ~ 2026-09-26`（约 700 天有数据）；实时 ADS 时间跨度 `2024-10-25 08:16:00 ~ 2026-09-26 11:37:00`（分钟级稀疏）。
- 行为事件时间范围 `2024-10-02 21:53:33 → 2026-09-26 13:16:13`；实时侧流量 19644 个分钟窗口、离线侧 19644 个窗口，**时间范围几乎完全重合**。
- **为什么重要**：只有两侧时间范围重合，才能做**全窗口对账**，不需要打折覆盖区间。这是"19643 个窗口逐窗口比对"能成立的前提。
- **依据**：`docs/sprint/SPRINT_3.md` 第 2 节；`docs/sprint/SPRINT_5.md` 第 2.3 节。

### Q6. 你怎么保证不是"跑通了就算"？

三个机制：

1. **验收脚本的退出码是有意义的**：分步 `[OK]/[FAIL]` + 统计 + 失败 `exit 1`；健康检查类脚本要求"正确返回退出码，禁止无论结果都返回 0"。
2. **测试必须真实执行**：禁止只检查文件是否存在；冒烟测试必须校验数据内容（字段、行数、关系），不只是连通性。
3. **失败路径可执行证明**：`run-quality-checks.sh --proof-fail` 故意改坏期望值，断言必须退出码 1，然后恢复再跑一次证明失败来自断言。
- 本项目反复出现的反面案例也是证据：**"成功信号不可信"**——命令返回成功、构建报成功、自检全绿，都不能替代"回到目标状态去验证"。
- **依据**：`AGENTS.md` 第 4.3、8 章、第 15.8 节；`docs/sprint/SPRINT_11.md` 第 1.2 节。

## 二、核心机制（对账与口径）

### Q8. 你的对账为什么能证明实时和离线一致？

因为它不是一个"看起来差不多"的比较，而是**逐窗口的可加/计数指标比对**：

1. **前提一：事件与业务行一一对应**。实时指标算在 Kafka 事件上，离线指标算在 MySQL 业务行上；映射关系逐条列明（`ORDER_CREATED` ↔ `orders` 1 行且 `event_time = create_time`；`PAYMENT_SUCCESS` ↔ `payment` 行且 `pay_time IS NOT NULL`；`REFUND_CREATED` ↔ `refund` 1 行）。
2. **前提二：粒度相同**。离线 ADS 特意输出 1 分钟粒度（`ads_batch_trade_1m`），与实时表**同粒度、同字段名、同类型、同顺序**，否则无法逐条比。
3. **前提三：口径同一份**。两侧都按 `sql/metadata/metrics.md` 的定义计算，可加指标无事件补 0、比率指标分母为 0 留 NULL。
4. **比对方式**：逐窗口比对，差异逐条列出；区间尾部留 3 分钟安全边界；**单边窗口单独统计**（实测两个域都是 0/0）。
5. **结果**：交易域 11458 个窗口不一致 0，两侧 GMV 精确到分相等；流量域 19643 个窗口不一致 0。
- **它不能证明什么**（主动说）：它证明的是**这两条链路在已发生的数据上给出了同一个数**，不能证明任何一个数在业务上是"正确"的——那个由与 MySQL 事实源的独立核对来覆盖（Sprint 1/3 的验收中都做了）。
- **依据**：`docs/sprint/SPRINT_3.md` 第 3.2、3.3、7 节；`docs/sprint/SPRINT_5.md` 第 9.2 节。

### Q9. 口径不同的指标怎么处理？

按"可加 / 去重 / 派生"三类分别处理（`sql/metadata/metrics.md` 第 3.1 节）：

| 类别 | 字段 | 可以做什么 | **不可以**做什么 |
| --- | --- | --- | --- |
| 可加 | `pv` / `view_cnt` / `click_cnt` / `cart_cnt` / `favorite_cnt` / `buy_cnt` | 逐窗口比对；跨窗口/跨天直接 SUM 上卷 | — |
| 去重 | `uv` | 逐窗口比对；要天粒度就回到明细重新去重 | **跨窗口相加**（`SUM(uv)` 不是任何有意义的量） |
| 派生 | `click_rate` / `cart_rate` / `buy_rate` | 用"合计后的分子 / 合计后的分母"重算 | 对逐窗口比率求平均 |

- **两条实测证据**：`SUM(19644 个窗口的 uv) = 19999`（逐窗口去重的基数）vs 全部 20000 个事件的去重用户数 = 1200（人的基数），**相差约 16 倍但都正确**；若把"天 UV"写成 `SUM(分钟 uv)`，会系统性偏大且看起来仍然合理（19999 < 20000 的 PV，不会有人怀疑）。
- **离线侧的分工是固定的**：`ads_traffic_1m.uv` 跟随实时侧 Flink 语义（`COUNT(DISTINCT)`，近似去重，因为是参与对账的列）；`ads_traffic_1d.uv` 回到明细精确去重（业务事实列，被相等断言使用）；可加量 1d 对 1m 直接 SUM；比率用 1d 的分子分母重算。
- **依据**：`sql/metadata/metrics.md` 第 3.1 节；`docs/sprint/SPRINT_5.md` 第 9.1 节。

### Q10. 为什么 `ads_traffic_1m.uv` 用近似去重？不换成精确的吗？

- **是刻意的，不是遗漏**。它是参与批流对账的列，必须与实时侧 Flink 的同类实现保持**同一语义**，否则会因"算法不同"而对不上，且失败原因极难定位。
- 与之相对，**用来做相等断言的去重**（DWS 的 `uv`、作业自检里的天数）一律用精确实现（`SIZE(COLLECT_SET(x))`）。
- 这个取舍写进了 SQL 注释与口径文档。
- **依据**：`sql/metadata/metrics.md` 第 3.1 节；`docs/sprint/SPRINT_3.md` 第 8.3 节。

### Q11. `COUNT(DISTINCT)` 为什么不能拿来做相等断言？

- Spark SQL 的 `COUNT(DISTINCT x)` 默认走 **HyperLogLog 近似实现**（误差上限约 5%）。
- 实测现象：自检报 `1d order_user_cnt == DWD 全局去重 5883（期望 1195）`、`类目 1d 条数 == 1m 条数 2834（期望 5998）`，**看起来像"离线少算了一半数据"，实际数据完全正确**——是断言用的函数不准。
- 排查花了两轮，因为"2834 对 5998"这种数字太像真的丢数据了。
- **修法**：做相等断言的地方一律改用 `size(collect_set(x))`；指标列本身仍保留 `COUNT(DISTINCT)`（理由见 Q10）。
- **依据**：`docs/sprint/SPRINT_3.md` 第 8.3 节。

### Q12. 除了这条，还有哪些"断言写错"的案例？

至少四处，都很典型：

1. `SUM(1d.order_user_cnt) == DWD 全局去重用户数` —— **去重计数不可加**，逐日之和（5883）必然大于全局去重（1195）。正确写法是逐日核对 + 单调性检查。
2. 类目 `1d` 行数 == 类目 `1m` 行数 —— 粒度不同（分钟×类目 vs 日×类目），应比"（日×类目）组合数"。
3. 流量域"字段顺序与实时表一致" —— `DESCRIBE` **会把分区列一并列出**，12 列被拿去和 13 列比。
4. 归档自检"全绿但表是空的" —— 空值断言打在空的目标表上，**空洞地通过**。
- **共同教训**：**断言失败时，第一件事是确认"这条断言在说什么"，而不是先怀疑数据。断言写错比没有断言更危险。**
- **依据**：`docs/sprint/SPRINT_3.md` 第 8.4 节；`docs/sprint/SPRINT_5.md` 第 9.4 节；`docs/sprint/SPRINT_4.md` 第 10.2 节。

### Q13. 那个 `click_rate` 缺陷到底是怎么回事？为什么判它错在实时侧？

- **现象**：窗口 `2026-03-21 19:23:00`，实时侧 `view_cnt=2 / click_cnt=1`，但 `click_rate = 0.0000`；离线侧同窗口算出 `0.5000`。
- **五步判定**：
  1. 打印双方原值：0.0000 vs 0.5000，差 0.5000；
  2. 看差值量级：差在**小数点后第一位**，不是末位 → **排除浮点/舍入**，所以不能加容差；
  3. **用第三方判据定责**：`1/2 = 0.5` 是纯算术，不需要比较两侧。离线侧 0 个矛盾窗口、实时侧 1 个 → 差异不在"两侧算法不同"，在实时侧那一行自相矛盾；
  4. 找旁证：实时侧 `click_rate` 全表取值只有 `{0.0000, NULL, 1.0000}`，而全表满足 `0 < click_cnt < view_cnt` 的**分数窗口恰好只有这 1 个**——目前数据只有一个分数样本，而它就是错的（分子为 0 或分子 = 分母的窗口无法暴露截断）；
  5. 对照回归：交易域同一判据 11459 个窗口 0 矛盾。
- **影响范围**：7 个对账判据列在全部 19643 个窗口逐窗口一致，**不影响任何已发布口径的指标数值**。
- **依据**：`docs/sprint/SPRINT_5.md` 第 9.3 节；`sql/metadata/metrics.md` 第 3.3 节。

### Q14. 你为什么不修它？

- **修它的代价**：缺陷在实时链路（Flink 作业）。`behavior_event` 的全部 20000 条消息**仍在 Kafka 里**（earliest = 0），重部署会从 earliest **全量重放**，覆盖实时侧全部 19644 个窗口。那是实时链路的一次全量重建。
- **收益**：修一个派生列的一行。
- **结论**：为一个"小数点后的显示问题"承担"整条实时链路重放"的风险，性价比不成立。项目列了 A/B/C 三个方案并**选择 C**（记录并暂不处理），该选择经项目负责人**复核后维持不变**：**不走方案 A**。
- **其中方案 B 被明确否决**（只改 SQL 不重部署）：会造成"仓库代码与运行作业不一致"，比不改更危险。
- **处置方式（四个动作，都要能说出来）**：① **已定位**（五步判定，用纯算术 `1/2 = 0.5` 这个第三方判据定责，确认离线侧自洽、实时侧 1 个矛盾窗口）；② **判据已改严**（从"两侧比率相等"改为"每侧比率 == 按该侧自身计数重算"），而不是加容差；③ **证据已落盘**（`realtime_rate_anomaly_windows = 1` 作为一等结论，逐窗口标记，作业与验收脚本都单独打印）；④ **未修，原因是重放成本远大于影响**。定性上必须说清：**这是"已定位并留证的真实缺陷"，不是"未解决"，也不是"环境问题"。**
- **依据**：`docs/sprint/SPRINT_5.md` 第 9.3、10 节；`docs/DECISIONS.md` ⏳10。

### Q15. 你怎么知道对账没有"只比两边都有的窗口"来掩盖缺失？

因为**单边窗口是单独统计的**：汇总表里有 `realtime_only_windows` 与 `batch_only_windows` 两个字段，实测两个域都是 **0 / 0**。这样"差异为 0"就有边界可核——否则"某一侧缺了一批窗口"会被静默掩盖。
- 依据：`docs/sprint/SPRINT_5.md` 第 9.2 节判据构成表第 3 条。

## 三、选型与对比

### Q16. 为什么用 Iceberg？Parquet 外部表不行吗？

- **Parquet 外部表缺三样**：没有 ACID（写入中途失败会留下半份数据，只能靠"重跑覆盖"兜底，而那要求每次整分区重写）；没有 schema 演进（源表加字段只能改 DDL，历史数据与新数据的一致性靠人管）；没有时间旅行（无法回答"昨天的表长什么样"，出问题也无法回滚到某个快照）。
- **为什么选 HiveCatalog**：机器上已有 Hive Metastore 3.1.3，Sprint 2 的 Parquet 外部表也在它里面；复用意味着**两种表格式共用同一个目录**，迁移期可逐表对照。
- **否决了什么**：REST Catalog（要多一个常驻进程，内存不允许）；Hadoop Catalog（无法与既有 HMS 表共存）；Flink-Iceberg 连接器（没有流式写湖的需求）。
- **代价**：Java 字节码版本冲突，Iceberg 从任务书写的 1.11.0 降到 **1.10.2**；命名必须避让 catalog 名。
- **依据**：`docs/sprint/SPRINT_5.md` 第 1、1.1、2.3.1、3.1 节；`docs/DECISIONS.md` D13。

### Q17. 迁移过程中怎么保证不出错？

四道：

1. **不原地改**：Parquet 外部表保持不动，Iceberg 表用**不同的库名**建，迁移期逐表对照行数与金额。同名替换会覆盖元数据且无法回滚。
2. **每张表核两样**：行数 **加** 金额 SUM。**行数相同不代表内容没坏**（截断或转型出错时行数照样相等），金额是最敏感的探针。
3. **验证表格式真的生效**：每张表建完后取 `DESCRIBE EXTENDED` 的 `Provider`，必须是 `iceberg`（18 项全过）。
4. **核对清单本身**：作业末尾核对"Iceberg 库表数 == 迁移清单表数"，验收脚本断言库表数 = 23。因为**迁移作业只核对自己清单里的表，漏掉谁它都不会报错**——漏加表会导致"检查不出错"，校验照样全绿（18 张表那次 60/60、23 张表复跑那次 70/70，**两个数的范围不同，不能说成同一个判据的两个结果**）。
- **实测**：迁移清单 18 → 23 张表；18 张表那次 **60/60** 通过，扩到 23 张表复跑那次 **70/70**。
- **依据**：`docs/sprint/SPRINT_5.md` 第 3.2、8.1、9.6 节。

### Q18. 能回滚吗？

- **能退回**：迁移期间两版并存（`lakehouse.` Parquet 外部表 + `iceberg.lakehouse_iceberg.` Iceberg 表），任一侧出问题可以停用另一侧，不需要恢复数据。
- **Doris 侧**：实时链路始终在 Doris，不受 Iceberg 影响；离线结果装载进 `lakehouse_ads` 库，`--stage load` 可单独重跑。
- **真正的"回滚"限制（主动说）**：Iceberg 的快照/时间旅行能力目前**只验证了可用**（`verify-sprint-5.sh` 第 4 步断言快照数 > 0），**没有在业务流程中实际使用**过"回滚到某个快照"。这是一条应当写明的不足。
- **一处反例**：装载脚本曾经是"先 `TRUNCATE` 再 `INSERT`"，在湖仓不可用时会留下**被清空但没装载**的服务层——这是**没有回滚路径**的破坏性顺序。该问题已修（清空前先探测源端可读且至少一行，不满足则保留数据并失败退出）。
- **依据**：`docs/sprint/SPRINT_5.md` 第 3.2 节；`docs/sprint/SPRINT_11.md` 第 10.3 节；`docs/DECISIONS.md` ⏳12。

### Q19. 这个项目和直接上 Flink + Doris 有什么区别？

- Flink + Doris 只解决**实时**这一段。本项目要回答的是**实时与离线是不是同一个数**，所以必须有第二条独立链路（Spark → Iceberg）与一份共同口径，并做逐窗口对账。少了离线侧，"批流一体"无从验证。
- 另外两道本题特有的工程约束：实时与离线**共用一台 16 GB 机器**（必须错峰）；两条链路的结果要**装进同一个查询层**（Doris）才能并排对比。
- **代价**：多维护一条链路、多一套调度、多一层内存管理。

### Q20. 和直接上 ClickHouse 有什么区别？

- ClickHouse 是**查询引擎**，不是口径一致性的解法。换成 ClickHouse 之后，"实时与离线算的是不是同一个数"这个问题依然存在，只是换个地方存在。
- 本项目选 Doris 的具体理由是：它能同时承接**实时写入**（Routine Load + UNIQUE KEY + merge-on-write 实现幂等）与**离线批量导入**（`S3()` 表函数直读 Parquet），因此两条链路的结果落在同一个查询层，服务层与 Agent 只需要一个出口。
- ClickHouse 属项目规范中"未经批准禁止引入"的清单内组件；引入需走"说明原因 → 说明影响 → 给出方案 → 等待确认"的流程。
- **依据**：`AGENTS.md` 第 2.3 节；`docs/sprint/SPRINT_3.md` 第 4.2 节。

### Q21. 为什么不用 Lambda 架构？

- Lambda 的问题恰恰是本课题要解决的：同一指标两份实现、口径不一致、维护成本翻倍。
- 本项目的做法是**共用分层模型与共用口径文件**：两条链路都按 ODS/DWD/DWS/ADS 分层、都以 `sql/metadata/metrics.md` 为唯一定义，并用对账证明这一点成立。
- 更准确的定位是"湖仓融合 + 统一口径"，而不是纯 Kappa（本项目并没有把离线链路也改成纯流式）。
- **依据**：`docs/PROJECT_DESIGN_V1.md` 第 1.1 节；`sql/metadata/metrics.md` 第 6 节。

### Q22. 为什么监控不用 cadvisor / node-exporter / alertmanager？

- **内存预算**：监控的硬上限是 512 MB（Prometheus 256m + Grafana 256m），每多一个容器就多一份常驻内存，塞不下。
- **替代方案**：容器级内存实测改用 `docker stats --no-stream` 取证——**取证方式可以换，预算是硬约束**。
- **告警未接入是明确的边界**：阈值判断刻意留在 `infrastructure/quality/`，因为那里是**可审计的 SQL**，比 YAML 里的表达式更容易讲清楚。
- **依据**：`docs/sprint/SPRINT_11.md` 第 5、10 节。

### Q23. 为什么 Prometheus 不用最新版 3.14.0？

因为它虽然是最新版（2026-08-17 发布），但 **EOL 是 2026-09-30——只剩 3 天**，不适合钉在一个毕业设计里。最终选 3.13.3：3.13 是 LTS 线（2026-07-01 发布，LTS 支持到 2027-07-31）。
- **顺带一个容易踩的细节**：两个镜像的 tag 写法不同——`prom/prometheus:v3.13.3`（带 v）而 `grafana/grafana:13.2.2`（不带 v）。写成不带 v 会拉不到镜像。
- **依据**：`docs/sprint/SPRINT_11.md` 第 2、2.1 节。

## 四、边界与安全

### Q24. Agent 怎么保证不胡说？

四个机制：

1. **来源可核对**：回答附**实际执行**的 `executed_sql`（守卫会改写 LIMIT，所以必须返回改写后的那条）、命中的 `docs`（**带文件与行号**，可当场翻到那一行）、以及 `tables`（**由服务端提取**，不靠调用方自报）。
2. **失败即失败**：查询失败必须返回真实错误，**严禁回退到编造数据或经验值**；MCP 不可达时工具返回失败结果，**不**自动回退到直连。
3. **口径有出处**：检索节点每问必跑（不是"让模型自己决定要不要查"），命中结果写入 `state.docs` 随回答返回；如果语料里确实没有某个口径（例如"复购率"），要求**如实说明语料中没有**，不得编造公式。
4. **可观测的过程**：`validation` / `retries` / `graph.path` 都是响应字段，能看出它走了哪些节点、重试了几次。
- **实测**：问「复购率怎么算」→ 如实回答"口径文档里没有复购率的定义"并给出核查过程；问「用 ads_traffic_1d 查 PV/UV」→ 两次被拒后如实回答"给不出来"并列出错误原文。
- **依据**：`docs/sprint/SPRINT_7.md` 第 3.3、4.2 节；`SPRINT_8.md` 第 9.5 节；`AGENTS.md` 第 10.1、10.3 节。

### Q25. 怎么防止它执行危险 SQL？

**三道防线**：

| 防线 | 位置 | 拦住什么 |
| --- | --- | --- |
| ① SQL 守卫 | `services/api/app/sqlguard.py` | 非 SELECT、多语句、注释、DDL/DML、白名单外的表；强制 LIMIT |
| ② 只读账号 `agent_ro` | Doris | 即使守卫被绕过，写操作仍被数据库拒绝 |
| ③ 连接级超时 15s | 数据服务 | 慢查询断开，不拖垮集群 |

- **实测四类攻击全部被拒且原因正确**：DELETE → `NOT_SELECT`；未授权表 → `TABLE_NOT_ALLOWED`；多语句 → `MULTI_STATEMENT`；注释注入 → `COMMENT`。
- **强制 LIMIT 实测**：请求 5 行 → `executed_sql` 带 `LIMIT 5`、`row_count = 5`。
- **两层拒绝的实证**：`agent_ro` 建表被 Doris 拒绝（`Access denied; you need (CREATE)`）。
- **两道已知取舍（主动说）**：结尾分号 `;` 也被拒、字符串字面量里的 `;` 也被拒——属**误伤而非漏洞**（要区分就得做词法分析），被拒后 Agent 会改写 SQL 重试，两条都写成了断言以防被当 bug 顺手改掉。
- **依据**：`docs/sprint/SPRINT_7.md` 第 3.2、8 节；`SPRINT_12.md` 第 2.3 节。

### Q26. Agent 的权限是怎么隔离的？

**进程边界即权限边界**：

- Agent 进程里**没有数据库凭据**，也**没有 mysql 客户端依赖**。它只能通过 HTTP 调只读数据服务（`POST /data/api/query`）取数。所以"Agent 不得拥有数据库管理员权限"由**架构**保证，而不是靠代码自觉——**想绕过也没有入口**。
- 服务端口只绑回环：数据服务 `127.0.0.1:8000`、Agent `127.0.0.1:8100`、MCP `127.0.0.1:8200`，只应由 Nginx 反代访问。直接暴露到公网既绕过 Nginx 的方法限制，也让这道进程边界失去意义。
- **为什么安全检查放在服务端而不是 Agent 里**：放在 Agent 里等于让被约束者自己当裁判。
- **MCP 侧同样**：`services/mcp/app/config.py` 只读非敏感环境变量；systemd 单元**没有** `EnvironmentFile=.env`；验收会扫单元文件 + `/proc/<pid>/environ` + 源码，都不许出现任何口令键名。
- **依据**：`docs/sprint/SPRINT_7.md` 第 1.1、2 节；`SPRINT_10.md` 第 3、7 节；`README.md` 第 7.3 节。

### Q27. MCP 是不是又开了一条绕过守卫的路？

不是，这正是本阶段的设计核心。

- **两条路径的终点、守卫、账号完全相同**（`POST /data/api/query` + `sqlguard` + `agent_ro`），差别只在"谁来发起那次 HTTP"。
- **如果它变成"另一条能取数的路"，"不得绕过 sqlguard"这条铁律立刻就被绕过了——因为绕过的方式恰恰是"再实现一遍"。** 因此 MCP 服务里唯一的取数实现就是 HTTP 调那个只读接口，依赖里没有任何数据库驱动。
- **实证**：经 MCP 发 DELETE / 未授权表 / 多语句 / 注释注入，四类全部被拒且原因正确；同一 SQL 经 MCP 与经直接 HTTP 的结果**逐字段 IDENTICAL**，`executed_sql` 也相同。
- **为什么不做自动降级**：自动降级会让 MCP 路径在任何一次连接抖动后**悄悄消失**，而所有断言仍然全绿——这是最难发现的一类失效。因此路径由 `AGENT_DATA_PATH` 显式决定。
- **依据**：`docs/sprint/SPRINT_10.md` 第 2、3、5.2、7 节。

### Q28. 接口没有鉴权，不怕被刷吗？

- **如实说：接口无鉴权是已知限制**——知道 IP 就能读指标。
- **缓解条件**：全部接口**只读**（写操作被守卫和只读账号两层拒绝），且不涉及个人隐私字段（本项目是合成数据）。
- **计划**：后续加 Token；演示环境（毕业设计）可接受。
- 同类限制还包括：Airflow 用 SimpleAuthManager（官方声明"仅供开发测试"、口令明文、无轮换）；MinIO 用 root 凭据且密钥对 `ps` 可见。
- **依据**：`docs/DECISIONS.md` 第三节第 1、2、4 条与 ⏳2、⏳3、⏳4。

### Q29. 为什么用明文 HTTP？为什么不直接上 HTTPS？

- **曾经上过**：为了规避公网偶发 502，站点启用 443 + 自签证书，公网实测 **64/64 全部 200**。
- **后来停用**：按 IP 访问只能自签，浏览器每个会话都要点一次"高级 → 继续前往"，演示观感不好；等注册域名 + 申请证书 + 完成备案后再启用。
- **支撑这个决定的补充实测**：关掉客户端 VPN 代理后重测，明文 HTTP **30/30 全部正常，零异常**——那个改写响应的中间设备在 **VPN 的出口路径上**，不在这条 IP 直连路径上。所以"必须上 TLS"这个结论被修正成了"当前网络下明文即可"。
- **方法比结论更值得说**：那个 502 **没有 `Server` 响应头、响应体为空**，而 nginx 发出的 502 必带 `Server: nginx/1.24.0` 与 HTML 错误页 → 它**不是 nginx 发的** → 一个响应头把嫌疑从"我们的服务"缩小到"链路中间"。**结论要跟着证据走，不要跟着上一次的结论走。**
- **演示前提**：明文形态下**不要挂 VPN / 代理**。
- **依据**：`AGENTS.md` 第 15.7 节；`docs/sprint/SPRINT_6.md` 第 8.6 节；`docs/DECISIONS.md` ⏳2、D6。

## 五、资源与事故

### Q30. 内存只有 16 GB，为什么要同时跑实时和离线？

不是"要"，是**只能**——本项目只有这一台服务器（4 核 / 16 GB / 100 GB），实时链路常驻约 13.7 GB。

- **所以做法是错峰**，不是并行：跑批前暂停 Flink 栈（释放约 1.65 GB，实测 2282 → 3935 MB）→ 过内存闸门（阈值 3000 MB）→ 跑批 → 恢复 Flink 栈并跑健康检查自检。
- **四层防护**：① 拒绝启动（可用 < 3000 MB 直接拒绝；已有 Spark 作业时拒绝叠加）；② 错峰执行；③ 限制上限（驱动/执行器各 768m，`spark-submit` 容器补 `mem_limit`）；④ 4 GB swap 兜底（swappiness=10，**故意不写 fstab**，因为 Doris BE 不允许在有 swap 的机器上启动）。
- **代价**：批处理期间实时链路暂停，看板曲线会延后追上（数据不丢——Flink 从已提交位点续跑，重复部分由 Doris UNIQUE KEY 幂等覆盖）。这也是调度时间选凌晨 03:00 的原因。
- **依据**：`docs/sprint/SPRINT_3.md` 第 4.4、8.1 节；`AGENTS.md` 第 15.5、15.8 节。

### Q31. 出过事故吗？怎么解决的？

**出过两次性质不同的事故**，都在报告里单列。

**第一次：批处理打穿内存，整机失联。** 服务器在几分钟内完全失去响应（SSH 无法建立会话、ICMP 无响应、nginx 与 FastAPI 全部超时），只能从云控制台强制重启。三层原因叠加：实时链路常驻 13.7 GB 只剩约 2.0 GB；Spark 驱动跑在宿主机（client 模式）约 2 GB 正好把余量吃干；**宿主机没有 swap**，内核无处回收页面，于是内存压力不是表现为"变慢"而是**整机假死**。先出现的症状其实是 Doris BE 拒绝所有查询（`MEM_ALLOC_FAILED`，sys available memory 510.64 MB），那才是第一现场。**数据无损失**（重启后容器自动恢复，health-check 11/11）。处置就是上面那四层防护。
- **教训**：在一台已经跑满的机器上，"再加一个批处理"不是加一个进程，而是把系统的安全余量直接归零。**先算内存账，再动手。**

**第二次：原子换树同步把机器状态删了。** 详见下一题。

- **依据**：`docs/sprint/SPRINT_3.md` 第 8.1 节。

### Q32. 第二次事故具体是什么？怎么定位的？

**现象**：为了绕过同步脚本的"Spark 运行中"守卫，写了一个"原子换树"同步脚本（`mv 旧树 → tar 解到 .new → mv 到位 → rm -rf .old`）。因为只打包了一个子目录，`rm -rf .old` 把 **`.env`（唯一存有真实凭据的文件）、三个 venv、`airflow/airflow.env`，以及三个由 compose 挂载的第三方 JAR** 一起删掉了。

**定位的三条证据**（这是重点）：

1. `docker compose` 直接不可用（它靠 `.env` 做变量插值）→ 范围从"某个服务配错了"缩小到"机器状态丢了"；
2. 报错是 `DatastoreDriverNotFoundException: com.mysql.cj.jdbc.Driver was not found in the CLASSPATH`——说的是"CLASSPATH 配错了"，**而真相是那个 JAR 被删了**。**报错指向的不是根因**；
3. 磁盘上"文件丢失"表现为**一个空目录**（Docker 会在挂载点文件不存在时把它创建成目录），`ls -la` 看上去像有东西 → **判断挂载型文件是否存在必须用 `-f` + `-s`**。

**根因**：不是环境问题，是**一个绕开守卫的决定**。守卫拦的是"运行中的脚本被半覆盖"；原子换树防住了半覆盖，却把**子集同步变成了整树替换**——子集之外的机器状态不再受保护。**绕过一个守卫时必须重新论证它原本防的是什么，以及新方案有没有引入更大的风险。**

**沉淀成硬规范**：共享文件权限按**所有读者**定（`.env` 必须 `640 root:dpapi`，600 会让 Agent 起不来，且**故障现场与改动现场不在一起**）；**禁止原子换树同步**，只覆盖需要覆盖的文件、用 `mv` 做单文件原子替换；凭据确认落盘前**禁止** `compose up/restart`；共享编排文件必须先落创作副本、验收核对 md5。

- **依据**：`AGENTS.md` 第 15.11 节；`docs/sprint/SPRINT_12.md` 第 8.2 节；`docs/DEVELOPMENT_LOG.md` 第 1529~1546 行。

### Q33. 内存闸门真的拦住过东西吗？还是只是个摆设？

真的拦过，而且这是它最有说服力的一次记录：

- 实测**主动拒绝过一次批处理**（当时可用内存 2258 MB）——**拒绝而不是硬跑**。这正是"闸门是按设计工作的"的证据，也是避免 Sprint 3 那种整机事故的机制。
- 另有 `--with-lake` 校验被闸门拒绝**两次**的记录。
- **为什么没有调低闸门**：实测暂停实时链路可释放约 1.65 GB。**调低闸门是把保护拆掉，错峰才是正解。**
- **依据**：`AGENTS.md` 第 15.8 节；`docs/DECISIONS.md` D11；`docs/sprint/SPRINT_11.md` 第 5 节。

### Q34. 批量作业要跑多久？为什么这么久？

- 一次成功运行：9 个任务耗时合计 **1992.3 s**，**端到端约 81 分钟**。
- **两个数不等**，必须一起说：`ads_layers` 的开始时间与 `dws_layers` 的结束时间之间有 48 分钟间隔（那天的重试/等待窗口，该 run 的 `ads_layers` 有多次 attempt）。
- **构成**：错峰固定成本（暂停 + 恢复）= 149.8 s；四个分层/归档作业 = 1514 s，**占 76%**；`load_to_doris` 128.8 s；`reconcile` 138.8 s。
- **结论**：要压缩端到端时间，应从**分层作业的 Spark 启动与分区数**入手，而不是优化装载或对账（两项加起来不到 270 s）。
- **对照**：一次人工触发的运行合计 1491.7 s、端到端约 25 分钟。
- **依据**：`docs/PERFORMANCE.md` 第 3.1、3.2、3.3 节。

### Q35. 性能数字是在什么条件下测的？

- 采集时间 **2026-09-27 09:11~09:15（+0800）**；现场 load average **1.46 / 3.06 / 3.85**；可用内存 **3921 MB**；**Spark 作业 0 个**；8 个 Flink sink 作业 RUNNING（常驻约 12 GB）。
- **采样口径**：每项 7 次，另有 1 次预热不计入；取**中位数**（同时给 min/max），**不报平均值**（单次延迟受 JIT / 页缓存 / 邻近查询影响大，平均值会被离群值拉走）。
- **路径**：全部经**本机回环**，**不含公网链路**，因此不代表浏览器访问体验。
- **批处理耗时取自 Airflow 元数据库**的既有运行记录，**没有为采这个数字重跑流水线**（内存铁律）。
- **为什么必须记现场**：同一台机器上，一次 Spark 作业就能把只读接口延迟改变数倍。没有现场的"8 ms"和"40 ms"看起来是性能差异，实际可能只是"测的时候有没有别的东西在跑"。
- **依据**：`docs/PERFORMANCE.md` 第 0、0.1 节。

## 六、反思与展望

### Q36. 你最大的技术贡献是什么？

三条，都是具体的：

1. **把"批流一体"做成了一个可证伪的断言**：交易域 11458 个窗口、流量域 19643 个窗口逐窗口比对，不一致 0；并且给出了判据的设计与**两次打磨过程**（去重指标不上卷、比率列按各自计数重算、单边窗口单独统计）。
2. **在 16 GB 单机上同时承载实时与离线**：错峰批处理 + 3000 MB 内存闸门，闸门按设计工作（拒绝过一次，可用 2258 MB）。
3. **把 Agent 的可信性做成了架构属性**：进程边界（无数据库凭据）、来源可核对（`executed_sql` / `docs` 带行号 / 服务端提取血缘）、失败与重试可数（实测 `retries=1` 与 `retries=2` 各一次）、拒绝即失败（不做自动降级）。

### Q37. 你最大的不足是什么？

**最实质的一条是那个 `click_rate` 缺陷的处置方式**，因为它最能说明我的取舍标准：

> 我定位到实时侧有一个窗口的比率列与它自己的计数矛盾（应为 0.5000，落库 0.0000），离线侧独立实现是对的。**但我没有修**——修它要重部署 Flink 作业并触发 Kafka 全量重放，覆盖实时侧全部 19644 个窗口；为一个小数点后的显示问题承担这个风险不划算。我的处置是把判据**改严**、把矛盾窗口数**落盘成证据**、写进已知限制。**没有加容差，也没有删证据。**

**第二实质的是数据本身**：全部是合成数据，不代表真实业务分布。
**第三是结构债**：两份阶段分发表重复未重构。

（不要答"时间不够、做得还不够完善"。）

### Q38. 如果重做一遍，你会怎么改？

四条：

1. **结构上先收敛入口**：把阶段分发做成单一实现（现在的 `run-batch-pipeline.sh` 与 `submit-offline-job.sh` 各有一份 `case`，Sprint 4 已经因此踩过"改一处漏一处"的坑）。
2. **口径判据先写测试再写作业**：本项目的多次返工都源于"判据本身没被验证过"，把判据当作被测对象来写会更早发现问题。
3. **机器状态显式化**：把 `.env`、venv、挂载 JAR 这类"不可重建的机器状态"在仓库里列成一份清单，并让部署脚本启动时自检——而不是等事故之后才知道它们的存在。
4. **监控从一开始就带告警**：现在是"只抓取与展示"，问题不会主动通知。

### Q40. 检索为什么不用向量？这是不是偷懒？

不是偷懒，是三条事实约束下的选择（依据 `docs/sprint/SPRINT_9.md` 第 2.1 节）：

1. **DeepSeek 官方 API 没有 embeddings 端点**（官方文档只提供对话补全，`/v1/embeddings` 返回 404）。要走向量就必须**再引入一个外部供应商与 Key**。
2. **本机放不下本地 embedding 模型**（4 核 / 16 GB，实时链路常驻约 13.7 GB，可用约 4.3 GB）。
3. **向量库属项目规范明确禁止未经批准引入的技术栈**（Milvus / Elasticsearch）。

而且词法检索在本项目**够用而不是妥协**：语料只有几十篇；提问高度依赖关键词（`GMV`、`UV`、`ads_batch_trade_1m`、`payment_success_rate`），正是 BM25 最擅长的精确词项匹配；**命中理由可解释**（能说清"因为命中了 `gmv` 与同义词扩展 `卖了多少钱→GMV`"），而向量相似度给不出这种理由——而本项目的回答本来就要给来源。

**代价与对策也已登记**：语义相近但用词不同要靠**显式同义词表**（**55 条**，每条带理由，可审查、可增删、可测试；条数以 `services/agent/knowledge/synonyms.json` 的 `synonyms` 字段实测为准）覆盖；中文分词自实现（ASCII 词 + CJK bigram，不引入 `jieba`）；**先抽象接口** `Retriever.retrieve(query) -> docs`，日后换向量后端只替换这一个实现类。

**一条自证诚实的取舍**：文档里写清这是 **BM25 词法检索**（含 idf 与长度归一化），**不声称**语义检索。诚实描述比夸大更安全。

### Q41. 你的"RAG"到底算不算 RAG？

按本项目的写法：**算检索增强，但增强的是"口径与表结构的可追溯引用"，不是语义理解**。

- 检索是 `retrieve` 节点**每问必跑**的确定性前置步骤（不是让模型自己决定要不要查），命中结果进 `state.docs` 并随回答返回，带文件名与行号。
- 语料 65 条：指标口径 22 + 通用约定 15 + 事件格式 4 + 分层说明 8 + 表结构 16。
- **可验证性**：正例（"最近一周卖了多少钱"→ 命中 `metric:gmv`，来源 `sql/metadata/metrics.md:33`）与**负例**（"今天天气怎么样适合钓鱼吗"→ hits 为空）都写成了验收项——只有正例的话，"把所有词都映射一遍"的坏配置也能全绿。
- **不声称的部分**：不做语义检索、不做重排模型、不做用户反馈闭环。

### Q42. 你从这个项目里学到的最重要的一件事是什么？

**"成功信号"不可信。**

这条在项目里反复出现，每次形态不同，但都是同一类：

- 命令返回成功、构建报成功、自检全绿，都可能什么也没干（归档阶段 0.6 秒"成功"，实际静默空转）；
- `tr -d '\n'` 把 SQL 注释与语句压成一行，整条语句变成注释，`mysql` 不报错、退出码 0；
- 自检在**空表**上空洞地通过；
- 维表为空导致 JOIN **静默返回 0 行**（HTTP 200、`row_count=0`、信封完整）；
- `pgrep -c` 匹配的是进程名而不是命令行，会稳定地返回 0，把人引向"进程已死"的错误结论；
- 用健康端点验证凭据会得出**相反**的结论（MinIO 的 health 端点对**正确**凭据也返回 400，它根本不看 Authorization 头）。

**所以任何观测手段都要先确认它在测什么**；而验收的判据必须是**回到目标状态去验证**（表里到底多少行、镜像里到底有没有那个 jar），并且要有一个**必然失败的对照组**。

- **依据**：`AGENTS.md` 第 15.8 节；`docs/sprint/SPRINT_4.md` 第 10.2 节；`docs/sprint/SPRINT_5.md` 第 8.3 节；`docs/sprint/SPRINT_11.md` 第 7.1、7.13 节；`docs/PERFORMANCE.md` 第 5 节。

## 附录：三个"必背"回答（如果只能准备三个）

**① 数据是合成的**：合成、种子可复现（`20260926`）、业务约束生成期强制、时间因果保证；局限是不代表真实分布；正因为它可复现且满足约束，才支撑得起逐窗口对账。

**② 怎么证明一致**：前提是事件与业务行一一对应 + 离线 ADS 与实时同粒度；方法是逐窗口比对 + 区间截断 + 单边窗口单独统计；结果是交易域 11458 个窗口、流量域 19643 个窗口不一致 0，两侧 GMV 精确到分相等；并且判据被打磨过两次（方向都是变严）。

**③ 最大的不足**：实时侧 1 个窗口的 `click_rate` 缺陷——能定位、离线侧正确、修它要全量重放所以选择不修、处置是把判据改严并落盘证据、**没有加容差也没有删证据**。
