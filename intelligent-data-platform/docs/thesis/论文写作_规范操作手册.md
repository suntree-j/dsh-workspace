# 论文写作规范操作手册（本课题专用）

> 配套《codex论文写作实战指令手册8.20.docx》使用：手册给的是**通用指令模板**，本文件把它落成**这个课题的具体操作**——哪一章用哪条指令、素材从哪个文件取、什么话不能说、怎么验收。
> 适用对象：本人、Codex、任何接手写这份论文的人。

---

## 0. 这份手册要治的三个病

上一版材料出问题，不是文笔问题，是三个流程病：

| 病 | 症状 | 药方 |
| --- | --- | --- |
| **时态错位** | 开题材料写成了结题报告（"已实现""已跑通""实测"） | 先问：这句话是**打算**还是**结果**？开题只准写打算 |
| **实现细节冒充学术内容** | 大量篇幅讲判据表、比率列、零值窗口 | 论文讲"为什么这么做、这么做解决了什么"，实现细节进附录或指标字典 |
| **数字无出处** | 同一个数字在五份文件里有三个版本 | 所有数字只从 `REAL_DATA_FACTS.md` 取，取的时候连**口径**一起抄 |

---

## 1. 三条底线（违反任意一条，整段重写）

1. **证据可核**：每一个数字、每一句"证明了什么"，都要能指到具体文件/表/命令。
2. **时态正确**：开题=将来时；中期=进行时；论文正文=过去时陈述结果 + 现在时陈述结论。
3. **不编造**：文献必须真实存在且卷期页可查；没有的数据就写"未取得"，不写"约为"。

---

## 2. 写作工作流（六步，每步绑定具体动作）

对应手册附录"AI 辅助论文写作的正确工作流"，但落成本课题的动作：

| 步 | 谁做 | 做什么 | 用哪条指令 |
| --- | --- | --- | --- |
| 1 | 本人 | 定研究问题、跑数据、拿证据（**已完成**：`REAL_DATA_FACTS.md` + `EVIDENCE_MATRIX.md`） | — |
| 2 | 本人 | 定大纲与每章核心论点（`REPORT_OUTLINE.md` 已定 7 章） | 指令 03 |
| 3 | AI 辅助 | **逐节**写：一次只写一节，先给素材再要求输出 | 指令 05–10 |
| 4 | 本人 | 改写：删套话、补本项目细节、把"我们"改成"本文" | 指令 13/15 |
| 5 | AI 辅助 | 统稿与自检 | 指令 12/14/19/20/21 |
| 6 | 本人 | 通读、核所有数字与引用、导出、打印校对 | 指令 22 |

**硬规则**：绝不让 AI 一次性写整章。每次输入必须包含三样：①本节要回答的问题 ②可用的证据（文件 + 表名 + 数值） ③不许出现的内容。

## 3. 章节 → 指令 → 证据 → 验收

| 章 | 写作要点 | 手册指令 | 证据来源 | 验收 |
| --- | --- | --- | --- | --- |
| 摘要（中/英） | 200–300 字/词，一段式；只写问题、方法、结论，不写背景铺垫 | 04、17 | `REPORT_DRAFT.md` 摘要段 | 关键词 3–5 个；无数字堆砌 |
| 1 绪论 | 漏斗式：行业现象 → 两条链路并存 → 同一个指标两个数 → 本文要补的空白；研究现状按主题分，不按时间罗列 | 05、06 | `docs/thesis/REPORT_OUTLINE.md` §1；文献 16 条 | 国内外都要有；每条引注有对应文献 |
| 2 相关技术 | 每小节三段式：是什么 → 在本项目哪一段 → 为什么不用另一种 | 06 | `services/agent/knowledge/layering.md`、`README.md` 版本表 | 不出现"最新版本"；版本号钉死 |
| 3 需求分析 | 功能需求给"谁在什么场景要什么"，非功能需求给可度量指标（内存、时延上限） | 03、07 | `AGENTS.md`、`docs/development-environment.md` | 每条需求能落到一个验收脚本 |
| 4 平台设计 | 分层设计（采集/计算/存储/服务）+ 指标口径的唯一性 + 对账设计；**不写实现细节** | 03 | `docs/PROJECT_DESIGN_V1.md`、`sql/metadata/metrics.md` | 有一张架构图 + 口径表；无代码 |
| 5 平台实现 | 按"做的时候遇到的问题 → 怎么解决 → 结果如何"写；问题要具体（如整数除法、乱序装载） | 07、08 | `REAL_DATA_FACTS.md`、`DEVELOPMENT_LOG.md`（只取事件不取数字） | 每个坑给根因与修法，不写"经过努力" |
| 6 测试与验证 | 对账结果、质量校验、性能、安全四块；**每个结论前先给口径** | 08 | `EVIDENCE_MATRIX.md` | 数字与 `REAL_DATA_FACTS.md` 逐字一致 |
| 7 总结与展望 | 三条贡献 + 五条限制 + 后续方向；限制要具体到"哪个能力没做" | 10、16 | `DATA_AND_LIMITATIONS.md` | 不出现"首次/填补空白/重大突破" |
| 附录 | 符号说明、图表清单、复现命令 | — | `REPORT_DRAFT.md` 附录1–5 | 图表清单与正文表题编号一致 |

## 4. 证据使用规则

### 4.1 数字只有一个出口

**所有数字从 `docs/thesis/REAL_DATA_FACTS.md` 取。** 该文件之外的任何数字（含聊天记录、旧报告、PPT、代码注释）都不作为写作依据；发现冲突，以 `REAL_DATA_FACTS.md` + 现场复查命令为准，并同步修正该文件。

### 4.2 数字三件套

每写一个数字，同时给出：**值 + 口径 + 出处**。
> 例：交易域在 `2011-11-01 08:16 ~ 2011-11-30 17:40` 的对账区间内共 40,358 个分钟窗口，两侧逐窗口比对不一致为 0（口径：`TAIL_GUARD_MINUTES = 3` 截尾；出处：`ads_reconcile_summary`）。

只写"不一致为 0"不写口径 = 不合格。

### 4.3 措辞红线

| 不能写 | 改写为 |
| --- | --- |
| 完全一致 / 零差异 / 一模一样 | 对账区间内逐窗口比对不一致为 0 |
| 生产可用 / 高并发 / 支撑百万级 | 在单机 4 核 16 GB 上稳定运行 |
| 全量验证 / 全部覆盖 | 在已装载的数据集范围内逐窗口验证 |
| 实时比离线快 | 实时链路面向低时延查询，离线链路面向准确与可回溯 |
| 向量检索 RAG | 词法检索（BM25）+ 同义词表 |
| 42 万条 / 千万级 | 按 `REAL_DATA_FACTS.md` 的实际装载量写，不取整 |

### 4.4 时间与规模表述

- 两个数据集**保留原始事件时间**（交易域 2009-12–2011-12，流量域 2017-11），不得写"为贴近当下做了时间平移"。
- 不得把"官方全量规模"与"实际入库规模"混为一谈：说全量时标"官方（未入库）"，说入库时标"入库子集"。

## 5. 文献规则

1. **数量**：基准 16 条（外文 7 / 中文 4 / 规范文档 3 / 数据集 2），答辩版不再减少；扩充只增不减。
2. **可核**：每条给"作者. 题名[类型]. 刊名, 年, 卷(期): 页码. DOI"。**不确定的卷期页宁可不写，也不编。**
3. **一一对应**：正文引注集合 == 文献表集合，双向都不许有空。
4. **中文文献 ≥4 条**：否则"国内外研究现状"里的"国内"是空的。
5. **数据集用 `[DS/OL]`**：`CHEN D. Online retail II data set[DS/OL]. Irvine: UC Irvine Machine Learning Repository, 2011[2026-11-06]. https://doi.org/10.24432/C5CG6D.`
6. **引注位置**：句末标点前；一条句子引多篇写 `[3,12]`；不引整段。

## 6. 语言风格（去 AI 味）

### 6.1 禁用词表

恰恰、才是、正是、本身、赋能、闭环、抓手、维度、链路打通、经过努力、深入探索、一定程度上、具有重要的现实意义、本文的贡献在于（改成具体动作）。

### 6.2 句式规则

- 一段一个论点，**首句就是论点**，后面给证据。
- 不用"首先/其次/最后"三段式套话，用内容本身排序。
- 破折号每千字 ≤1 个；感叹号 0 个。
- 长句拆短：单句 ≤45 字。
- 不写"我们认为"，统一写"本文"。

### 6.3 时态与人称

| 位置 | 时态/人称 |
| --- | --- |
| 设计与实现 | 本文采用 / 本文实现了（现在完成） |
| 实验与结果 | 得到 / 显示 / 达到（陈述事实，不加"成功地"） |
| 结论与展望 | 表明 / 说明 / 后续将（现在时） |
| 开题材料 | 拟 / 将 / 计划（**禁止**任何完成时） |

### 6.4 段落长度

正文段落 80–200 字；连续三段超过 250 字必须拆。表格前后各留一行正文说明，不许只放表不说话。

## 9. 八个真实教训（都踩过）

1. **模板行带 `w:cantSplit`**：内容超一页会被 Word **静默丢弃**，页面上看不出异常。必须删该属性并目视复核。
2. **表格重复 `tblW`/`tblLayout`**：会产生两个同名元素，Word 按后者重排列宽，整张表和模板"长得不一样"。
3. **同一条 SQL 在两边算不一样**：Flink 里 `CAST(SUM(a)/SUM(b) AS DECIMAL)` 是**整数除法**，先转型再除才对。
4. **多代重放导致装载乱序**：`earliest-offset` 每次重启都整代重放，Doris UNIQUE KEY 后写覆盖先写，GMV 少 18%。修法是单代重放 + 单分区。
5. **`.env` 覆盖 compose 默认值**：TaskManager 堆只有 2 GB，1,000 万条时 OOM。改配置要同时查 `.env`。
6. **判据本身会造出假通过**：分母为 0 的比率若参与判定，会把"无数据"判成"不一致"。比率列只做诊断。
7. **"看起来是缺陷其实不是"**：`SUM(quantity × product.price)` 与 `amount` 不等的 909 行，是折扣模型，不是脏数据；先查口径再下结论。
8. **AI 写的文献会编**：上一版 16 条里有 3 条卷期页是错的、4 条中文是补的；**任何文献都要自己去数据库核**。
