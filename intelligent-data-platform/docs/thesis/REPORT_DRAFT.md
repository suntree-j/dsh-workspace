## 摘要

电商业务的数据同时以两种形态产生：一类是点击、加购、下单、支付、退款等持续不断的事件流，对时效性的要求是秒级；另一类是日级、月级的经营分析，对准确性与可回溯性的要求高于时效性。传统做法把两者建成两套系统，代价是同一指标存在两份实现，口径容易分叉；一旦实时与离线对同一个"GMV"给出不同数值，建立在其上的任何智能应用都失去了判断依据。

本文构建了一个面向电商场景的批流一体数据分析平台。平台以 Kafka 作为统一事件入口，实时链路为 Kafka → Flink → Doris，用 1 分钟滚动窗口产出秒级指标；离线链路为 MySQL 与 Kafka → Spark → Iceberg（HiveCatalog，存储于 MinIO/S3A），按 ODS → DWD → DWS → ADS 四层建模，由 Airflow 按依赖调度；两条链路共用一份指标口径文件 `sql/metadata/metrics.md` 作为唯一定义，并在此之上提供只读数据服务、Vue 数据看板，以及一个不持有数据库凭据的自然语言问答 Agent（LangGraph 图式编排 + BM25 词法检索 + MCP 工具暴露）。

本文的核心验证手段不是"链路跑通"，而是**逐窗口交叉对账**：交易域在 11458 个分钟窗口上逐窗口比对，不一致 0 个，两侧 GMV 精确到分相等（51,890,375.77）；流量域在 19643 个分钟窗口上逐窗口比对，不一致 0 个、单边窗口 0 个（见 `docs/sprint/SPRINT_3.md` 第 7 节、`docs/sprint/SPRINT_5.md` 第 9.2 节）。**这一结论的范围必须与数字一起读**：它指"在两侧数据范围求交并尾部留 3 分钟安全边界后的**对账区间内**、以**分钟窗口**为粒度、在**缺失侧补 0** 的统一口径下，逐窗口比对的可加/去重计数类指标一致"；它**不**覆盖对账区间之外的数据，交易域也**没有**"单边窗口 = 0"的断言（只有"实时侧 ≥ 离线侧 × 90%"的覆盖率容差），派生比率列则不进入交易域对账。**另需披露一个静默窗口**：交易域 11458 个窗口中，**5504 个窗口两侧 GMV 均为 0（48.03%，平凡一致）**，真正承载判别力的是其余 **5954 个有非零业务量的窗口**。在 16 GB 单机上同时承载实时与离线两条链路，采用错峰批处理（暂停 Flink 栈释放约 1.65 GB → 跑批 → 强制恢复并自检），内存闸门阈值 3000 MB，闸门曾主动拒绝一次批处理（可用 2258 MB），选择"拒绝而非硬跑"（见 `AGENTS.md` 第 15.8 节）。

12 个开发阶段（Sprint 0~12）全部验收通过；Iceberg 迁移覆盖 23 张表并逐表核对行数与金额；全量自动化测试 353 passed / 0 failed / 0 skipped / 3 xfailed（见 `docs/sprint/SPRINT_12.md` 第 8.3 节）。**"全部验收通过"不等于"没有遗留问题"**：Sprint 5 仍留 1 项未归零的实时侧数据缺陷（见下段），本文据实披露而不隐藏。

本文如实披露以下限制：全部数据为程序生成的**合成数据**，不含真实业务分布；站点当前为**明文 HTTP**，未启用 TLS；Airflow 使用官方声明"仅供开发测试"的 SimpleAuthManager；实时侧存在 1 个窗口的 `click_rate` 比率列与自身计数矛盾（离线侧同一窗口计算正确）；实时链路执行脚本存在一份重复的阶段分发表未重构。

**关键词**：批流一体；Lakehouse；Apache Iceberg；流批对账；数据质量；检索增强生成；自然语言转 SQL；只读权限边界

## Abstract

E-commerce data arrives in two forms at once: a continuous event stream (views, cart additions, orders, payments, refunds) that demands second-level freshness, and day-level or month-level operational analytics that demand accuracy and traceability above freshness. The conventional approach maintains two separate systems, at the cost of two implementations per metric; once the streaming and batch paths disagree on a single number such as GMV, any intelligence layer built on top of them loses its basis for judgement.

This thesis builds a unified batch-and-streaming analytics platform for e-commerce. Kafka serves as the single event ingress. The streaming path is Kafka → Flink → Doris, producing second-level metrics over one-minute tumbling windows. The batch path is MySQL and Kafka → Spark → Iceberg (HiveCatalog, stored on MinIO/S3A), modelled in four layers (ODS → DWD → DWS → ADS) and orchestrated by Airflow. Both paths share a single authoritative metric dictionary, `sql/metadata/metrics.md`. On top of this foundation the platform exposes a read-only data service, a Vue dashboard, and a natural-language question-answering agent that holds no database credentials (LangGraph orchestration, BM25 lexical retrieval, MCP tool exposure).

The central form of validation is not "the pipeline runs" but **window-by-window cross-path reconciliation**: 11,458 one-minute windows in the trade domain with zero mismatches and GMV equal to the cent on both sides (51,890,375.77), and 19,643 one-minute windows in the traffic domain with zero mismatches and zero one-sided windows (`docs/sprint/SPRINT_3.md` §7; `docs/sprint/SPRINT_5.md` §9.2). Both paths run on a single 16 GB host through time-staggered batch execution: the Flink stack is suspended (releasing approximately 1.65 GB), the batch pipeline runs, and the streaming stack is forcibly restored and self-checked. The memory gate threshold is 3,000 MB and once actively refused a batch run at 2,258 MB available, preferring refusal to running anyway (`AGENTS.md` §15.8).

All twelve development stages passed acceptance. The Iceberg migration covers 23 tables with per-table row-count and monetary-sum verification. The full test suite reports 353 passed / 0 failed / 0 skipped / 3 xfailed (`docs/sprint/SPRINT_12.md` §8.3).

The thesis discloses its limitations: all data is **synthetic**, generated by a program; the site currently serves **plain HTTP** without TLS; Airflow uses the SimpleAuthManager that upstream documents as development-only; one window in the streaming path carries a `click_rate` value that contradicts its own counters (the batch path computes the same window correctly); and a duplicated stage-dispatch table in the streaming-side scripts remains unrefactored.

**Keywords**: batch-stream unification; Lakehouse; Apache Iceberg; cross-path reconciliation; data quality; retrieval-augmented generation; natural language to SQL; read-only privilege boundary

# 第 1 章 绪论

## 1.1 研究背景

电商业务的数据天然同时具备两种形态，两者的特征与诉求并不相同（`docs/PROJECT_DESIGN_V1.md` 第 1.1 节）：

| 形态 | 特征 | 典型诉求 |
| --- | --- | --- |
| 实时流 | 点击、加购、下单、支付、退款等事件持续产生 | 实时 GMV、实时订单量、实时在线人数、风控 |
| 批量离线 | 日/月级别的经营分析、用户画像、商品分析 | 准确、可回溯、口径统一 |

这两类数据的差别不只是"快慢"，还体现在一致性与存储要求上。以用户行为埋点为例，其量级远高于交易事实（每次交互一条 vs 每单一条），且不需要强一致、不需要落业务库，主要用途是漏斗、画像与推荐；而订单、支付、退款是可对账的业务事实，必须有唯一权威副本（`docs/data-source-design.md` 第 4.2 节）。因此把两类数据塞进同一套处理方式并不合适。

传统做法是把实时链路与离线链路分成两套系统（Lambda 架构），代价是**同一指标两份实现、口径不一致、维护成本翻倍**（`docs/PROJECT_DESIGN_V1.md` 第 1.1 节）。

## 1.2 研究意义

本文认为，批流一体最核心也最难回答的问题只有一个：

> 同一条业务事实，走实时链路和走离线链路，算出来的指标是不是同一个数？

这个问题的意义在于它的下游后果。如果实时说 GMV 100 万、离线说 95 万，那么：

```text
同一个「GMV」会出现 3 种算法
   ↓
实时说 100 万、离线说 95 万
   ↓
Agent 引用哪一个都是"错的"
   ↓
数据不可信，智能层无从谈起
```

（`sql/metadata/metrics.md` 第 6 节）

因此本文不满足于"离线也能算出 GMV"，而是要求**逐窗口比对、差异逐条列出、差异为 0 才算通过**（`docs/sprint/SPRINT_3.md` 第 1.1 节）。这一要求把"口径统一"从一句设计原则变成了一个可证伪的断言：只要有一个窗口对不上，结论就不成立。

## 1.3 国内外研究现状

> **本节说明**：本文素材来源于工程实施记录，其中不含文献调研内容。以下仅陈述与本文技术选型直接相关的技术现状，用于解释设计取舍的依据；正式的国内外研究现状需另行检索补充，本文不在此处罗列未经核实著录信息的文献。

在技术侧，与本课题直接相关的现状有四条：

**其一，湖仓表格式要解决的具体缺陷。** 本文使用的 Parquet 外部表方案（`EXTERNAL TABLE ... STORED AS PARQUET`）能用，但缺三样东西：没有 ACID（写入中途失败会留下半份数据，只能靠"重跑覆盖"兜底，而那要求每次整分区重写）、没有 schema 演进（源表加字段只能改 DDL，历史数据与新数据的一致性靠人管）、没有时间旅行（无法回答"昨天的表长什么样"，出问题时也无法回滚到某个快照）。这三条正是本文引入 Iceberg 的直接动因（`docs/sprint/SPRINT_5.md` 第 1 节）。

**其二，大模型在数据分析场景的接入方式。** 当前主流做法是"自然语言转 SQL"，由模型生成查询语句、由服务端执行、由模型解释结果。本文在这一路径上引入两个约束：一是把 SQL 安全检查与只读账号放在服务端而非 Agent 进程内，使"Agent 不得拥有数据库管理员权限"由进程边界保证；二是要求回答必须附带实际执行的语句与命中的口径来源，使"不得伪造查询结果"可以被逐条核对（`docs/sprint/SPRINT_7.md` 第 2 节、第 3.3 节）。

**其三，检索增强的两种实现路线。** 常规做法是 embedding + 向量库。本文在实际条件下否决了这条路线，依据是三条可核实的事实：DeepSeek 官方 API 只提供对话补全、**没有 embeddings 端点**；本机（4 核 / 16 GB，实时链路常驻约 13.7 GB）放不下本地 embedding 模型；向量库属于项目规范明确禁止未经批准引入的技术栈（`AGENTS.md` 第 2.3 节列出 Milvus / Elasticsearch）。因此本文采用 BM25 词法检索加显式同义词表（`docs/sprint/SPRINT_9.md` 第 2.1 节）。

**其四，工具能力的标准化暴露。** Model Context Protocol（MCP）提供了"服务器声明它提供哪些工具、客户端可以 `list_tools()` 读出来"的机制，使"权限最小化"从一句设计口号变成可枚举、可审查的事实（`docs/sprint/SPRINT_10.md` 第 1 节）。

## 2.2 实时计算：Kafka + Flink + Doris

**Kafka 使用 KRaft 模式**，不部署 ZooKeeper；4 个 topic（`order_event` / `payment_event` / `refund_event` / `behavior_event`）各 3 分区、副本 1。分区键的选择有明确目的：订单类事件用 `order_id` 作键、行为事件用 `user_id` 作键，保证同一订单或同一用户的事件落入同一分区，从而保证**分区内有序**（`sql/metadata/kafka_topics.md` 第 4 节）。

**Flink 使用事件时间语义**，窗口类型为 1 分钟滚动窗口（TUMBLE），不使用处理时间。理由在口径文件中写得很直接：**不用处理时间，保证乱序/重放结果一致**（`sql/metadata/metrics.md` 第 1 节）。这一点是后续逐窗口对账能够成立的前提——如果实时侧按处理时间切窗口，同一批事件重放时会落到不同窗口，离线侧无论如何都无法与之逐窗口对齐。

**Doris 用 Routine Load 承接 Flink 的写出**，表的键模型为 UNIQUE KEY + merge-on-write，因此对同一窗口的多次更新（Flink 侧 `upsert-kafka` 在窗口最终触发前会写多条中间态）会收敛为最新值。这一幂等性质是"批处理期间暂停 Flink、恢复后从已提交位点续跑"不会造成数据重复的基础（`docs/data-source-design.md` 第 5.1 节）。

**一个实测得出的格式约束**：事件时间字段格式为 `yyyy-MM-dd HH:mm:ss.SSS`，而不是 ISO-8601 带时区偏移的写法。原因是 Flink 的 JSON 格式解析器不接受后者，实测报 `Fail to deserialize at field: event_time`。这属于实测后的选择，不是风格偏好（`docs/data-source-design.md` 第 4.4 节）。

## 2.3 湖仓与表格式：Spark + Iceberg

选择 Iceberg 的原因是 Parquet 外部表缺 ACID、schema 演进与时间旅行三项能力（见 1.3 节）。

**Catalog 选型**：本项目选 HiveCatalog（`type=hive`），理由是机器上已经有 Hive Metastore 3.1.3 在运行，Sprint 2 的 Parquet 外部表也在它里面；复用意味着**两种表格式共用同一个目录**，迁移期可以逐表对照。否决了两个备选：REST Catalog 需要额外部署一个服务（多一个常驻进程），在本机可用内存条件下不值得；Hadoop Catalog 用文件系统当目录、没有中心元数据，无法与既有 HMS 表共存，迁移期会很别扭（`docs/sprint/SPRINT_5.md` 第 3.1 节）。

**明确不引入的能力**：不引入 Flink-Iceberg 连接器。理由是没有"流式写湖"的需求——归档走 Spark 批读已经验证可用，**不为了"看起来完整"而加**（`docs/sprint/SPRINT_5.md` 第 1.1 节）。

**迁移策略是不原地改**：Parquet 外部表保持不动，Iceberg 表用不同的库名建，迁移期逐表对照行数与金额，出问题能立刻退回。理由同样是可回滚：Iceberg 的 `CREATE TABLE ... USING iceberg` 与 Hive 的 `CREATE EXTERNAL TABLE ... STORED AS PARQUET` 是两种表，同名替换会覆盖元数据、且无法回滚（`docs/sprint/SPRINT_5.md` 第 3.2 节）。

**代价**：引入 Iceberg 过程中遇到了一次 Java 字节码版本冲突（详见 5.4 节），最终把版本从任务书中写的 1.11.0 降到 1.10.2。

## 2.4 调度：Airflow

**Executor 选 LocalExecutor**。备选与否决理由：CeleryExecutor 需要 Redis 或 RabbitMQ 做 broker，两者都被技术栈禁令排除；KubernetesExecutor 需要 K8s，同样被排除。本机 4 核、单机部署，LocalExecutor 是唯一不引入新组件又能并发的选择（`docs/sprint/SPRINT_4.md` 第 2.2 节）。

**元数据库用 MySQL 而非 PostgreSQL**。Airflow 官方"首选"是 PostgreSQL，但项目规范明确禁止未经批准引入 PostgreSQL；而 MySQL 8.4 是 Airflow 明确支持的后端，服务器上**已经有**这个 MySQL 8.4.11。为零成本满足需求而引入一个被规范禁止的新组件，是把"技术选型"当成"照抄官方推荐"。结论：用 MySQL，新增独立库 `airflow`（`docs/DECISIONS.md` D2）。

**用独立 venv（`.venv-airflow`）是硬冲突而非洁癖**：Airflow 3.3.2 钉 `fastapi>=0.129,<0.137`，而数据服务用 `0.141.1`。装在一起必然把线上看板的接口依赖降级（`docs/DECISIONS.md` D3）。

**不部署 triggerer**：它只为 deferrable operator 服务，本项目全是短时 shell/Spark 任务。在本机可用内存仅约 2.5 GB 的前提下，少一个常驻进程是实打实的收益。**这是有意的取舍，不是漏装**（`docs/DECISIONS.md` D4）。

## 2.5 大模型应用：Tool Calling、LangGraph、词法检索与 MCP

**模型选 `deepseek-flash`**。理由：本项目上下文很短（口径字典 + 表结构 + 一条 SQL），不需要 pro 档模型；flash 支持 Tool Calls；价格约为 pro 的 1/4.5（`services/agent/README.md` 第 1 节）。

**思考模式默认关闭**，这不是省事的默认值，而是权衡的结果。DeepSeek 官方文档明确写着：携带了 `tools` 参数的请求，在后续所有请求中必须完整回传 `reasoning_content` 给 API，即使该轮模型未实际进行工具调用；若未正确回传，API 会返回 400 报错。对"生成 SQL"这个场景，开启思考模式的代价是 token 成本成倍增加（每轮思维链都要回传）、实现复杂度上升（漏传即报 400）、可复现性下降（同一问题两次可能生成不同 SQL），而收益与代价不成比例。因此默认关闭，并由代码中的 `assistant_message()` 统一负责回传该字段，使调用方不必关心这个细节（`docs/sprint/SPRINT_7.md` 第 4.4 节）。

**用 LangGraph 替换单轮工具调用循环**，原因是单轮循环有三处结构性问题：没有显式的**规划**产物（模型第一轮就可能直接写 SQL，口径查询变成"看心情"，且没有可审查的规划留下）；没有独立的**校验**步骤（查询返回 HTTP 200 就等于"这步过了"，没人检查结果是否为空、分母是否为 0）；**重试**不是一等公民（靠模型自己看到错误文本后"愿意"再试，轮次用尽就强制收尾，无法回答"到底重试了几次、为什么停"）（`docs/sprint/SPRINT_8.md` 第 1 节）。

**检索用 BM25 词法检索而非向量检索**，依据是三条事实：DeepSeek 官方 API 没有 embeddings 端点（官方文档只提供对话补全，`/v1/embeddings` 返回 404）；本机放不下本地 embedding 模型（4 核 / 16 GB，实时链路常驻约 13.7 GB，可用内存约 4.3 GB）；向量库属未批准技术栈。若坚持向量检索，就必须再引入一个外部供应商与 Key，或引入一个跑不动的本地模型，两条路都更差（`docs/sprint/SPRINT_9.md` 第 2.1 节）。

词法检索在本项目**够用**，而不是妥协：语料只有几十篇量级，BM25 的排序质量足够；提问高度依赖关键词（`GMV`、`UV`、`复购率`、`ads_batch_trade_1m`、`payment_success_rate`），这正是 BM25 最擅长的精确词项匹配；命中理由可解释——可以说清"因为命中了 `gmv` 与同义词扩展 `卖了多少钱→GMV`"，而向量相似度给不出这种理由，而本项目的回答本来就要给来源；且零新增基础设施、零新增依赖（`docs/sprint/SPRINT_9.md` 第 2.2 节）。

同期的明确代价与对策也已登记：语义相近但用词不同的提问召回不到，对策是**显式同义词表**（一份可审查、可增删、可测试的配置，而不是藏在代码里的 if-else）；中文没有空格、BM25 的词边界不明，对策是自实现分词（ASCII 词按词边界切分，CJK 连续串切 bigram，不引入 `jieba`）；词法后端将来可能不够用，对策是先抽象接口 `Retriever.retrieve(query) -> docs`，日后换向量后端只替换这一个实现类（`docs/sprint/SPRINT_9.md` 第 2.3 节）。

**MCP 被定位为"同一份只读能力的另一种暴露方式"，而不是第二条取数通道**。这个定位是本项目的一条设计核心：如果 MCP 变成"另一条能取数的路"，那么"不得绕过 sqlguard"这条铁律立刻就被绕过了——因为绕过的方式恰恰是"再实现一遍"（`docs/sprint/SPRINT_10.md` 第 2 节）。

## 2.6 治理：数据质量与可观测性

**数据质量校验做成"清单 + 引擎 + 每条一个标量 SQL"**，而不是一次性脚本。理由是：一次性的校验脚本在演示里能跑，但它不产生持续的可信度——没有人会在每天批处理之后手工敲一遍。真正有价值的形态是"批处理跑完 → 自动校验 → 不合格就让本次运行失败"，这样问题会在**产生的那一次**暴露，而不是在三天后被人发现看板数字不对（`docs/sprint/SPRINT_11.md` 第 1.1 节）。

**监控只做抓取与展示，告警未接入**。这是一个明确的边界，而不是疏漏：Prometheus 只做抓取与展示，没有 Alertmanager / 告警规则；阈值判断刻意留在 `infrastructure/quality/`，因为那里是**可审计的 SQL**，比 YAML 里的表达式更容易讲清楚。若要补告警，优先用 Grafana 的 alerting（数据源已经就绪）（`docs/sprint/SPRINT_11.md` 第 10 节）。

端到端数据流分五段（同文件第 2.2 节）：

```text
2. 实时链路   Kafka → Flink → Doris（DWD/DWS/ADS）→ 秒级指标
3. 离线链路   MySQL/Kafka → Spark → Iceberg（on MinIO）→ Hive 元数据
```

## 4.2 部署分层原则

**数据层继续用 Docker Compose，服务层直接装在宿主机。** 这是本项目贯穿始终的一条设计取舍。

| | 数据层 | 服务层 |
| --- | --- | --- |
| 组件 | MySQL / Kafka / MinIO / Doris / Flink / Spark / Hive Metastore / Prometheus / Grafana | Nginx / FastAPI 数据服务 / 前端静态文件 / 问答 Agent / Airflow / MCP 服务 |
| 部署方式 | Docker Compose | apt + systemd |
| 理由 | 手工安装风险高、依赖多、需要版本绑定；且已用命名卷稳定运行 | 只有几个进程，`journalctl` / `systemctl restart` / `nginx -t` 比容器编排更直接 |

（`docs/DECISIONS.md` D1；`docs/sprint/SPRINT_6.md` 第 2.1 节）

对 Airflow 而言，这一选择还有一条**决定性理由**：Airflow 要调的就是人手工跑的那些脚本。如果 Airflow 跑在容器里，它要完成同样的事就必须挂载 `docker.sock`（等于把宿主机容器控制权交给一个 Web 应用）、把 `scripts/` 与 Spark 客户端挂进容器（路径与用户映射问题），并且容器内调宿主机 docker 的路径与权限差异会使人手工跑与调度跑**行为不一致**。最后一条是根本问题：**调度应该复用人工入口，而不是平行实现一套**。两者行为一旦分叉，就再也说不清"我手工跑是好的，为什么调度跑就错"（`docs/sprint/SPRINT_4.md` 第 3.1 节）。

**代价（如实记录）**：换机器时要多跑几个安装脚本。这些脚本已全部脚本化并保证幂等，但仍是额外的工作量。

## 4.3 数仓分层与命名规范

四层的职责边界如下表，其中"不做"一列是刻意写明的，用于防止层间职责蔓延：

| 层 | 只做 | 不做 |
| --- | --- | --- |
| ODS | 类型归一、落地 | 不做清洗、不做维度补全 |
| DWD | 去重、空值过滤、维度补全、统一命名 | 不做聚合 |
| DWS | 按主题轻度聚合（天粒度） | 不做跨主题加工、不做比率指标 |
| ADS | 按指标口径出数（含比率），对齐实时表结构 | 不做明细查询 |

（`docs/sprint/SPRINT_3.md` 第 3.1 节）

**为什么 DWS 不出比率指标**：比率的分子分母来自不同聚合，放在 DWS 会出现"两个 DWS 表各算一半比例"的口径分裂风险。因此 DWS 只出**可加指标**，比率一律在 ADS 层按 `sql/metadata/metrics.md` 的定义计算（同上）。

命名规范与 SQL 强制要求（`AGENTS.md` 第 5.1、5.3 节）：

```text
库名    小写下划线                ecommerce
表名    小写下划线 + 分层前缀      dwd_trade_order_detail
字段名  小写下划线                order_id / create_time
主键    <实体>_id                 user_id / order_id / payment_id

金额字段统一 DECIMAL(18,2)；比率 DECIMAL(10,4)
时间字段统一 DATETIME，时区 Asia/Shanghai
单 BE 环境建表必须指定 replication_num = 1
所有 DDL 必须存入 sql/ 并提交 Git，禁止手工改容器内数据库
```

## 4.4 存储选型与关键取舍

| 决策点 | 选择 | 否决的备选 | 代价 | 来源 |
| --- | --- | --- | --- | --- |
| 湖仓文件系统 | MinIO（S3A 协议） | HDFS | 与原始设计中"湖仓在 HDFS"的表述不一致，须在报告中说明偏差 | `AGENTS.md` 第 15 节 Sprint 2 行；`docs/DEVELOPMENT_LOG.md` 第 382 行 |

关于 HDFS → S3A 这处偏差需要说明清楚：原设计的湖仓存储是 HDFS，实际改用 MinIO/S3A，原因是**内存不足**（`AGENTS.md` 第 15 节 Sprint 2 行明确标注"HDFS 因内存不足改用 S3A，见 SPRINT_2.md 2.2"）。这是一个被资源条件约束的设计变更，不是实现失败。

关于流量域并入 Sprint 5 的决策，理由记录得很具体：Iceberg 会改变湖仓的存储与表管理方式，先按 Parquet 分层建好、再整体迁到 Iceberg，等于同一件事做两遍，且迁移期间容易出现"两套表并存、口径分叉"；而归档（有源）才是 Sprint 3 记录缺口的实质，那部分 Sprint 4 已经完成（`docs/DECISIONS.md` ⏳6）。

## 4.5 指标口径的唯一权威

`sql/metadata/metrics.md` 是**唯一权威口径定义**。规则是：同一指标在全项目只能有一个定义；实时链路、离线链路与 Agent 都必须引用它，不得自建第二份（该文件开头的规则段）。

落地为三条具体机制：

**其一，空值约定必须两侧一致。** 1 分钟滚动窗口是固定骨架：只要窗口内发生过订单、支付、退款中的任一类事件，该窗口在 `ads_realtime_trade_1m` 中就会有一行。不同业务流的事件时间天然错位（支付发生在下单之后的另一分钟），因此会出现"这一分钟没有支付成功事件"的情况。此处 `payment_cnt` 的语义是"这一分钟没有支付成功事件"，即 **0**，不是"未知"。若置 NULL，看板会显示空白、下游 `SUM()` 会忽略该行，容易被误判为丢数据。因此约定：

| 类别 | 字段 | 无事件时 |
| --- | --- | --- |
| 可加指标 | `gmv` / `order_cnt` / `order_user_cnt` / `payment_cnt` / `payment_amount` / `payment_fail_cnt` / `refund_cnt` / `refund_amount` | `0` |
| 比率指标 | `avg_order_amount` / `payment_success_rate` / `refund_rate` / `click_rate` / `cart_rate` / `buy_rate` | `NULL`（分母为 0） |

**离线链路必须遵循同一约定，否则实时与离线无法对账**（`sql/metadata/metrics.md` 第 2.1 节）。

**其二，三类指标的运算规则必须分清。** 流量域的指标不是同一类东西：`pv` 与 5 个行为计数（`view_cnt` / `click_cnt` / `cart_cnt` / `favorite_cnt` / `buy_cnt`）是**可加**指标（可逐窗口比对，也可跨窗口、跨天直接 SUM 上卷）；`uv` 是**去重**指标（可逐窗口比对，但要天粒度必须回到明细重新去重，**不可以跨窗口相加**——`SUM(uv)` 不是任何有意义的量）；`click_rate` / `cart_rate` / `buy_rate` 是**派生**指标（必须用"合计后的分子 / 合计后的分母"重算，**不可以**对逐窗口比率求平均）（`sql/metadata/metrics.md` 第 3.1 节）。同理，交易域参与对账的 8 个判据列的准确说法是 **"7 个可加指标 + 1 个去重指标"**（`order_user_cnt` 的实现是 `COUNT(DISTINCT user_id)`），**不是"8 个可加指标"**。

**其三，接口层的口径不存第二份。** `/meta/metrics` 接口在运行时解析 `sql/metadata/metrics.md`（按文件 mtime 缓存），文档里表格的"同上"会被还原成真实表名，域（交易/流量/类目）与空值约定一起解析出来。这样做的意义是：口径只有一份，改了文档刷新页面就生效，不存在"文档写的和接口返回的不一致"（`docs/sprint/SPRINT_6.md` 第 3.5 节）。

## 4.6 安全设计

**三道防线**（`docs/sprint/SPRINT_7.md` 第 3.2 节）：

| 防线 | 位置 | 拦住什么 |
| --- | --- | --- |
| ① SQL 守卫 | `services/api/app/sqlguard.py` 的 `validate_select` | 非 SELECT、多语句、注释、DDL/DML、白名单外的表；强制 LIMIT |
| ② 只读账号 | Doris `agent_ro` | 即使守卫被绕过，写操作仍被数据库拒绝 |
| ③ 连接级超时 | `read_timeout = 15s` | 慢查询断开，不拖垮集群 |

**进程边界即权限边界。** Agent 进程里没有数据库凭据，也没有 mysql 客户端依赖。它能做的查询，与"一个人类用户在浏览器里点看板"受**同一道约束**：同一个 `POST /data/api/query`、同一个 `sqlguard` 校验、同一个只读账号 `agent_ro`——因此"Agent 不允许直接拥有数据库管理员权限"由**架构**保证，而不是靠代码自觉。**已实测的四类攻击（DELETE / 未授权表 / 多语句 / 注释注入）均被拒绝且原因正确；在 Agent 进程内未发现绕过路径**（不使用 mysql 客户端、不持有凭据）。需要说明的是：**"不存在任何绕过路径"不是可以穷尽验证的命题**，本文只把进程边界作为**部署约束**陈述；守卫自身的覆盖边界见 §7.3 与 `docs/thesis/FINAL_AUDIT_REPORT.md`。相应地，SQL 安全检查被放在**服务端**而非 Agent 内部：放在 Agent 里等于让被约束者自己当裁判（`docs/sprint/SPRINT_7.md` 第 1.1、2 节）。

**网关契约**：`/data/api/query` 是该服务**唯一接受外部 SQL** 的接口。它用 POST 而非 GET，是**长度**问题而不是语义问题：LLM 生成的 SQL 常带多列与多个聚合，实测轻易超过 2KB；放查询串会撞上各级代理的 URL 长度限制（nginx `large_client_header_buffers` 默认 8KB，中间设备可能更小），表现为"简单问题能问、复杂问题 502"这种最难定位的故障。Nginx 侧为该路径单独开精确匹配的 location 并只放行 POST；其余路径仍是 `limit_except GET HEAD OPTIONS { deny all; }`（`docs/sprint/SPRINT_7.md` 第 3.4 节）。

**为什么返回 `executed_sql`**：守卫会**改写**语句（补上或收敛 LIMIT）。返回**实际执行的那一条**，才能满足"Agent 不得伪造查询结果"——"我查了这句话"必须可核对，而不是靠调用方自述。血缘表名同样由服务端提取（`sqlguard.extract_tables()` 与校验**共用同一套正则**），如果让调用方自报读了哪些表，血缘字段就失去可信度（`docs/sprint/SPRINT_7.md` 第 3.3、3.5 节）。

**端口纪律**：数据服务 `127.0.0.1:8000`、问答 Agent `127.0.0.1:8100`、MCP 服务 `127.0.0.1:8200` 均只绑回环，只应由 Nginx 反代访问。直接暴露到公网既绕过 Nginx 的方法限制，也让"Agent 进程无数据库凭据、只能经只读服务取数"这道进程边界失去意义（`README.md` 第 7.3 节；`docs/sprint/SPRINT_10.md` 第 7 节）。

## 4.7 内存预算与错峰模式

这是本项目的**最硬约束**，也是"16 GB 单机同时跑实时与离线"这一目标的全部难度所在。

实时链路常驻约 13.7 GB；离线 Spark 批处理的驱动跑在**宿主机**上（client 模式），加执行器合计约 1.5 GB。直接叠加会打穿内存——**实测导致整机失联**（事故详情见 5.11 节的前置事故与 `docs/sprint/SPRINT_3.md` 第 8.1 节）。

因此离线批处理采用**错峰执行**：

```text
scripts/batch-mode.sh
  1) 暂停 Flink 栈（jobmanager / taskmanager / sql-gateway / jobs）
  2) 内存闸门检查（可用 < 3000 MB 直接拒绝启动）
  3) 跑离线流水线
  4) 恢复 Flink 栈并跑 health-check.sh 验证实时链路回到健康
```

（`docs/sprint/SPRINT_3.md` 第 4.4 节）

暂停期间事件继续堆在 Kafka，Flink 从已提交位点继续消费，重复部分由 Doris UNIQUE KEY 幂等覆盖——**不丢数据**，代价只是"暂停期间的实时曲线会延后追上"（同上）。

关于闸门阈值的一个决策需要记录：实测暂停实时链路可释放约 1.65 GB（2282 → 3935 MB）。项目没有因为闸门经常拦人而调低它，理由是**调低闸门是把保护拆掉，错峰才是正解**（`docs/DECISIONS.md` D11）。

四层防护是从"事前拒绝"到"事后兜底"（`docs/sprint/SPRINT_3.md` 第 8.1 节）：

| 层 | 措施 | 文件 |
| --- | --- | --- |
| 1 拒绝启动 | 可用内存 < 3000 MB 直接拒绝跑批；已有 Spark 作业时拒绝叠加 | `scripts/lib/memory-guard.sh` |
| 2 错峰执行 | 跑批前暂停 Flink 栈，跑完自动恢复并验证健康 | `scripts/batch-mode.sh` |
| 3 限制上限 | 驱动/执行器各 768m；`spark-submit` 容器补 `mem_limit` | `scripts/lib/spark-job.sh`、`docker-compose.yml` |
| 4 兜底 | 4 GB swap（swappiness=10）；**故意不写 fstab**，因为 Doris BE 不允许在有 swap 的机器上启动 | `scripts/setup-swap.sh` |

## 5.1 实时链路：Kafka → Flink → Doris

实时链路包含 8 个 Flink sink 作业（4 个 DWD 清洗作业 + 4 个指标聚合作业），每个作业 1 个实例；下游是 8 个 Doris Routine Load 作业，全部 RUNNING 且 `errorRows = 0`（`docs/sprint/SPRINT_1_VERIFICATION_STATUS.md` 第 2 节）。

落库结果与源端逐层一致：

| 层 | 对象 | 实测值 | 与上游一致 |
| --- | --- | --- | --- |
| 源 | Kafka `order_event` | 6000 条 | = MySQL `orders` 行数 |
| 源 | Kafka `payment_event` | 5406 条 | = MySQL `payment` 行数 |
| 源 | Kafka `refund_event` | 254 条 | = MySQL `refund` 行数 |
| 源 | Kafka `behavior_event` | 20000 条 | 生成器上报条数；Kafka 侧累计位点合计亦为 20000（0:6506 + 1:6592 + 2:6902） |
| DWD | `dwd_trade_order_detail` | 6000 行 | 与源 topic 一致 |
| DWD | `dwd_trade_payment_detail` | 5406 行 | 一致 |
| DWD | `dwd_trade_refund_detail` | 254 行 | 一致 |
| DWD | `dwd_traffic_behavior_detail` | 20000 行 | **行数 = `distinct event_id` 的基数**（`COUNT(DISTINCT event_id)` 同为 20000），**不等于链路处理量** —— 见下方"29 倍重放"注 |
| DWS | `dws_traffic_overview_1m` | 19644 行（窗口） | PV 合计 20000 |
| ADS | `ads_realtime_trade_1m` | 11459 行（窗口） | 见 5.3 节 |
| ADS | `ads_realtime_traffic_1m` | 19644 行（窗口） | PV 合计 20000 |
| ADS | `ads_realtime_category_1m` | 5998 行（窗口 × 类目） | 订单 6000 / GMV 一致 |

（`docs/sprint/SPRINT_1_VERIFICATION_STATUS.md` 第 2 节）

一个容易被误读的数字需要说明：ADS/DWS 的 Routine Load `loadedRows` 大于窗口数属于正常现象——`upsert-kafka` 对同一窗口会写多条更新消息（窗口未最终触发前的中间态），Doris 侧按 `UNIQUE KEY(window_start)` 收敛为最新值；另有少量**墓碑消息**（value = null，实测 29475 条消息中 25 条），Doris 直接跳过，不计入错误行（同上）。

> **⚠️ "行数 = distinct `event_id` 基数"，不是"链路处理量"（答辩必问）。**
> 上表的实时 DWD 行数是 **Doris 表内按主键去重后的行数**。链路实际处理量要大得多：
> Kafka 侧 `dwd_traffic_behavior_detail` topic 的 `latest` 位点合计 = **580000 = 29 × 20000**
> （即 Flink 作业被重放 29 轮）；交易域同理约 29 倍
> （订单 `174000 = 29 × 6000`、支付 `156774 = 29 × 5406`、退款 `7366 = 29 × 254`）。
> Doris 侧 `SHOW ROUTINE LOAD` 的 `loadedRows` 与上述逐项吻合（行为表 580000、`errorRows = 0`），
> 而表内 `COUNT(*)` 仍是 20000 / 6000 / 5406 / 254 —— 机制是 Doris 侧为
> `UNIQUE KEY(...)` + `enable_unique_key_merge_on_write = true`，**重复主键被 upsert 覆盖**。
> 因此：**可以**说"实时 DWD 与源端在**去重后的行数**上一致"；
> **不可以**说"实时链路只处理了 20000 条事件"，也不可以把 `event_id` 当作全局唯一键
> （实测存在两代编号 `40001–49999` 与 `410000–420000`，`evt_420000` 是**生成器进程内序号**，
> **不等于** 42 万条消息）。完整的只读取证见 `docs/thesis/FINAL_AUDIT_REPORT.md` §1.3/§7 与
> `docs/thesis/EVIDENCE_MATRIX.md`。

**本链路一次真实故障与修复。** 指标一度翻倍：PV 合计 39987，而事件只有 20000。根因是 SQL Gateway 为 session 模式，**重启 `flink-jobs` 容器不会取消旧作业**，旧作业把重放的事件累加到了旧的窗口状态里。修法是新增 `scripts/cancel-flink-jobs.sh` 并在提交脚本启动时自动清场，同时在健康检查中增加"Flink 作业唯一性"检查项（`docs/sprint/SPRINT_1_VERIFICATION_STATUS.md` 第 5 节）。

同一节还记录了一次类目作业提交失败：Flink 写入按位置对齐，SELECT 的列顺序（`window_start, window_end, category_name, …`）与 sink / Doris 表的列顺序（`window_start, category_name, window_end, …`，因为 UNIQUE KEY 必须是有序前缀）不一致。这条错误的特征是"作业提交失败但报错不指向列顺序"，属于必须靠人工比对两边列清单才能发现的类型。

> **其二：`dws_trade_user_1d` 是 5851 还是 5883？** 同样两个来源、两个数：`docs/sprint/SPRINT_3.md` 第 7.1 节记 **5851**，`docs/sprint/SPRINT_5.md` 第 2.3 节（迁移对照基准）与第 8.1 节（迁移后逐表行数）记 **5883**。后者是**较晚的观测**且在两个不同小节里一致出现，因此本文在 5.4 节引用 Iceberg 迁移结果时采用 **5883**；而 5.2 节的行数表按原文保留 5851 并在此标注差异。**这两个数不参与任何对账判据**（交易域对账判据是 `ads_realtime_trade_1m` 与 `ads_batch_trade_1m` 的 5 项指标），因此不影响核心结论。
>
> 处理原则与 Iceberg 的 `60/60` 与 `70/70` 一致：**同名不同范围的数字，保留各自出处并写明范围，不合并、不取平均值、不为"看起来一致"而丢掉一次真实验收。**

**事件口径映射是本层最容易出错的地方。** 实时链路的指标算在 **Kafka 事件**上，离线链路的指标算在 **MySQL 业务行**上。两张表要能对账，必须先证明事件与业务行一一对应：

| 实时事件（Kafka） | 计数口径 | 离线等价来源（MySQL / ODS） | 映射规则 |
| --- | --- | --- | --- |
| `ORDER_CREATED` | 1 事件 = 1 订单 | `orders` 表 1 行 | `event_time = orders.create_time` |
| `PAYMENT_SUCCESS` | 成功支付 | `payment` 行且 `pay_time IS NOT NULL` | `event_time = payment.pay_time` |
| `PAYMENT_FAILED` | 失败支付 | `payment` 行且 `pay_time IS NULL` | `event_time` 为支付尝试时间（见下） |
| `REFUND_CREATED` | 1 事件 = 1 退款 | `refund` 表 1 行 | `event_time = refund.refund_time` |

（`docs/sprint/SPRINT_3.md` 第 3.2 节）

其中 `PAYMENT_FAILED` 的 `event_time` 在业务表里**没有独立字段**（MySQL 只有 `pay_time`，失败则为空）。项目明确规定：**不允许**用 `create_time` 冒充支付尝试时间，否则对账必然错位（同上）。

**为什么用 PySpark 脚本 + `spark.sql()` 而不是纯 `.sql` 文件**：需要在作业内做**自校验**（每层跑完立即断言行数关系，不一致就以非 0 退出）。纯 SQL 交给 `spark-sql -f` 跑就只能"跑完不报错"，无法回答"算得对不对"（`docs/sprint/SPRINT_3.md` 第 4.1 节）。

**离线结果如何进 Doris**：用 Doris 的 `S3()` 表函数直读 Parquet，不用 Stream Load、不用外部 loader。理由是 Stream Load 要求把文件推到 BE 的 HTTP 端口，就得再起一个"读 S3 → POST"的 loader 进程（多一个要维护、要监控、可能挂掉的东西）；TVF 一条 SQL 解决，不引入任何新组件、新端口、新进程（`docs/sprint/SPRINT_3.md` 第 4.2 节）。

| 退款笔数 / 金额 | 254 / 1,825,511.73 | 254 / 1,825,511.73 | 0 / **0.00** |

（`docs/sprint/SPRINT_3.md` 第 7.2 节）

两个引擎、两套计算框架、两条独立链路，同一个数。这一结论后来在 Airflow 编排下被独立复现（`docs/sprint/SPRINT_4.md` 第 10.1 节：`[scope] 对账窗口 11458 个，一致 11458 个，不一致 0 个`）。

### 5.3.2 判据的两次打磨

**判据不是一次写对的。** 记录这两次打磨，是因为它们反映了对账工作的实际难点：难的不是算，而是**先确认判据本身在说什么**。

**第一次打磨：离线表多一个分区列。**

`traffic-ads` 自检 34/35，唯一失败项是"字段顺序与实时表一致"。表面看像是离线表结构写错了。实际根因是：`describe_columns` 读的是 `DESCRIBE` 的输出，而 **`DESCRIBE` 会把分区列一并列出**（`dt` 在最后）。实时表没有分区列，于是 12 个数据列被拿去和 13 列（12 + `dt`）比较——**断言写错，不是数据错**，数据顺序完全正确。

修法是把判据改为"数据列逐列同序 **+ 分区列 `dt` 只在最后**"，并补一条"除 `dt` 外无多余字段"的反向守卫（`docs/sprint/SPRINT_5.md` 第 9.4 节第 1 条）。

**第二次打磨：比率列按各自计数重算。**

流量域对账的原始判据是"两侧比率相等"。实际采用的是一个**更强**的独立判据：

> 每一侧的比率 == 由该侧**自己的**计数按 `metrics.md` 公式重算。

改动方向是**变严而不是变松**，理由有两条：其一，"两侧比率相等"既不增加信息（判据列相等时比率在数学上必然相等），又会被两侧除法实现细节的末位差异误报；其二，新判据不需要两侧一致就能判定**谁错**，而且两侧一起错成同一个值它照样能抓出来（`docs/sprint/SPRINT_5.md` 第 9.2 节第 2 条）。

**这两次打磨的共同教训**：断言失败时，第一件事是确认"这条断言在说什么"，而不是先怀疑数据。项目里同一类问题出现过多次：`COUNT(DISTINCT)` 是近似算法不能拿来做相等断言（`docs/sprint/SPRINT_3.md` 第 8.3 节）；`SUM(1d.order_user_cnt) == DWD 全局去重` 这条断言本身就是错的，因为去重计数不可加（同文件第 8.4 节）；`awk '$1=="amount"` 取不到类型、Sprint 4 的"自检在空表上全绿"（`docs/sprint/SPRINT_5.md` 第 9.4 节末）。**断言写错比没有断言更危险：它会把人引向"数据错了"的错误结论，浪费时间去查一个并不存在的问题。**

### 5.3.3 流量域对账与口径陷阱

流量域对账的实测输出：

```text
[jdbc]   ads_realtime_traffic_1m → 19644 行
[lake]   ads_traffic_1m          → 19644 行
[scope]  对账区间 [2024-10-02 21:53:00 , 2026-09-26 13:14:00)
[scope]  对账窗口 19643 个（实时侧 19643 个），一致 19643 个，不一致 0 个
[scope]  单边窗口：仅实时 0 个，仅离线 0 个
[scope]  PV 合计：实时 19998 vs 离线 19998
[scope]  窗口 UV 范围：实时 [1, 3] vs 离线 [1, 3]
[check] ===== 10/10 通过 =====
```

（`docs/sprint/SPRINT_5.md` 第 9.2 节）

实时侧 19644 个窗口、离线侧 19644 个窗口，区间尾部按惯例留 3 分钟安全边界，因此逐窗口比对覆盖 19643 个窗口。判据的构成与交易域有三处实质差别：

| # | 差别 | 做法 |
| --- | --- | --- |
| 1 | 判据含**去重**指标 | `uv` 逐窗口比对成立；全程**不做任何 `uv` 上卷**（`SUM(uv)` 不是有意义的量） |
| 2 | 比率列不参与主判据 | 换成更强的独立判据："每一侧的比率 == 由该侧自己的计数按 `metrics.md` 公式重算" |
| 3 | 单边窗口单独统计 | 汇总表记录 `realtime_only_windows` / `batch_only_windows`，使"差异为 0"有边界可核 |

（`docs/sprint/SPRINT_5.md` 第 9.2 节）

**支撑"三类指标不可混用"这条规则的实测证据，本身就很说明问题**：

```text
SUM(19644 个窗口的 uv) = 19999        ← 逐窗口去重的基数
全部 20000 个事件的去重用户数 = 1200   ← 人的基数
```

两者相差约 16 倍，但**都正确**——它们是两个不同的定义。若把"天 UV"写成 `SUM(分钟 uv)`，会系统性偏大且看起来仍然合理（19999 < 20000 的 PV，不会有人怀疑），属于最难发现的口径错误（`sql/metadata/metrics.md` 第 3.1 节；`docs/sprint/SPRINT_5.md` 第 9.1 节）。

第二个数已用精确算法复核：`SIZE(COLLECT_SET(user_id))` = 1200、`COUNT(DISTINCT user_id)` = 1200（Parquet 侧与 Iceberg 侧一致）。**顺带一条教训**：项目文档里一度把这个数写成 **1199**——那是一次早期估算的残留，**从未被真正测量过**，却因为"看起来像个真实数字"而在多处被引用。**写入文档的数字必须能指回一条可复现的命令**（`sql/metadata/metrics.md` 第 3.1 节）。

### 5.3.4 一处未归零的发现

流量域对账留下了**唯一一个没有归零的数字**，如实记录如下。

```text
window_start = 2026-03-21 19:23:00
实时 ecommerce.ads_realtime_traffic_1m：
    uv=3 pv=3 view_cnt=2 click_cnt=1 cart_cnt=0 favorite_cnt=0 buy_cnt=0
    click_rate = 0.0000        ← 按 metrics.md 第 3 节公式 1/2 应为 0.5000
离线 iceberg.lakehouse_iceberg.ads_traffic_1m：
    uv=3 pv=3 view_cnt=2 click_cnt=1 cart_cnt=0 favorite_cnt=0 buy_cnt=0
    click_rate = 0.5000        ← 正确
```

（`docs/sprint/SPRINT_5.md` 第 9.3 节；`sql/metadata/metrics.md` 第 3.3 节）

**判定过程是"先定因，再定判据"，共五步**：

```text
第 1 步 打印双方原值      实时 0.0000 vs 离线 0.5000，差值 0.5000
第 2 步 看差值的量级      差在小数点后第一位，不是末位
                          → 不是浮点/舍入口径差异，排除"加容差"这条路
第 3 步 用第三方判据定责  1/2 = 0.5 是纯算术，无需比较两侧
                          离线侧 0 个矛盾窗口，实时侧 1 个
                          → 差异不在"两侧算法不同"，在实时侧那一行自相矛盾
第 4 步 找旁证            实时侧 click_rate 全表取值只有 {0.0000, NULL, 1.0000}；
                          全表满足 0 < click_cnt < view_cnt 的分数窗口恰好只有这 1 个
                          → 目前数据只有一个分数样本，而它就是错的
                            （分子为 0 或分子 = 分母的窗口无法暴露截断）
第 5 步 对照回归          交易域同一判据：11459 个窗口 0 个矛盾
                          （avg_order_amount / payment_success_rate 都正常）
```

（`docs/sprint/SPRINT_5.md` 第 9.3 节）

**影响范围已量化**：7 个对账判据列（`uv` / `pv` / 5 个行为计数）在全部 19643 个窗口逐窗口一致，因此该缺陷**不影响任何已发布的指标口径**，只影响实时侧 `click_rate` 这一个派生列的一行。**判据定性**：可加/去重计数类指标是**硬一致性判据**（进 `is_match`、进 `is_pass`）；比率列是**派生指标**，只作**诊断性异常登记**（diagnostic anomaly）、**不参与 `is_pass`** —— 因此该异常**不阻断对账作业的退出码**（作业只对**离线侧** anomaly 做硬断言）。这不等于隐藏：异常窗口数已落进汇总表与逐窗口列，可随时复核。

**为什么选择不修复**：缺陷在实时链路（Flink 作业 → Doris）。修它需要改并重部署 Flink 作业，而 `behavior_event` 的全部 20000 条消息**仍在 Kafka 里**（earliest = 0），重部署会把它们**从 earliest 重放一遍**，覆盖实时侧全部 19644 个窗口。那是实时链路的一次全量重建，风险与收益不成比例。项目在这个问题上给出了 A/B/C 三个方案并选择 C（记录并暂不处理），该选择经项目负责人复核后**维持不变**（`docs/sprint/SPRINT_5.md` 第 10 节；`docs/DECISIONS.md` ⏳10）。其中方案 B（只改 SQL 不重部署）被明确否决，理由是"会造成仓库代码与运行作业不一致，比不改更危险"。

**这一项的定性必须说准**：它是**"已定位、已用第三方判据定责、判据已改严、证据已落盘、经成本评估后决定不修"**的真实缺陷，**不是**"未解决"，也**不是**"环境问题"。

**处置方式上有一条值得单独强调**：判据**改严**而**不是加容差**。矛盾窗口数作为一等结论落盘（`ads_reconcile_traffic_summary.realtime_rate_anomaly_windows = 1`），逐窗口标记 `ads_reconcile_traffic_1m.realtime_rate_anomaly`；作业与验收脚本都单独打印它，并明确标注"缺陷在实时链路"。**没有为了让数字变 0 而给比率加容差，也没有把它从证据里删掉**（`docs/sprint/SPRINT_5.md` 第 9.3 节）。

需要如实说明的一点：**`70/70` 这一侧没有逐项细目**——`AGENTS.md` 只记了总数，`SPRINT_5.md` 未记录这次复跑的明细。按 23 张表与同一套判据推算，`70 = 23（Provider） + 23（行数） + 金额列合计 + 1（库表数）`，即该次运行的金额列合计项为 23；但这属于**按判据构成的推算，不是文档中的原始记录**，故本文只把它当作口径解释，不当作实测细目引用。**两个数字都保留、各自按自己的范围标注：删掉其中一个等于丢掉一次真实验收。**

逐表行数与 Parquet 侧（迁移前基线）**未发现差异**（范围：**迁移清单内的 18 / 23 张表**；判据是 `COUNT(*)` 精确相等，**不是**逐行或全字段比对），含金额 SUM 核对（同上）。**行数相同不代表内容没坏**（截断或转型出错时行数照样相等），因此每张含金额的表都额外做了 `SUM(金额) 源 == 目标` 的核对——金额是最敏感的探针（同上）；但该核对是**整表合计**，且只覆盖 6 个金额列名（`gmv`/`amount`/`payment_amount`/`refund_amount`/`avg_order_amount`/`total_amount`），**不能**据此声称"逐行一致"或"所有字段一致"（未验证维度见 `docs/thesis/FINAL_AUDIT_REPORT.md` §C-15 与 `EVIDENCE_MATRIX.md`）。

### 5.4.2 三段名与 catalog 命名陷阱

迁移过程中挖出三个缺陷，全都不是环境问题，而是**设计与认知问题**（`docs/sprint/SPRINT_5.md` 第 8.2 节）：

**陷阱一：库名与 catalog 同名，"建库"这句话就没有唯一含义。**

现象：`CREATE DATABASE` 报 `Cannot create namespace with invalid name:`，**冒号后是空的**。

根因：该一段名与已注册 catalog **同名**。Spark 解析一段名时会先把它当目录名，于是解析成"目录 + 空命名空间"。修法是 catalog 改名 `iceberg`，库名 `lakehouse_iceberg` 保持不变（HiveCatalog 的命名空间就是 Hive 库名，库名没有错、不用改）（`docs/DECISIONS.md` D13）。

**陷阱二："改完没生效"可能是因为文件根本没进运行环境。**

现象：catalog 改名后**报错一字不差**，像没改过。

根因：`spark-defaults.conf` 是 Dockerfile **构建期 `COPY`** 进镜像的，而 `spark-submit` 是 `docker compose run` 的临时容器，只挂了 `jobs` 与 `sql`。结果是**改了 conf 等于没改，且没有任何提示**。修法是把 conf 挂进 spark-submit，与 jobs/sql 一样"改完即生效"（`docs/DECISIONS.md` D14）。

**陷阱三：两段名永远属于当前目录。**

现象：表建出来了，但可能建在**另一个目录的同名库**里。

根因：Spark 的**两段名 = (命名空间, 表)，永远属于当前目录**，不会因为名字看起来像就跳到 Iceberg 目录——只写两段名会静默落到别处，**而行数核对读的也是同一个错地方**（这一点尤其危险：核对与被核对的对象一起错，两边都"一致"）。

修法：源表写 `spark_catalog.lakehouse.*`、目标表写 `iceberg.lakehouse_iceberg.*`，**全程三段名**（`docs/DECISIONS.md` D13；`docs/sprint/SPRINT_5.md` 第 8.2 节第 3 条）。

### 5.4.3 分区写入器 OOM 的结构性修复

**现象**：执行器连续 `OutOfMemoryError`，4 次 `Lost executor ... code 52`，最后报 `MetadataFetchFailedException`。

**根因**：703 个 `dt` 分区 vs 默认 200 个 shuffle 分区，**AQE 又把小分区合并**回去 → 少数 task 各持有几百个分区写入器。数据才 2 万行，**与数据量无关**。

**修法（结构性修复）**：分区表 `INSERT` 加 `DISTRIBUTE BY 分区列` + `spark.sql.shuffle.partitions` 提高到 1000 + 关掉 AQE 合并，使一个 task 约等于一个分区。

**明确不采用的方案**：把执行器内存调大。理由是 OOM 的根因是"一个 task 同时持有的分区写入器个数"，这是结构问题；调大内存只是掩盖症状，分区数一涨还会复发（`docs/DECISIONS.md` D15；`docs/sprint/SPRINT_5.md` 第 8.2 节第 4 条）。

### 5.4.4 与任务书的偏差（必须记录）

三处偏差全部有据可查（`docs/sprint/SPRINT_5.md` 第 8.4 节）：

1. **Iceberg 版本 1.11.0 → 1.10.2。** 1.11.0 的 class 文件是 major 61（Java 17），而 Spark 镜像的 JRE 是 Java 11（只认到 55），实测报 `UnsupportedClassVersionError`。任务书里曾写"JDK 11 在 Iceberg 1.11 支持的 8/11/17/21 之内"——这是**错的**：**"官方支持在 Java 11 上运行"与"其发布的字节码要求 Java 17"是两件不同的事**，前者是兼容性声明，后者是构建目标。作者在记录中把这条定性为"这正是'不猜版本'要防的那类错误，只不过这次猜的是'支持范围'而不是版本号"（同文件第 2.3.1 节）。
2. **catalog 名 `lakehouse_iceberg` → `iceberg`**：见 5.4.2 陷阱一。
3. **DDL 不落盘 `sql/iceberg/`，改为从源表 schema 推导**：手写 18 张表的 DDL 会与源表定义分叉，而分叉只有在迁移之后才会被发现；schema 推导保证"两边定义同源"，且 `CREATE TABLE` 语句会打印出来可逐条核对。

### 5.4.5 一个诊断方法上的教训

排查"迁移进程是不是还活着"时，作者用了 `pgrep -c batch-mode`，得到 0，据此判断"进程死了"，还怀疑过 OOM、怀疑过 ssh 超时把进程带走——**两次结论都是错的**。

`pgrep -c <pattern>` 默认匹配的是**进程名**，而 `bash scripts/batch-mode.sh` 的进程名是 `bash`，因此它会稳定地返回 0。必须写 `pgrep -af <pattern>`（`-f` 才匹配完整命令行）。真相是作业一直在跑，只是 `[verify]` 阶段的 checker 最后才统一输出，中间十几分钟没有任何日志——**"没有输出"被当成了"已经死掉"**（`docs/sprint/SPRINT_5.md` 第 8.3 节；`docs/DECISIONS.md` 第四节）。

这是同一类错误的第三次出现：Sprint 4 是"命令返回成功 ≠ 目标状态正确"，这次是"命令返回 0 条 ≠ 进程不存在"。**任何观测手段都要先确认它在测什么。**

## 5.5 调度：Airflow

DAG `offline_lakehouse_pipeline` 的任务图（`docs/sprint/SPRINT_4.md` 第 5.1 节）：

```text
pause_realtime → [ ods_extract ‖ archive_behavior ] → dwd_layers → dws_layers
              → ads_layers → reconcile → load_to_doris → restore_realtime
```

设计要点：

1. **每个 stage 是独立 Airflow 任务**，而不是把 `batch-mode.sh` 整个塞进一个任务。理由：Airflow 的价值就在于**每层的可见性、独立重试与失败定位**；塞成一个任务的话，Airflow 只是个定时器，退化成 cron。
2. **`ods_extract` 与 `archive_behavior` 并行**（数据源不同，MySQL vs Kafka，无依赖），但两者都必须在 `pause_realtime` 之后（内存闸门）。
3. **`restore_realtime` 用 `trigger_rule=all_done`**：无论中间哪一步失败都必须恢复实时链路——否则一次失败的批处理会让看板一直停在那里，这比批处理失败本身严重得多。
4. **恢复后自检**：调用 `scripts/health-check.sh`，它的退出码就是任务结果。
5. **`max_active_runs=1`**：不允许两次批处理重叠（重叠必然打穿内存）。

**调度时间选每天 03:00**，因为批处理期间实时链路是暂停的（看板曲线会延后追上），选在使用者最少的时间窗把"暂停"的影响降到最低（同文件第 5.2 节）。

实测结果（`AGENTS.md` 第 15.8 节；`docs/sprint/SPRINT_4.md` 第 10.1 节）：

```text
✅ verify-sprint-4.sh   通过 40 / 失败 0 / 跳过 0（8 步）
✅ Airflow 3.3.2        宿主机 systemd 三单元
     apiserver(180MB) / scheduler(175MB) / dagprocessor(125MB)

✅ 元数据库用 MySQL      专用账号 airflow：对 ecommerce 被拒绝（最小权限实证）

```

**六条硬规范**（都是实测教训，`AGENTS.md` 第 15.8 节）：

> 1. **调度必须复用人工入口**。DAG 的每个 stage 都调 `run-batch-pipeline.sh --stage X`，闸门（内存 / 不叠加作业）都在脚本里。这样"手工跑"与"调度跑"受**同一套**约束，不存在两条路径行为不一致。
> 2. **重试与超时必须显式写在算子上**。Airflow 3.3.2 里 `@dag(default_args={...})` 的 `retries` / `execution_timeout` **不生效**——实测会导致 DAG run **永久卡死**（状态停在 `up_for_retry` 却已无重试次数），而恢复任务依赖它，于是实时链路一直停着。
> 3. **暂停与恢复必须是两个独立任务**，恢复用 `trigger_rule=all_done`。
> 4. **切换站点协议（`SITE_SCHEME`）后必须重跑 `deploy-airflow.sh`**，否则 `api.base_url` 残留旧协议，任务执行回调会静默失效。
> 5. **人工敲 airflow 命令一律用 `scripts/airflow.sh`**，不要用裸 `airflow`——裸命令不加载 `airflow.env`，会静默落到 sqlite 并报"需要迁移"（极具误导性）。
> 6. **不要覆盖正在运行的 shell 脚本**（bash 边读边执行），**也不要在 DAG run 进行中改 DAG 文件**（新任务会被注入到该 run 里）。

第 6 条有两次实测支撑：一次是**对账已经成功**（11458 窗口零差异），却因为在它运行期间覆盖了 `run-batch-pipeline.sh` 而被判失败——一个纯粹的假故障；一次是 `archive_behavior` 因 DAG 文件在 run 进行中被修改而提前执行，当时服务器上的脚本还是旧版，报"未知阶段"（`docs/DECISIONS.md` 第四节）。

**归档阶段排掉的六层障碍**（`docs/sprint/SPRINT_4.md` 第 10.2 节），其中**三层属于同一类**：

| 层 | 障碍 | 根因 |
| --- | --- | --- |
| 1 | 阶段静默空转、0.6 秒报成功 | 漏加 `case` 分支 + 无兜底 |
| 2 | `Failed to find data source: kafka` | 官方 Spark 镜像不带 Kafka 连接器 |
| 3 | "构建成功"却没变化 | Dockerfile 改在了会被同步覆盖的副本 |
| 4 | `ClassNotFoundException`（executor 侧） | **重建镜像 ≠ 容器换镜像** |
| 5 | 读到 20000 却写 0 行 | 格式串里的 `T` 非法 → `event_time` 全 NULL → 被过滤 |
| 6 | 自检全绿但表是空的 | 空值断言打在空的目标表上，**空洞地通过** |

> **六层里有三层属于同一类：「成功信号」不可信。** 命令返回成功、构建报成功、自检全绿，都不能替代**回到目标状态去验证**（表里到底有多少行、镜像里到底有没有那个 jar）。

## 5.6 服务层：只读数据服务与看板

**接口清单**（全部 GET，前缀 `/data/api`，来源 `docs/sprint/SPRINT_6.md` 第 3.2 节）：`/health`、`/overview`、`/metrics/trade`、`/metrics/traffic`、`/metrics/category`、`/funnel`、`/orders`、`/orders/{order_id}`、`/meta/metrics`、`/meta/tables`、`/categories`，外加 Sprint 7 新增的 `POST /query`。

**统一响应信封**（同文件第 3.3 节）：

```json
{
  "data":  { "...": "业务数据" },
  "source": {
    "tables": ["ecommerce.ads_realtime_trade_1m"],
    "metric_definitions": [{ "metric": "GMV", "field": "gmv", "formula": "...", "null_policy": "无事件补 0" }],
    "time_range": { "start": "2024-10-25 08:16:00", "end": "2026-09-26 11:37:00" },
    "note": "全量口径：对所有 1 分钟窗口求和"
  },
  "generated_at": "2026-09-26T13:51:51+08:00"
}
```

**为什么每个响应都要带 `source`**：这是"Agent 的最终回答必须能够说明数据来源"在接口层的落地——前端把它显示在每页底部，Agent 直接复用它组织回答，不需要另建一套血缘数据（同上）。

**前端无构建步骤**：Vue 3.5.13 全局构建 + 浏览器内模板，ECharts 5.6.0 本地 vendor，不引用外部 CDN，不使用 npm / Vite / webpack。理由：本项目只有 6 个页面、无第三方业务依赖，引入构建链会带来"服务器要装 Node、产物要单独发布、版本要锁"的额外成本；而 Vue 的全局构建已经足够，而且**源码即产物**，排查问题时看到的就是运行时的代码。代价：vendor 文件需联网下载一次（`docs/sprint/SPRINT_6.md` 第 4.1 节；`AGENTS.md` 第 3 章目录表已注明 `vendor/` 不入 Git）。

**两个与口径一致的前端约定**（`docs/sprint/SPRINT_6.md` 第 4.3 节）：金额按字符串处理（后端返回 `"51890375.77"`，前端展示补零加千分位，跨行累加先转整数分（`BigInt`）再算，**绝不用浮点累加**）；`null` 显示为 `—` 而不是 0（比率类指标分母为 0 时后端返回 `null`；可加指标后端已补 0，正常显示 `0.00`）。

**一次真实缺陷**：前端把绝对路径当相对前缀，拼出了 `/data/api/api/...`，整站所有请求 404——表现为看板全页报错，看起来像后端挂了。根因是 `<meta name="api-base" content="/data/api">` 给的是**绝对路径**，重构时把它当成"相对前缀"又拼了一次 `/api`。修法是显式定义 `API_BASE` 与 `AGENT_BASE` 两个完整基址，`buildUrl(base, path, params)` 只拼一次，并在注释里写明"绝不能再叠前缀"（`docs/sprint/SPRINT_7.md` 第 9.3 节）。

**接口无鉴权**是本层的一条已知限制：知道 IP 就能读指标（只读，不能改数据）（`docs/DECISIONS.md` 第三节第 1 条）。

## 5.7 Agent 图：检索 → 规划 → 取数 → 校验 → 反思 → 汇总

实际落地的图（`docs/sprint/SPRINT_8.md` 第 9.3 节）：

```text
retrieve → plan ─┬─(规划成功)→ execute → validate ─┬─(有阻塞性问题且还有额度)→ reflect → plan
                 └─(规划失败)→ summarize            └─(通过/额度用尽/超时)→ summarize → END
```

节点/边/上界都经 `GET /graph` 对外可读（实测返回 6 节点、8 条边、三重上界）。

**为什么 `reflect` 之后回到 `plan` 而不是 `execute`**：错误信息（"表未授权"）通常意味着**计划本身错了**（选错了表），而不是"同一条 SQL 再跑一遍就会好"。回到 `plan` 才能真正改变做法；回到 `execute` 只会把同一条错 SQL 重放一次——**那是重试，不是重新规划**（`docs/sprint/SPRINT_8.md` 第 3.1 节）。

**终止性（三重上界）**：`retries` 达到 `AGENT_MAX_RETRIES`（默认 2）即不再反思；工具调用总轮次达到 `AGENT_MAX_TOOL_ROUNDS`（默认 6）即强制收尾；总耗时达到 `AGENT_TOTAL_TIMEOUT`（默认 120s）即强制收尾。**收尾调用不携带 `tools`**——否则模型还能继续发起调用，图停不下来（同文件第 3.3 节）。

**与 Sprint 7 的关系是复用而不是重写**：4 个工具与 `ToolBox` 原样复用（工具集合是安全边界，不因换编排而变）；`llm.py` 的三个函数原样复用；`sqlguard` 守卫与只读账号不动；`SYSTEM_PROMPT` 的三条铁律与数据地图保留原文，只把"工作流"一节改写为图式步骤；`Agent.ask()` 的单轮循环由 `LangGraphAgent.ask()` 取代，但 **`Agent` 类保留**作为对照实现与回归基线（同文件第 3.4 节）。

### 5.7.1 两个真实缺陷（都是 P0）

**缺陷一：`propose_sql` 的 tool_call 没有被回应，导致整个请求被拒。**

现象：功能看起来全做对了（规划产出、SQL 真实执行），但回答正文是"汇总阶段调用模型失败：BadRequestError ... An assistant message with 'tool_calls' must be followed by tool messages responding to each 'tool_call_id'"。

根因：规划阶段用了一次工具调用（`propose_sql`）作为"计划的数据格式"，但服务端把它当成普通的工具结果消费掉了，**没有补一条 `role=tool` 的回应**。DeepSeek（与 OpenAI 同协议）要求带 `tool_calls` 的 assistant 消息后面必须跟齐每个 `tool_call_id` 的 tool 消息，否则**下一个请求**整体 400。

修法：规划节点为每个 `propose_sql` 调用补一条"计划已受理"的 tool 回应。**为什么不是简单删掉工具、改用纯文本 JSON**：工具调用给出的是**结构化参数**（目标表 + SQL + 理由），不依赖解析散文；那正是本项目要的"规划是数据而不是散文"（`docs/sprint/SPRINT_8.md` 第 9.6.1 节）。

**缺陷二：规划器复用全局消息流，重规划变成重放。**

现象：同一问题第一次失败后，模型把**同一条错 SQL** 又提了一遍（`ads_batch_trade_1m` 没有 `window_start` 列，被查了两次）。

根因：规划器接着上一轮的消息继续生成，上下文里既有上一版计划、又有上一轮的查询结果——模型看到"已经有数据了"，没有动机改变做法；而且它并不知道自己上一版写了什么具体的 SQL。

修法：规划器每轮只用**干净的上下文**——系统提示词 + 问题 + 检索结果 + **上一版计划原文** + **真实失败原文**。实测第二版计划明确写出了"上一版失败原因读明白了：…Unknown column 'window_start'…属于猜测，踩坑了"，并改成"先探测天表真实列名"——**这才是重新规划**（同文件第 9.6.2 节）。

验收标准要求"反思重试真实触发过至少一次"，实测结果（`docs/sprint/SPRINT_8.md` 第 9.5 节）：

| # | 问 | 图路径 | retries | 结果 |

## 5.8 检索：BM25 词法检索 + 显式同义词表

**语料构成**（实测 `/retrieval`，`docs/sprint/SPRINT_9.md` 第 9.2 节）：

```text
docs_total = 65
  metric      22  ← sql/metadata/metrics.md 的指标行（逐行成块，同名合并）
  convention  15  ← 同文件的通用约定
  topic        4  ← sql/metadata/kafka_topics.md 的事件类型
  layering     8  ← services/agent/knowledge/layering.md
  table       16  ← GET /meta/tables（与 sqlguard 白名单逐表对应）

channels = {
  'sql/metadata/metrics.md'                  : 'ok（37 条）'
  'sql/metadata/kafka_topics.md'             : 'ok（4 条）'
  'services/agent/knowledge/layering.md'     : 'ok（8 条）'
  'live_tables'                              : 'ok（16 张表）'
}
```

`channels` 是**刻意暴露**的：任何一路语料缺失都会在这里显示原因，而不是让检索悄悄变差——"少了一路语料却假装完整"是最难发现的故障（同上）。

**文档模型带行号**。每条语料是一个 `Doc`，含 `doc_id`（如 `metrics.md#L33`）、`title`、`text`、`source`、`line`、`kind`。**为什么要行号**：回答里写"依据 `sql/metadata/metrics.md`"只能证明"有这么个文件"；写上 `L33` 才能让人**当场翻到那一行核对**（`docs/sprint/SPRINT_9.md` 第 3.1 节）。

**`retrieve` 是图的第一个节点，不是"让模型自己决定要不要查"**：

```text
retrieve（确定性执行，命中写入 state.docs）
   ↓
plan（提示词里带上 state.docs 的格式化结果）
   ↓
execute → validate → reflect → …
```

**为什么不让模型决定要不要检索**：检索是**每问必需**的前置步骤，让模型"有时想起来查"会得到不稳定的口径引用——而这正是本阶段要消除的问题。同时 `retrieve` 仍作为第 5 个工具注册进 `/tools`（能力面可枚举、可审查），但**不参与模型的工具选择循环**（`docs/sprint/SPRINT_9.md` 第 3.3 节）。

**同义词真实生效的实证**（核心验收项，`docs/sprint/SPRINT_9.md` 第 9.3 节）：

```text
问：最近一周卖了多少钱        ← 问法里不含 GMV 字样
  expanded : ('卖了多少钱', ['gmv', 'payment_amount'], w=1.00)
             ('卖了多少',   ['gmv'],                  w=0.90)
  hit      : metric:payment_amount | sql/metadata/metrics.md:38 | 支付金额（payment_amount）
  hit      : metric:gmv            | sql/metadata/metrics.md:33 | GMV（gmv）
```

**负例同样成立**（只有正例的话，"把所有词都映射一遍"的坏配置也能全绿）：

```text
问：今天天气怎么样适合钓鱼吗
  hits = []            ← 不硬凑命中
```

**四条检索质量踩坑**（全部由真实问句暴露，`docs/sprint/SPRINT_9.md` 第 9.5 节）：

1. **"提到某词的文档"压过"定义该词的文档"**：问「最近一周卖了多少钱」（同义词 → `gmv` + `payment_amount`）时，排第一的是 `metrics.md` 里那句列举了所有可加指标的约定行——它同时命中两个查询词项，长度惩罚压不住它；而真正定义 GMV 的那一行只命中一个词项。修法：加"标题命中加成"（`TITLE_BONUS`），理由是**词袋模型没有字段概念，"提到"某词的行不该压过"定义"该词的行**。另把同名指标（`gmv` 在交易域与类目域各一行）**合并成一条**，既保证来源不重复，也避免"用户问 GMV 却拿到类目口径"。
2. **短词项是噪声**：`payment_amount` 自身含子串 `amount`，ASCII 切分会同时产出两者；而 `amount` 出现在每一行业务指标里，把无关文档也拉进了结果。修法：**给长词项当子串的短词项直接丢弃**。
3. **孤立中文单字是噪声**：`算`、`的`、`是` 这类单字几乎出现在每一篇文档里，idf 很低却数量极多，把 `matched_terms` 填满噪声——表现为"看起来命中了很多，其实无关"。修法：分词丢弃**孤立中文单字**。
4. **markdown 表头会被当成一条数据**：第一版解析器把 `| 指标 | 字段名 |` 这行也当成了一条口径条目。表头与数据行的**形态完全一样**，只有"它在分隔行 `| --- |` 的上一行"这个位置信息能识别它。修法：解析器在遇到分隔行时回退掉紧邻的上一行，并做成默认行为而不是让调用方各自判断（漏掉的后果是语料里多出一条叫"指标"的假条目）。

**一条自证诚实的取舍**：文档写清这是 **BM25 词法检索**（含 idf 与长度归一化），**不声称**语义检索。项目在风险表里把"声称 RAG 却只是关键词 `grep`"列为需要正面回答的质疑，并给出结论："诚实描述比夸大更安全"（`docs/sprint/SPRINT_9.md` 第 6 节风险表末行）。

**一条架构边界的澄清**（很重要，容易被误解）：Agent 读自己仓库里的文档**不属于持有数据库凭据**。"Agent 不允许直接拥有数据库管理员权限"约束的是**数据库权限**；RAG 语料是**知识**，不是**凭据**。Agent 仍然没有任何数据库连接信息，取数仍只经 `POST /query`（`docs/sprint/SPRINT_9.md` 第 2.4 节）。

## 5.9 MCP：把只读能力声明出来

**两条路径**（`docs/sprint/SPRINT_10.md` 第 2 节）：

```text
路径 A（直连）  Agent ── HTTP ─────────────────────────► 只读数据服务 ──► Doris
路径 B（MCP）   Agent ── MCP(streamable-http) ──► MCP 服务 ── HTTP ──► 只读数据服务 ──► Doris
                                                              └─ 无凭据
```

**两条路径的终点、守卫、账号完全相同**（`POST /data/api/query` + `sqlguard` + `agent_ro`），差别只在"谁来发起那次 HTTP"。这一点是本阶段的设计核心：**MCP 不是一条新的取数通道，而是同一份只读能力的另一种暴露方式。如果它变成"另一条能取数的路"，那"不得绕过 sqlguard"这条铁律立刻就被绕过了——因为绕过的方式恰恰是"再实现一遍"。**

**铁律在代码里的落点与证明方式**（同文件第 3 节）：

| 铁律 | 落点 | 怎么证明 |
| --- | --- | --- |
| 不得给 MCP 直接数据库凭据 | `services/mcp/app/config.py` 只读非敏感环境变量；systemd 单元**没有** `EnvironmentFile=.env` | 验收第 3 步：扫单元文件 + 扫 `/proc/<pid>/environ` + 扫源码，都不许出现任何口令键名 |
| 不得绕过 `sqlguard` | `services/mcp/app/client.py` 唯一的取数实现是 HTTP 调 `POST /data/api/query`；MCP 的依赖里**没有**任何数据库驱动 | 验收第 4 步：经 MCP 发 DELETE / 未授权表 / 多语句 / 注释注入，四类都必须被拒绝且原因正确 |
| 权限最小化 | 暴露 4 个只读工具，与只读接口一一对应；没有写工具、没有任意 HTTP 出口、没有文件读写 | 验收第 2 步：工具数恰为 4，且与 Agent 的取数工具**逐名相等** |
| 失败即失败 | `client.py` 把数据服务的错误信封原样抛出；`server.py` 里不存在任何兜底默认值分支 | 验收第 4 步的拒绝原因；单元测试 `test_mcp_failure_does_not_fall_back_to_direct_http` |

**端到端一致性实证**：同一 SQL 经 MCP 路径与直接 HTTP 路径的结果**逐字段 IDENTICAL**，`executed_sql` 也相同；比对之前先加**非空守卫**（避免"两边都空"的假通过）。**拒绝经 MCP 透传后语义未丢**：DELETE 的真实返回是 `is_error=False` + `structured_content={"ok":false,"error":{"code":"NOT_SELECT"}}`，底层 HTTP 400 同码（`AGENTS.md` 第 15.12 节）。

**为什么不做"能连 MCP 就用 MCP"的自动降级**：验收必须能回答"这一次到底走了哪条路"。自动降级会让 MCP 路径在任何一次连接抖动后**悄悄消失**，而所有断言仍然全绿——这是最难发现的一类失效。因此路径由 `AGENT_DATA_PATH` 显式决定（`http` 或 `mcp`），MCP 不可达时工具返回失败结果，**不**自动回退到直连（`docs/sprint/SPRINT_10.md` 第 5.2 节）。

**三条值得单独记的设计取舍**（同文件第 9.2 节）：

1. **分流点只有一个**：`ToolBox.call()` 是唯一的取数路径分流点（`if self.data_path == "mcp" and name in _MCP_TOOL_NAMES`）。放在这一处而不是散在五个方法内部有两个实际好处："哪些工具走了 MCP"是一眼可读的事实；而 Sprint 7 已验收的直连实现一行都不用改，回归风险最小。
2. **非取数工具不走 MCP**：`retrieve_docs` 查的是 Agent 自己的语料文件，`propose_sql` 是图内部的规划协议。把它们也塞进 MCP 会让"最小能力集合"这个说法失真——它们本来就不是取数能力。单元测试 `test_non_fetch_tools_never_go_through_mcp` 锁住这一点。
3. **`tables_lookup` 的"查不到"报失败，而"没有可用表"报成功**：`tables_lookup(table=不存在)` 返回 `ok=False` 并列出可用表——因为对模型来说"表不存在"与"表存在但没有列"是完全不同的信息，后者会让它以为"这张表是空的"从而写出一条**语法正确但语义错误**的 SQL。

## 5.10 数据质量与监控

**质量校验的组织方式**（`docs/sprint/SPRINT_11.md` 第 4.1 节）：一个清单文件 `infrastructure/quality/checks.conf`（25 条校验，每条含域 / 严重级 / 引擎 / SQL / 算子 / 阈值 / 说明 / 排查提示）+ 一个执行引擎 `run-check.sh` + 每条校验一个 SQL 文件（**必须返回恰好一个标量**）+ 一个可调度总入口 `scripts/run-quality-checks.sh`。

校验项覆盖 7 类：

```text
行数非空守卫        3 条   交易域 / 流量域 / 分层代表表
主键唯一            3 条   交易域 / 流量域 / 离线 ADS 窗口
关键字段非空        3 条   交易域 / 流量域 / ADS 窗口
枚举合法            2 条   event_type（行为漏斗）/ payment_status
漏斗单调            1 条   VIEW > CLICK > CART > BUY
层间一致            4 条   实时 DWD↔离线 ADS 订单数 / 行为明细↔ADS PV /
                           DWD↔ADS 订单数 / DWD==ODS 逐表（spark）
ADS 窗口数 > 0      1 条   四个窗口粒度表的非空守卫
1m↔1d 汇总一致      1 条   可加指标在两个粒度上必须相等
金额关系            3 条   GMV 实时==离线 / 支付<=订单 / 退款<=支付
新鲜度              4 条   两个 1m 窗口 + 两个 dt 分区
```

**分两个引擎是有意的内存纪律**，不是实现不完整：

| engine | 查什么 | 为什么 |
| --- | --- | --- |
| `doris` | 实时链路 + 已装载的离线结果 | 走 Doris FE 的 MySQL 协议，**不起 Spark**，可以在实时链路运行时随便跑 |
| `spark` | 湖仓里的 Iceberg 表（DWD == ODS 逐表） | 湖仓在 MinIO 上，Doris 侧读不到。需要一次性 `spark-sql` 容器（驱动约 1 GB），因此**默认不跑**，由 `--with-lake` 显式驱动并受内存闸门约束 |

（`docs/sprint/SPRINT_11.md` 第 3.1 节）

**失败路径是可复现的证明，不是一句声明。** "校验失败会 exit 1"这句话无法靠读代码证明——一个无论结果都 `exit 0` 的脚本，读起来也可能很像对的。因此交付物包含一个可执行的证明：

```bash
bash scripts/run-quality-checks.sh --proof-fail
```

它故意把两条校验的期望值改成不可能成立的值，断言两次都必须返回退出码 1，然后**再跑一次正常校验**证明失败来自断言而不是数据被改坏。实测：演示 1 期望 `999999999999` → `[FAIL]` → 退出码 1；演示 2 期望 `-1` → `[FAIL]` → 退出码 1；恢复后仍全绿（`AGENTS.md` 第 15.11 节；`docs/sprint/SPRINT_11.md` 第 10.1 节）。

**监控实测**（`AGENTS.md` 第 15.11 节）：

```text
Prometheus   prom/prometheus:v3.13.3（LTS）  mem_limit 256m  实测占用 105 MiB
Grafana      grafana/grafana:13.2.2          mem_limit 256m  实测占用 187 MiB
             两个容器合计 512m —— 预算上限
抓取目标     4/4 up（prometheus / doris-fe / doris-be / grafana）
             Doris FE 1564 条、BE 1019 条指标
公网入口     /grafana/ → 200（面板 23 个，匿名只读）
             /metrics/ → 200（原始指标，只放行 GET/HEAD/OPTIONS）
```

**版本选择上有一条值得记录的判断**：Prometheus 3.14.0 虽然是最新版（2026-08-17），但其 EOL 为 2026-09-30——只剩 3 天，不适合钉在毕设里。因此选 3.13.3（LTS 线，3.13.0 于 2026-07-01 发布，LTS 支持到 2027-07-31）（`docs/sprint/SPRINT_11.md` 第 2 节）。

**一处"用健康端点验证凭据会得出相反结论"的实测**（同文件第 7.13 节）：

```text
MinIO /minio/health/live：
  不带任何凭据   → 200
  带正确凭据     → 400   ← 关键：正确也报错
  带错误凭据     → 400
```

也就是说该端点**根本不看 Authorization 头**，它对"带凭据的请求"一律返回 400。拿它当口令判据，会把**正确的口令判成无效**——方向刚好相反。正确判据是"真的做一次 S3 操作"，并且带对照组（`mc ls` 对正确凭据列出 `lakehouse/`，对错误凭据报 `The Access Key Id you provided does not exist in our records.`）。

> **通用教训**：验证"某个值对不对"时，判据必须能**区分对与错**。只测"我期望的那个输入"，而不设一个**必然失败的对照组**，就无法判断这个判据本身是有效判据还是一个恒定的响应。

**"一条恒红的校验比没有校验更糟"** 也有一条实测（同文件第 7.6 节）：新鲜度阈值第一版定 26h，实测数据的事件时间最后到 `T 日 13:16`，而按日调度的批处理在 `T+1 凌晨` 才把它算进 ADS，于是 `T+1` 的"现在"与最新窗口差 **31.8h**——这是**日批的正常形态**。结果四条新鲜度校验全红。最终定 48h（漏跑一整天会变成 50~56h，必然报警），并把"稳态滞后 31.8h"写进配置注释，让后来者知道这个数是**测出来的**，不是拍的。

## 5.11 一次真实事故的完整复盘

> 本节记录一次**由实施动作直接引入**的事故。把它单列成一节，是因为它暴露的不是某个技术难点，而是"共享状态 + 并行改动"这一类风险，以及一次**绕开安全守卫**的决策过程。这类内容比一次成功的技术选型更有参考价值。

### 5.11.1 事件

在 Sprint 12 实施期间，为绕过同步脚本 `sync-subset.ps1` 的"Spark 运行中"守卫，作者写了一个新的同步脚本，其远端步骤是：

```text
mv /opt/data-platform /opt/data-platform.old
  → tar 解到 /opt/data-platform.new
  → mv .new 到位
  → rm -rf .old          ← 这一步出了问题
```

因为只打包了 `services/mcp` 一个子目录，`rm -rf .old` 把**旧树里的一切**都删掉了，包括：

```text
.env                                    ← 唯一存有真实凭据的文件
.venv / .venv-agent / .venv-airflow     ← 三个虚拟环境
airflow/airflow.env                     ← Airflow 的环境文件
三个由 compose 挂载的第三方 JAR：
  infrastructure/spark/lib/mysql-connector-j-8.4.0.jar
  infrastructure/hive/client-lib/hadoop-aws-3.1.0.jar
  infrastructure/hive/client-lib/aws-java-sdk-bundle-1.11.271.jar
```

（`docs/sprint/SPRINT_12.md` 第 8.2 节；`AGENTS.md` 第 15.11 节）

### 5.11.2 根因：不是"环境问题"，是一个绕开守卫的决定

守卫（`sync-subset.ps1` 拒绝在 Spark 运行时同步）拦的正是"运行中的脚本被半覆盖"。**原子换树确实防住了"半覆盖"，却把子集同步变成了整树替换**——子集之外的机器状态（配置、虚拟环境）就不再受保护了。

> **「绕过一个守卫」时，必须重新论证被绕过的那个守卫原本防的是什么，以及新方案是否引入了别的、可能更大的风险。** 本次没有做这一步——这就是事故的根因。

（`docs/sprint/SPRINT_12.md` 第 8.2 节；`docs/DEVELOPMENT_LOG.md` 第 1537~1542 行）

### 5.11.3 连带损失的误导性症状

事故的处置过程留下了两条极有价值的记录（`AGENTS.md` 第 15.11 节）：

**其一：Docker 会在目标文件不存在时把挂载点创建成空目录。**

于是"文件丢失"在磁盘上表现为"一个空目录"，而 `ls -la` 看上去像是**有东西**（有那一行）。只有 `[ -f ]` 与 `[ -s ]` 才会揭穿它。

> **判断挂载型文件是否存在，用 `-f` + `-s`，不要只看 `ls`。**

**其二：报错指向的不是根因。**

Metastore 起不来时报的是 `DatastoreDriverNotFoundException: com.mysql.cj.jdbc.Driver was not found in the CLASSPATH`——它说的是"CLASSPATH 配错了"，而真相是"那个 JAR 文件被删了"。顺着错误信息去查 `hive-site.xml` / `--auxpath` 会一无所获。

**其三：恢复操作本身也有陷阱。** 两个易踩的细节：`docker cp` 的目标若**已存在且是目录**，它会把源**放进该目录里**（变成 `xxx.jar/xxx.jar`），校验时只看到一个空目录；提取后必须**与镜像内原件做 md5 比对**（本次三个 JAR 全部 MATCH），否则"大小看起来对"也可能是不完整的文件（`AGENTS.md` 第 15.11 节）。

### 5.11.4 事故沉淀出的硬规范

这次事故与同期另一起"顺手把 `.env` 权限收紧成 600"的事故，共同沉淀出五条硬规范（`AGENTS.md` 第 15.11 节）：

> 1. **共享文件的权限必须按"所有读者"定，不能按"最小权限"直觉定。** 本机 `.env` 必须是 **`640 root:dpapi`，不能是 600**——因为 `data-platform-api` 以 `dpapi` 组身份运行、`data-platform-agent` 以 `dpagent` 用户（`dpapi` 组成员）运行，两者都需要**组读**。实测后果：写成 600 会让 Agent 直接起不来（`PermissionError: /opt/data-platform/.env`），而症状出现在"别人负责的服务"上——**故障现场与改动现场不在一起**，是最难关联的一类故障。权限属于"别人也依赖的共享状态"，**每次部署都要校正一次**。
>
> 2. **禁止任何"原子换树 / 镜像式"同步。** 正确做法：**只覆盖需要覆盖的文件**，且用 `mv` 做**单文件**原子替换（换 inode，正在执行的脚本不会读到半截内容），绝不动目录本身。
>
> 3. **在确认凭据已落盘之前，禁止 `docker compose up / restart`。** 容器/进程的 `Config.Env` 里可能还留着**上一份**凭据（进程启动时读入内存，文件删了也还在）。此时重建容器非但不能"修好"，反而会把**唯一的一份**凭据丢掉。排查顺序应当是：先确认 `.env` 在位且可用 → 再重建容器。
>
> 4. **改共享编排文件（`deploy/**`、`docker-compose.yml`）必须先落创作副本再同步。** 服务器上直接改的仓库文件，会被任何一次"创作副本 → 工作区 → 服务器"的同步**静默回滚**（同步报成功、nginx 也不报错，只是功能变回旧行为）。验收时必须核对 live 配置与仓库副本的 **md5 一致**（实测 `b5197e5121e08d689daebb72d3e626e2`，两侧一致）。
>
> 5. **会改机器状态的验收脚本，开头必须检查 `.env` 是否存在，不存在就 `exit 1`。** 否则脚本会在"没有凭据"的机器上跑出一堆看起来像功能缺陷的失败，把真正的根因埋在噪声里。反之：**只做解析/只读的入口（如 `--list`）不应依赖 `.env`**。

### 5.11.5 同时暴露出来的一个破坏性操作顺序问题

`.env` 恢复之后复跑 `verify-sprint-3.sh`，第 6 步（服务装载）5 项全红（Doris 侧四张离线 ADS 表行数不匹配）。关键线索是：08:45 时这些表**还有数据**（Sprint 11 的质量校验实测全绿），而湖仓侧（期望值的来源）一直完好——也就是说，**Doris 侧的数据是被"清掉"的，不是湖仓那边坏的**。

根因在装载脚本自身：

```text
第 189 行：  if ! doris_q -e "TRUNCATE TABLE ${DORIS_DB}.${table};"; then ... fi
第 197 行：  INSERT INTO ${DORIS_DB}.${table} (...) SELECT ... FROM S3(...)
第 210 行：  log_error "${table} 装载失败（表可能已被清空，请重跑本脚本恢复）"
```

即**先 `TRUNCATE`，再从湖仓（`S3()` TVF）装载**。在 `hive-metastore` 崩溃或不健康的那段时间里执行它，就会**先把 Doris 清空、再由一个读不到湖仓的 `INSERT` 失败**，留下一个"被清空但没有装载"的服务层。

> `TRUNCATE` 与随后的 `INSERT` 虽然"各自原子"，但**两者之间不是原子的**。一旦第二步失败，系统就停在一个**比失败前更差的状态**：不是"装载没更新"，而是"数据没了"。对**服务层**（看板、接口直接读这里）尤其致命——它会让"一次失败的批处理"升级成"对外服务没有数据"。

（`docs/sprint/SPRINT_11.md` 第 10.3 节；`docs/DECISIONS.md` ⏳12）

该问题后来已修（提交 `b195d19`）：`TRUNCATE` 之前先探测源端（S3 路径可读、且至少一行），不满足就**保留现有数据并失败退出**，而不是先把数据删掉再试（`docs/DECISIONS.md` ⏳12）。

### 5.11.6 事故的价值

这一节的核心结论可以概括为三条判据（`AGENTS.md` 第 15.11 节）：

> **这个文件还有谁在读？这个目录里还有什么我没看见的状态？我现在做的动作，别人会不会依赖它的旧值？**

事故还顺带说明了一件与"验收"直接相关的事：**「测试全绿」只有在环境处于目标状态时才有意义**。同一份测试在这一天里以四种面目出现（见 6.1 节），而每一次都"看起来像是代码问题"。

## 6.1 测试体系与全量测试结果

测试分三层：单元测试（`-m unit`，零外部依赖）、冒烟测试（`-m smoke`，服务未启动时**优雅跳过**而不是误报失败）、验收脚本（每个 Sprint 一个，分步 `[OK]/[FAIL]` + 统计 + 失败 `exit 1`）。

全量测试的实测结果（`docs/sprint/SPRINT_12.md` 第 8.3 节）：

**这个数字必须连着"漂移史"一起读。** 在收口过程中，同一份测试出现过四种结果，**没有一次是因为代码变了**（`docs/sprint/SPRINT_12.md` 第 8.4.1 节）：

**那 7 条失败为什么不是代码问题**：它们的**测试名字**看起来都像真缺陷（`test_no_float_columns_in_ods`、`test_money_columns_are_decimal` —— 像是"ODS 里出现了 float 列"）。看实际报错才发现是 `java.net.ConnectException: Connection refused`（`spark-sql` 连不上 `hive-metastore:9083`）。**如果只看测试名就下结论，会得出一个完全错误的判断，然后去改根本没错的代码。必须看实际报错。**

> **结论**：`skipped` 从 0 → 22 → 47 → 0，`failed` 从 7 → 0。数字变好**不是因为我们改了什么**，而是因为外部依赖恢复了。**验收结论必须连同"当时的环境状态"一起给**——单独一个"353 passed"是没有信息量的，加一句"当时 ADS 已装载完成"才是可核对的事实。

另一条由这次事故暴露出的测试环境问题：`pytest` **不在任何 requirements 文件里**，一直是手工装的；`tests/test_data_generator.py` 依赖的 `Faker` / `python-dotenv` 同样不在。因此重建 venv 时它们全部丢失。已新建 `requirements-dev.txt` 正式声明这三个包。教训是：**任何一次真实用到的安装，都必须能从仓库里的某个文件重放出来**（`docs/sprint/SPRINT_12.md` 第 8.5 节）。

## 6.2 逐窗口对账（验证方法）

第 5.3 节已给出对账结论。这里补充**方法**层面的三点设计，它们是"差异为 0"这句话能够被采信的原因：

1. **对账区间必须截断。** 实时链路仍在消费，最新窗口可能尚未封闭，因此区间尾部留 3 分钟安全边界，只比对"两端都已封闭"的窗口（`docs/sprint/SPRINT_5.md` 第 9.2 节）。
2. **单边窗口必须单独统计。** 汇总表记录 `realtime_only_windows` / `batch_only_windows`，实测两个域都是 0 / 0。这样"差异为 0"就有了边界可核——否则"只比对两边都有的窗口"会把"某一侧缺了一批窗口"这种情况掩盖掉（同上）。
3. **判据列必须列清楚，并区分可比与不可比。** 交易域判据为 **8 列**（**7 个可加指标 + 1 个去重指标** `order_user_cnt`，后者两侧同为近似去重、只支持逐窗口比较）；流量域判据为 `uv` / `pv` / 5 个行为计数共 **7 列**，加上 3 个比率列的**独立**判据（每侧与自己重算，只作诊断性异常登记、不参与 `is_pass`）。而 `dws_traffic_funnel_1d` 里的 4 个"每步去重人数"是离线新增的下钻维度，实时侧没有对应列，因此**不参与批流对账**——这一点写进了 DDL 与 `metrics.md`（`sql/metadata/metrics.md` 第 3.2 节）。

**三类"抗质疑"材料**（把"我做了"升级成"我能证明"），本项目都有：

1. **失败路径的证明**：`--proof-fail` 故意把两条校验的期望值改成不可能成立的值（`999999999999`、`-1`），断言两次都必须返回退出码 1，然后**再跑一次正常校验**证明失败来自断言而不是数据被改坏（`docs/sprint/SPRINT_11.md` 第 1.2、10.1 节）。**一个从未红过的断言，等于没有断言。**
2. **防空集合假通过**：质量校验里有 3 条行数非空守卫 + 1 条"ADS 窗口数 > 0"；MCP 的两路径一致性比对之前先加非空守卫（因为"两边都为空"也是完全一致，但毫无意义）；归档作业的自检曾因"空值断言打在空的目标表上"而**空洞地通过**，该失效模式已被单独记录（`docs/sprint/SPRINT_4.md` 第 10.2 节；`docs/PERFORMANCE.md` 第 5 节）。
3. **判据被打磨的过程**：见 5.3.2 节的两处判据修改，以及 5.3.4 节"用第三方判据（纯算术 1/2 = 0.5）定责、确认缺陷在实时侧而离线侧自洽"的完整过程。**这一段比"不一致 0"更能说明对账工作真的在验证，而不是在凑结果。**

## 6.5 性能基线

**采样口径先于数字**（`docs/PERFORMANCE.md` 第 0 节）：

| 项 | 取值 |
| --- | --- |
| 采样次数 | **只读接口类每项 7 次**（另有 1 次预热不计入）；**Agent `/ask` 实际为 n=2**（原始采集日志 `/tmp/perf-bc.log` 记 `{"n": 2, ...}`；脚本本身**对 `/ask` 没有预热调用**，且循环次数写死为 2，`REPEAT` 对它无效） |
| 统计量 | 中位数（同时给 min/max）；**不报平均值**——单次延迟受 JIT / 页缓存 / 邻近查询影响大，平均值会被离群值拉走 |
| 双端耗时 | 客户端 `wall_ms`（curl `%{time_total}`）+ 服务端 `elapsed_ms`；两者之差 = HTTP + JSON 编解码开销 |
| 采集路径 | 全部经**本机回环**（`127.0.0.1`），**不含公网链路**，因此**不代表**用户从浏览器访问的体验 |
| 缓存状态 | 只读接口**每项先打 1 次预热**并排除在统计外，且 `REPEAT=7` 意味着**同一条 SQL 连打 8 次**、目标表只有万行级 → 这组数字是**热缓存**条件下的中位数，**结构上不可能包含冷缓存代价**，不能外推为冷启动延迟；OS 页缓存 / Doris BE 缓存的影响**未单独测量** |
| 批量作业耗时 | 取自 **Airflow 元数据库** `task_instance.duration` 的既有运行记录（`SELECT ... ROUND(duration,1)`），**不是日志**；**没有**为采这个数字重跑流水线（内存铁律）。口径是**9 个任务各自 `duration` 的算术和**，因此它**不等于墙钟端到端**，且**含 1 次重试 attempt**（该 run 的 `ads_layers` 是 `try_number=2`） |
| Agent 问答 | **n=2**（不含预热，脚本未做预热）；每次真实调用 DeepSeek，单次约 18~20 s；`retries=1` 说明该次测量**多走了一轮 `reflect → plan`**，故 19.2 s 里含一次重试的代价，不是一个"干净单轮"的问答延迟 |

> ⚠️ **性能结论的边界（必须与数字一起引用）**：以上全部结果都是
> **单机实验环境**（腾讯云 4 核 / 16 GB）、**单请求串行**、**本机回环**、**热缓存**口径下测得的；
> 采集脚本**没有任何并发原语**（全是顺序 `for` 循环 + 单次 `curl`），
> 本项目**未做任何并发或压力测试**，**因此这些数字不构成对生产环境高并发能力的证明**，
> 也不构成容量规划依据。同理，Agent 端到端 19.2 s **不应被理解为数据平台的查询性能** ——
> 同一份证据恰恰证明相反：可单独测量的数据侧合计仅 18.3 ms（检索 2.9 + 取数 15.4），
> 约 **99.9% 的耗时在外部 LLM 服务往返**上。

**采集时的机器状态（测量现场）**：2026-09-27 09:11:32 ~ 09:15 (+0800)；load average 1.46 / 3.06 / 3.85；内存总 15989 MB / 已用 12067 MB / **可用 3921 MB**；Spark 作业 **0 个**；8 个 Flink sink 作业 RUNNING（常驻约 12 GB）。

   > 该次查询 `row_count = 0` —— 也就是说，**这一格测到的是"JOIN 一张空维表"的代价，而不是两表关联真正发生的代价**。
   > 该缺陷已于 2026-09-27 修复（提交 `b195d19`）；按同一口径重跑，同样的查询返回 **10 行**、中位数约 **7.4 ms**。
   > 上表保留原值 11.7 ms 是**为了不改历史观察值**，但它**不是**"两表关联"的真实延迟量级 —— 引用时应写"11.7 ms（采集时维表为空；修复后同口径约 7.4 ms）"。
2. **`GET /overview` 是最慢的接口（53.8 ms，约为最简接口的 30 倍）**。原因是它一次拼了 **6 条查询**（交易 KPI + 流量 KPI + 去重 UV + 窗口统计 + 类目排行），而 `GET /meta/metrics` 只解析本地文档（1.7 ms）。→ **优化方向明确**：若要压总览页延迟，应把 6 条查询合并或并行，而不是去优化 SQL 本身（SQL 已经是 5 ms 级）。
3. **`GET /meta/tables` = 43.2 ms**：它查 `information_schema` 拿全部授权表的列（16 张表 × 多列），属于预期的元数据开销；Agent 侧对它按 TTL 缓存（`TABLE_TTL_SECONDS`），因此不是每次问答都付这个成本。
4. ⚠️ **C 查询返回 0 行——这是一个真实的数据缺陷，不是性能问题**（见 6.5 节）。

| 项目 | 表 | 中位数 (ms) | min | max | 服务端 elapsed_ms | 行数 |
| --- | --- | --- | --- | --- | --- | --- |
| 实时 窗口聚合 | `ecommerce.ads_realtime_trade_1m` | **7.1** | 6.7 | 8.3 | 4 | 1 |
| 离线 按天聚合 | `lakehouse_ads.ads_batch_trade_1d` | **7.1** | 6.7 | 7.5 | 4 | 1 |

| 实时 明细扫描 | `ecommerce.dwd_trade_order_detail` | **9.4** | 9.1 | 10.5 | 7 | 200 |

**两侧没有可测量的差异**（同口径聚合都是 7.1 ms，类目排行 7.6 vs 8.0 ms，差 0.4 ms——小于 min/max 的波动范围，不构成结论）。


### 6.5.3 ③ 批量作业耗时

数据来源为 Airflow 元数据库 `task_instance` 表的既有运行记录（`duration` 字段）。一次完整的成功运行 `scheduled__2026-09-26T19:00:00+00:00`：

| # | 任务 | 对应脚本阶段 | 开始 | 结束 | 耗时 (s) |
| --- | --- | --- | --- | --- | --- |
| 1 | `pause_realtime` | —（错峰：暂停 Flink 栈） | 03:00:00 | 03:00:18 | **18.5** |
| 2 | `ods_extract` | `ods` | 03:00:19 | 03:01:20 | **61.6** |
| 3 | `archive_behavior` | `archive` | 03:01:21 | 03:07:25 | **363.3** |
| 4 | `dwd_layers` | `dwd` | 03:07:26 | 03:12:29 | **303.5** |
| 5 | `dws_layers` | `dws` | 03:12:30 | 03:19:10 | **399.7** |
| 6 | `ads_layers` | `ads` | 04:07:11 | 04:14:38 | **446.8** |
| 7 | `reconcile` | `reconcile` | 04:14:39 | 04:16:58 | **138.8** |
| 8 | `load_to_doris` | `load` | 04:16:59 | 04:19:07 | **128.8** |
| 9 | `restore_realtime` | —（错峰：恢复 Flink + 自检） | 04:19:08 | 04:21:19 | **131.3** |
| | **9 个任务耗时合计** | | | | **1992.3** |

**端到端**（首任务开始 → 末任务结束）：03:00:00 → 04:21:19 = **约 81 分钟**。

> 其中 `ads_layers` 的**开始时间**（04:07:11）与 `dws_layers` 的结束时间（03:19:10）之间有 **48 分钟的间隔**——那是当天的重试/等待窗口（该 run 的 `ads_layers` 有多次 attempt），因此"9 个任务耗时合计 1992 s"与"端到端 81 分钟"**不相等**。两个数都给出来，并把差异说明白，而不是只报小的那个。
>
> **另需写明求和口径（否则会被追问）**：本表的 1992.3 s 是 **9 个任务各自 `duration` 字段的算术和**，
> 数据取自 **Airflow 元数据库** `task_instance`（不是任务日志）；
> 且**这一次求和对同一任务的全部 attempt 行求和、未按 `try_number` 过滤** ——
> 也就是说它**含 1 次重试 attempt**（`ads_layers` 是 `try_number=2`）。
> 因此"1992.3 s"的准确表述是"**各任务 `duration` 之和（含 1 次重试 attempt）**"，
> 它既不是墙钟端到端，也不是"一次干净运行的计算成本"。
> （元数据库直接 `SUM(duration)` 得 **1992.2**，与逐项四舍五入到 0.1 s 后相加的 1992.3 差 0.1 s，属求和口径差异，非编造。）

结论：

1. **固定成本**：`pause_realtime` + `restore_realtime` = 18.5 + 131.3 = **149.8 s**，这是错峰模式的固有开销（暂停/恢复 Flink 栈并自检），**与数据量无关**。
2. **真正的耗时大头是四个分层/归档作业**：`archive`(363) + `dwd`(304) + `dws`(400) + `ads`(447) = **1514 s**，占 9 个任务耗时合计的 **76%**。这是 Spark 作业的启动与 shuffle 成本（本机单 worker、driver 768m）。
3. `load_to_doris` 只要 **128.8 s**（`S3()` TVF 直读 Parquet），`reconcile` **138.8 s**。
4. **本表的价值**：它是"要不要优化批处理"的判据——若要压缩端到端时间，应当从**分层作业的 Spark 启动与分区数**入手，而不是去优化装载或对账（那两项加起来不到 270 s）。

**一处保留观察**：对照的一次人工触发运行（`manual__2026-09-26T17:05:38+00:00`）中，`archive_behavior` 只用了 **0.6 s**，而主线那次是 363.3 s，相差 600 倍。该 run 的所有任务状态都是 `success`，所以**只能靠耗时异常发现**——这正是 Sprint 4 记录过的"归档阶段静默空转"的特征。该现象已登记为待复核项，并明确"复核时以**行数与分区数**为准，不要以'阶段返回成功 + 耗时短'为准"（`docs/PERFORMANCE.md` 第 3.2 节；`docs/sprint/SPRINT_12.md` 第 8.8 节）。

### 6.5.4 ④ Agent 单次问答端到端耗时

问题：`最近一周每天的 GMV 是多少？`；引擎：LangGraph 图；模型：`deepseek-flash`（`LLM_THINKING=false`）。

分解方法（每一项都在可核对的接口上单独量到）：

```text
总量          POST /ask 的客户端实测 wall time；响应里的 elapsed_ms 作为对照
取数          execute 节点实际执行的 SQL，单独打 POST /query
检索          retrieve 节点：同一句问题打 GET /api/retrieve?q=...&k=5
规划 + 汇总    = 总量 − 检索 − 取数     ← 两次 LLM 调用的差值
```

| 分段 | 对应图节点 | n | 中位数 (ms) | min (ms) | max (ms) |
| --- | --- | --- | --- | --- | --- |
| **总量** | 整图 | **2** ⚠️ | **19187.5** | 18175.8 | 20199.2 |
| 服务端自述总量 | 整图 | — | **18173** | — | — |
| 检索 | `retrieve` | 7 | **2.9** | 2.6 | 3.1 |
| 取数 | `execute` | 7 | **15.4** | 14.3 | 18.3 |
| **规划 + 汇总（差值）** | `plan` + `summarize` | — | **≈ 19169** | — | — |

> ⚠️ **"总量"这一行的 n 是 2，不是 3，而且没有预热。** 采集脚本对 `/ask` **没有预热调用**，
> 循环次数写死为 2（`REPEAT` 对该节无效）；原始采集日志 `/tmp/perf-bc.log` 记的也是 `{"n": 2, ...}`。
> 早期文档写"3 次（含 1 次预热）"与代码/日志不符，此处按**原始日志**订正为 **n=2**。
> 中位数 19187.5 ms 不受影响（去掉一个样本不改变两个样本的中位数取法），
> 但**样本量只有 2，且每次调用外部 LLM 的真实耗时在 18~20 s 之间波动**，
> 因此该数字只能作**量级参考**，不能当作稳定的性能指标。

结论：

1. **Agent 的耗时几乎全部来自 LLM：约 19.17 s / 19.19 s ≈ 99.9%。** 数据侧（检索 2.9 ms + 取数 15.4 ms = **18.3 ms**）只占 **0.1%**。
2. → **优化 Agent 延迟的方向只有一个：减少 LLM 往返次数或换更快的模型。** 优化 SQL 与索引在 Agent 端到端延迟上**几乎没有意义**（这是本基线最有价值的结论）。
3. **两次 LLM 调用 ≈ 19.2 s，即单次约 9.6 s**（规划一次 + 汇总一次）。本次还发生了 **1 次反思重试**，意味着实际可能调用了更多次——`retries=1` 说明图**多走了一轮 `reflect → plan`**，而这正是延迟的主要放大器：**每一次重试 = 多一次规划 LLM 调用**。
4. 首个 `executed_sql` 是 `information_schema.columns` 的元数据探测——说明模型在这一问上**先探表结构再取数**。这是 2 条 SQL 中的第 1 条。

> **诚实边界（必须写明）**：`19187.5 − 2.9 − 15.4 = 19169.2 ms` 这个差值是"总量减去我们能单独量的两段"，**不是对模型内部推理时间的测量**。它包含两次 DeepSeek API 调用的网络往返 + 服务端推理 + token 生成，无法在本机进一步分解。**不得**把它表述为"模型推理耗时"（`docs/PERFORMANCE.md` 第 4.2 节）。

> **本节全部性能数字的共同边界（一句话，必须与任何一处数字一起引用）**：
> 以上四类基线均在**单机实验环境**（腾讯云 4 核 / 16 GB）、**单请求串行**、
> **本机回环（127.0.0.1）**、**热缓存**条件下测得（`/ask` 仅 **n=2** 且无预热）；
> **本项目未做任何并发 / 压力测试**（采集脚本无并发原语，`SPRINT_12.md` 与
> `docs/PERFORMANCE.md` 均已把"压力测试/并发测试"列入"本 Sprint 不做"），
> **因此这些数字不构成对生产环境高并发能力的证明，也不能作为容量规划依据**。
> 可以主张的只有：**在单机、单请求、预热后、回环路径下**，只读接口点查/聚合/关联的

## 6.6 采集过程中发现的一处真实缺陷：派生表为空使 JOIN 静默返回 0 行

**现象**：第 6.5.1 节的 C 查询（`dwd_trade_order_detail JOIN dim_product`）返回 **0 行**，而 `dwd_trade_order_detail` 有 6000 行。

**定位**（用只读查询逐步收敛）：

```text
SELECT COUNT(*) FROM ecommerce.dwd_trade_order_detail   →  6000   ✅
SELECT COUNT(*) FROM ecommerce.dim_product              →  **0**  ⚠️
SELECT COUNT(*) FROM ecommerce.dim_user                 →  **0**  ⚠️
MySQL 侧：product = 600，user = 1200                    →  事实源有数据
两表 LEFT JOIN 抽样：o.product_id 有值，c.product_id 全为 null
```

**危害**：任何依赖维表 JOIN 的查询都会**静默返回 0 行**（HTTP 200 + `row_count=0`）。

> **静默返回 0 行比报错更危险。** 这条查询的 HTTP 状态是 **200**、`row_count` 是 **0**、响应信封完整、`source.tables` 也正确——从任何一个"接口是否健康"的角度看它都是正常的。只有把结果**与预期行数对照**（维表 JOIN 不该是 0 行）才能发现问题。

**性质**：不是"数据丢了"——湖仓与 MySQL 都有；是**装载阶段没有把维表放进 Doris**（`load-batch-to-doris.sh` 与 `sql/doris/**` 的覆盖范围问题）（`docs/PERFORMANCE.md` 第 5 节）。

**后续状态（已修并已服务器验证）**：提交 `b195d19` + 通配修正后，`load-batch-to-doris.sh` 支持 `<库>.<表>`（维表在 `ecommerce`）、第 5 段声明湖仓来源（`dim_product ← ods_product`）、第 2 段允许自带通配（非分区表用 `*.parquet`，分区表默认补 `**/*.parquet`）、并补了 `agent_ro` 对 `ecommerce` 的授权。实测：`--stage load` 后 **12 张表行数全部通过**，其中 `dim_product 600 == 湖仓 600`、`dim_user 1200 == 湖仓 1200`；经只读服务查那条曾恒为 0 行的 JOIN → **返回 10 行真实类目 GMV**（电脑办公 15,457,835.79…），`source.tables` 正确列出两张表（`docs/DECISIONS.md` ⏳11）。

这条记录的价值在于它与本项目反复出现的失效模式是同一类：**「成功信号」不可信**（`AGENTS.md` 第 15.8 节）、"自检在空表上空洞通过"（`docs/sprint/SPRINT_4.md` 第 10.2 节）、"`tr -d '\n'` 让整条 SQL 变成注释、退出码却是 0"（`docs/sprint/SPRINT_11.md` 第 7.1 节）。**"调用成功"不等于"结果可用"。**

## 7.2 主要贡献

**其一，把"批流一体"做成了可证伪的断言，并公开了判据的打磨过程。** 交易域 11458 个分钟窗口、流量域 19643 个分钟窗口逐窗口比对，不一致 0；两侧 GMV 精确到分相等（口径与边界见 5.3 节：对账区间内、补零比较、计数类判据）。更重要的是，本文给出了对账判据的两次打磨：离线表多一个分区列导致的"假失败"，以及比率列从"两侧相等"改为"每侧按自己计数重算"的判据升级。这两次打磨说明了同一件事——**判据本身必须先被验证**。

**其二，在 16 GB 单机上同时承载实时与离线两条链路。** 做法是错峰批处理 + 内存闸门（阈值 3000 MB）：暂停 Flink 栈释放约 1.65 GB，跑批后强制恢复并自检。闸门曾主动拒绝一次批处理（可用 2258 MB），选择**拒绝而非硬跑**。这条贡献的价值不在于"省了内存"，而在于把资源约束写进了自动化闸门，而不是靠人记得。

**其三，把 Agent 的可信性做成了架构属性而不是提示词属性。** 具体是四件事：**进程边界**（Agent 进程里没有数据库凭据，也没有 mysql 客户端依赖，"不得拥有数据库管理员权限"由架构保证）；**可核对来源**（回答附实际执行的 `executed_sql`、命中的 `docs` 带文件与行号、`tables` 由服务端提取而非调用方自报）；**可数的失败与重试**（`validation.issues` / `retries` / `graph.path` 都是响应字段，重试在实测中被真实触发）；**拒绝即失败**（SQL 守卫与服务端两道拒绝，MCP 路径不做自动降级，避免"路径悄悄消失而断言仍全绿"）。

| 6 | **实时侧 1 个窗口的 `click_rate` 与自身计数矛盾（经成本评估后决定不修）** | 不影响任何已发布口径的指标数值，只影响实时侧 `click_rate` 这一个派生列的一行；但会让"批流对账零差异"这句话变得不严谨 | **已定位**（五步判定，用纯算术 `1/2 = 0.5` 这个第三方判据定责 → 离线侧自洽、实时侧 1 个矛盾窗口）；**判据已改严**（改为"每侧比率 == 按该侧自身计数重算"）；**证据已落盘**（`realtime_rate_anomaly_windows = 1` 作为一等结论 + 逐窗口标记）。**这不是"未解决"也不是"环境问题"。** 机制层面原因标注为待确认（Flink SQL Gateway REST 未响应、`sql-client.sh` 在本机依赖配置下会挂住，未能单独隔离验证） | **不走方案 A**：A（重放实时链路）与 C（改 Flink 作业后重放）都会触发 Kafka 全量重放、覆盖实时侧 19644 个窗口，重放成本远大于该缺陷影响；方案 B 已被否决（会造成仓库代码与运行作业不一致）。项目负责人已复核维持此结论 |
| 7 | **结构债：两份阶段 `case` 重复** | 新增阶段要改两处，只改一处会出现"一个入口能跑、另一个静默跳过"（Sprint 4 已因此踩坑） | 未做重构。当前有两道防线：两份 `case` **都**有"兜底分支必须失败"的写法，因此漏加分支会大声失败而不是报告成功。**这是可维护性债，不是正确性缺陷** | 方案 A（让 `run-batch-pipeline.sh` 委托 `submit-offline-job.sh`）需一次性完成；方案 B（只读的防漂移断言）可立即做 |
| 8 | **`dim_*` 与 sqlguard 的历史缺口** | `dim_product` / `dim_user` 曾在 Doris 里长期为 0 行，导致维表 JOIN 静默返回 0 行；sqlguard 的 UNION 元数据探测曾按语序匹配、反序写法被放行（无越权数据） | 两者**均已修**：维表装载已修并服务器验证（12 张表行数全部通过，曾恒为 0 行的 JOIN 返回 10 行真实类目 GMV）；UNION 判据已成顺序无关（同时出现 `union` 与 `information_schema` 就拒绝），`information_schema` 单独查询仍允许 | 文档与代码的白名单数量曾不一致（文档写 19 张、代码 16 张），现以 `sqlguard.py` 为准；建议安排一次"数据服务侧权限边界复核" |
| 9 | **未做并发/压力测试** | 无并发容量结论 | 本机内存不允许（实时链路常驻约 12~13.7 GB，采集时可用仅 3.9 GB） | 需另开一台机器 |
| 10 | **未做 Iceberg 与 Doris 内表的查询延迟对比** | 缺一项高价值对比 | 需要 Spark 会话，会与实时链路抢内存 | 属独立任务 |
| 11 | **未采集公网链路延迟** | 现有性能数字全部为回环口径，不代表浏览器访问体验 | 公网口径与回环口径不同，需单独测并说明中间设备改写问题 | 独立测量 |
| 12 | **`information_schema` 在授权表集合内** | Agent 可以主动探测元数据（这让它在"表是否存在"这类问题上回答更可靠，但也意味着它能做库表结构探测这类动作） | 未改动该授权集合；MCP 的 `tables_lookup` 走服务自己拼的元数据查询、不接受用户传表名，因此经 MCP 无法做任意元数据探测 | 与第 8 条一并复核 |
| 13 | **无告警** | Prometheus 只抓取与展示，问题不会主动通知 | 阈值判断留在可审计的 SQL 清单里 | 优先用 Grafana alerting（数据源已就绪） |
| 14 | **湖仓层间校验只覆盖 5 张交易表** | `dwd_ods_parity_all.sql` 里的表名是写死的（`spark-sql -e` 不支持参数化），湖仓新增表时必须同步改那份 SQL 的 IN 列表，否则新表会**静默不参与**层间校验 | 该注意事项已写在 SQL 注释里 | 改为从 Metastore 动态取表清单 |

## 7.4 展望

**补短板（已有明确路径的）**：

1. **告警接入**：Grafana 数据源与面板已就绪，接 alerting 的成本主要在阈值设计而非工程实现。当前把阈值留在 `infrastructure/quality/` 的可审计 SQL 里，是为了让判定规则能被逐条讲清楚。
2. **结构债方案 A**：让 `run-batch-pipeline.sh` 的阶段分发委托给 `submit-offline-job.sh`，把阶段实现收敛到一处。方案 B（只读的防漂移断言）可先做，零行为变更、立即见效。
3. **对象存储最小权限**：为 `lakehouse` 桶建专用 MinIO 用户，密钥改走 `credential.provider` 或环境变量注入，消除 `ps` 可见的明文密钥。
4. **数据服务错误码区分**：Doris 的语句错误（如 `Unknown column`）目前被统一包成 503 `DORIS_UNAVAILABLE`，会让 Agent 把"我 SQL 写错了"误读成"仓库不可用"从而多跑一轮重试；建议改为 400 并把错误原文交给模型改写。

**扩能力（需要新条件的）**：

1. **真实数据源接入**：当前生成器同时扮演业务写入方与埋点方；接入真实业务库需要 CDC，且会带来真实数据分布的验证价值。
2. **Iceberg 时间旅行的实际使用**：目前只有"快照数 > 0"的断言（`verify-sprint-5.sh` 第 4 步），尚未在业务流程中使用"查询历史快照"这一能力。可考虑把它用于"批处理前后对比"与"出错时回滚到某个快照"。
3. **向量检索**：替换点只有一个接口（`Retriever.retrieve(query) -> docs`）。要切换到向量后端，需要先解决 embedding 来源问题（外部供应商 + Key，或一台放得下本地模型的机器）。
4. **Agent 会话记忆**：当前单次提问即一次图执行，不引入 checkpoint、不做多轮对话。会话状态与上下文管理是下一步的自然延伸。
5. **域名与受信任证书**：注册域名、申请证书、完成备案后启用 HTTPS，同时解决"按 IP 访问只能自签"带来的演示体验问题。
