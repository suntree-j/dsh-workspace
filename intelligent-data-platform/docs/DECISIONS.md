### ⏳ 12. 装载脚本"先清空后装载"，湖仓不可用时会留下**空的**服务层

| 项 | 内容 |
| --- | --- |
| 实证 | `scripts/load-batch-to-doris.sh` 第 189~198 行：逐表 **先 `TRUNCATE TABLE`，再 `INSERT ... FROM S3(...)`**，且**在清空之前不校验 S3 侧是否真的可读** |
| 本次真实后果 | `hive-metastore` 崩溃期间（`hive-site` 挂载的 JAR 被误删那次）跑过一次装载 → 表被清空、数据没装回来 → Doris `lakehouse_ads` 全空。症状出现在 **Doris**，根因在**湖仓侧**，而且**加载脚本自己报了成功/或只有一条被淹没的报错**（08:45 还有数据，之后变空，直到回归才发现） |
| 为什么危险 | 服务层是"对外正在被读的那一层"（看板、只读接口、Agent 都读它）。破坏性操作放在**校验之前**，等于把"能不能读到"的风险转嫁给了"读到的是不是空的" |
| 我的推荐 | **改成"先验证后清空"**：清空前先 `SELECT count(*)` 探一次 S3 路径（或先装到 `<table>_staging` 再 `ALTER TABLE ... REPLACE` 原子替换）。最小改法是在 `TRUNCATE` 前加一次"源可读且行数 > 0"的守卫，不通过就**跳过该表并让脚本非 0 退出** |
| 现状 | ✅ **已修（2026-09-27，提交 `b195d19`）**：`TRUNCATE` 之前先探测源端（S3 路径可读、且至少一行），不满足就**保留现有数据并失败退出**（`exit 1`），而不是先把数据删掉再试。原有的人工恢复也做过（`batch-mode.sh --stage load` 后逐表行数与湖仓一致，`ads_traffic_1m 19644 == 湖仓`）。**服务器验收待跑** |
| 若你不同意 | 告诉我保持现状，我会在论文里把"装载是破坏性顺序、依赖湖仓可用"作为**已知限制**写明 |

### ⏳ 13. sqlguard 的 UNION 元数据探测缺口**已修**（供你复核）

| 项 | 内容 |
| --- | --- |
| 原缺口 | `_FORBIDDEN_PATTERNS` 的 `METADATA_PROBE` 正则写成 `union all select ... from information_schema`，**按语序匹配**，只覆盖"元数据写在 UNION **后面**那一支"。把 `information_schema` 写在**前面**（`SELECT table_name FROM information_schema.tables UNION ALL SELECT gmv FROM 业务表`）会被放行 |
| 为什么值得修 | 两张表都在授权集合里，**没有越权数据**，但它是一次"未授权元数据探测"的入口，与 AGENTS §10.2 的表述不一致；更根本的是——**判据一旦写成"按顺序匹配"，同一件事换个语序就绕过去了**，这类"看起来还在防"的规则比没有规则更危险 |
| 修法 | 改成**顺序无关**的组合判据：只要同时出现 `union` 与 `information_schema` 就拒绝（lookahead，不消耗字符）。`information_schema` **单独**查询仍然允许（Agent 问"有没有这张表"要走它） |
| 实证 | 本地用纯 Python 对五种语句逐一比对新旧行为：反序 UNION 两种写法**旧版放行、新版拦截**；正序 UNION 两版都拦截（**无回退**）；单独查 `information_schema` 与普通业务查询**两版都放行**（**无过度拦截**）。服务器侧 `pytest tests/test_sql_guard_adversarial.py` 与接口对抗用例**待跑** |
| 测试 | 已按 `xfail(strict=True)` 的设计意图摘掉标记（它如期 XPASS，正是"修好那天会报错提醒回来改结论"），改成正式的拒绝断言 |
| 若你不同意 | 告诉我，我回退到"只拦正序"的旧判据（不推荐），并在论文里把该缺口作为已知限制写明 |

### ⏳ 14. 轮换数据源口令后，**仅 restart Grafana 不生效**（已修，供你复核）

| 项 | 内容 |
| --- | --- |
| 现象 | 轮换 `agent_ro` 口令后，数据服务用新口令一切正常，但 Grafana 报 `Error 1045: Access denied for user 'agent_ro'` |
| 根因 | Grafana 的 **provisioning 不会用一个"仍是 `${VAR}` 占位"的 `secureJsonData` 去覆盖已存储的口令** —— 它认为该字段没变，于是保留历史值。实测：容器 env 里是新值（32 字符），而站内数据源记录 `password_length=48`（旧值），且 `readOnly=true` 使 API 删除返回 403 |
| 处置 | 本项目 Grafana 是**完全 provisioning 化**的（数据源与面板都来自仓库文件、管理员口令来自 `.env`），命名卷里没有任何"只此一份"的东西 → **删卷重建即回到目标状态**。实测后 `ds/query` 查到 GMV `51890375.77`（与验收基线一致） |
| 重要区分 | **删 Grafana 的卷是安全的（它全是派生物）**；但**绝不能**用同样理由删 `.env` / venv / `airflow.env` —— 那些是**不可再生的机器状态**，正是本次事故的教训（AGENTS §15.11 硬规范 2 的立意） |
| 影响 | 运维知识：**"轮换口令"这件事的完成判据不是"服务重启成功"，而是"下游都拿到了新口令"** |

## 二、我已经决定并实施的事项（供你复核）

### ✅ D1. 服务层直装宿主机，不进 Docker（Sprint 6 起）

**决定**：数据层（MySQL/Kafka/MinIO/Doris/Flink）用 Compose；服务层（Nginx/FastAPI/前端/Agent/Airflow）用 apt + systemd。

**理由**：只有几个进程，`journalctl` / `systemctl restart` 比容器编排更直接；且 Airflow 需要调**人手工跑的那同一个脚本入口**，跑在容器里就必须挂 `docker.sock`（等于把宿主机容器控制权交给 Web 应用）。

**影响**：换机器时要多跑几个安装脚本（已全部脚本化、幂等）。

### ✅ D2. Airflow 3.3.2 + MySQL 元数据库（Sprint 4）

**决定**：用 MySQL 而非 PostgreSQL。

**理由**：AGENTS.md §2.3 禁止未经批准引入 PostgreSQL，而 Airflow 官方**明确支持 MySQL 8.0/8.4**，本机正是 8.4.11 —— **零成本满足需求，不违规引入新组件**。

**附带发现**：Airflow 官方**不支持 MariaDB**，本项目是真 MySQL，未踩此坑。

### ✅ D3. Airflow 用独立 venv（`.venv-airflow`）

**理由**：**硬冲突**，不是洁癖 —— Airflow 3.3.2 钉 `fastapi>=0.129,<0.137`，而数据服务用 `0.141.1`。装在一起必然把线上看板的接口依赖降级。

### ✅ D4. 不部署 Airflow 的 triggerer

**理由**：它只为 deferrable operator 服务，本项目全是短时 shell/Spark 任务。在本机可用内存仅约 2.5 GB 的前提下，少一个常驻进程是实打实的收益。**这是有意的取舍，不是漏装。**

### ✅ D5. 任务执行回调走回环而非公网

**决定**：`AIRFLOW__CORE__EXECUTION_API_SERVER_URL=http://127.0.0.1:8085/airflow/execution/`

**理由**：默认值由 `api.base_url` 推导 = 公网地址，会让**任务能否执行取决于 Nginx 与公网链路**。改指回环去掉这层依赖。

### ✅ D6. 站点协议由显式配置决定，不由证书探测决定

**决定**：`site_scheme()` 读 `.env` 的 `SITE_SCHEME`。

**理由**：**配置表达意图，证书只是产物** —— 机器上有证书不等于"现在想用 https"。停用 TLS 后，原来的"有证书就走 https"逻辑会让脚本去测一个没人听的 443。

### ✅ D7. DAG 每个阶段是独立任务 + 恢复用 `all_done`

**理由**：塞成一个大任务，Airflow 就退化成 cron；`all_done` 保证**任一上游失败也恢复实时链路**，否则看板会永久停在暂停状态。

### ✅ D8. 给 stage 任务加 `execution_timeout=45min`

**理由**：原本没有超时。后果比"任务慢"严重 —— **挂死的 stage 会永久占位，而恢复任务依赖它，实时链路会一直停着且无机制救回**。"永久挂住"比"失败"糟得多，因为失败至少触发恢复。依据实测单阶段 3.4~6 分钟。

### ✅ D9. `pause_realtime` 不再吞错误

**理由**：原实现 `compose stop ... >/dev/null 2>&1 && { ... }` 在失败时 `&&` 短路，**既不打印"已暂停"也不打印错误，最后照样报成功**。一个被吞掉的错误最终表现为"任务成功但什么都干不了"。原则：**"什么都没做"与"做成功了"必须能区分开**。

### ✅ D10. 实时链路恢复改用重试判据（最多 180 秒）

**理由**：原来 `sleep 25` 后只查一次。Flink 从 Kafka 位点续跑有时要 1 分钟以上，会出现最糟的形态：**链路正在恢复，任务却被判失败**，而 DAG 已结束、没人再确认。恢复本质是"最终一致"的过程。

### ✅ D11. 内存闸门阈值保持 3000 MB 不变，改用错峰模式适配

**理由**：实测暂停实时链路可释放约 1.65 GB（2282 → 3935 MB）。**调低闸门是把保护拆掉，错峰才是正解。**

### ✅ D12. 修正 AGENTS.md 的 Python 版本错误

**原文**「Python | 3.13 | 数据生成器 / 数据服务」是错的：宿主机实测 **3.12.3**，`3.13` 只属于 data-generator 容器。已拆成两行并说明为什么要拆。

### ✅ D13. Iceberg 的 catalog 命名 `iceberg`，库名保持 `lakehouse_iceberg`

**理由**：实测 `CREATE DATABASE IF NOT EXISTS lakehouse_iceberg` 报
`Cannot create namespace with invalid name:`（冒号后为空）。根因是**库名与已注册 catalog 同名**——
Spark 解析一段名时会先把它当目录名，解析出"目录 + 空命名空间"。
**库名与 catalog 同名时，"建库"这句话没有唯一含义。**
HiveCatalog 的命名空间就是 Hive 库名，库名没有错、不用改，改 catalog 名即可。

**顺带确立的硬约束**：Iceberg 表的引用一律写**三段名**（`iceberg.lakehouse_iceberg.表`）。
因为 Spark 的**两段名 = (命名空间, 表) 且永远属于当前目录**，
不会因为名字看起来像就跳到 Iceberg 目录 —— 只写两段名会静默落到别处，而行数核对读的也是同一个错地方。

### ✅ D14. `spark-defaults.conf` 必须挂载进 `spark-submit`，不能只靠镜像里的 COPY

**理由**：Dockerfile 是构建期 `COPY conf/spark-defaults.conf`，而 spark-submit 是
`docker compose run` 的临时容器，只挂了 `jobs`/`sql`。结果是**改了 conf 等于没改，且没有任何提示**
（D13 的改名就是这样"看起来没生效"了一轮）。挂载后 conf 与 jobs/sql 一样"改完即生效"。

### ✅ D15. 分区表迁移用 DISTRIBUTE BY + 抬高 shuffle 分区数 + 关 AQE 合并

**不采用**"把执行器内存调大"。理由：OOM 的根因是**一个 task 同时持有的分区写入器个数**
（703 个 dt 分区 vs 默认 200 个 shuffle 分区，AQE 又把小分区合并回去），
数据量只有 2 万行 —— 这是结构问题，调大内存只是掩盖症状，分区数一涨还会复发。

### ✅ D16. `restore_realtime()` 增加自愈：等到一半还不好就"取消 + 重新提交"

**理由**：实测批处理结束后实时链路**怎么等都不通过** —— jobmanager 先起、taskmanager 后起（差 5 分钟），
`flink-jobs` 在资源就绪前提交 SQL，部分作业直接 FAILED，而 **FAILED 的作业不会自动重试**。
它不是"慢"，是"死"，与 D10 的"还在恢复"症状完全一样，只能主动做一次才能区分。

## 四、过程中的技术教训（可直接用于论文"踩坑与解决"章节）

| 教训 | 一句话总结 |
| --- | --- |
| 响应头比错误码更有信息量 | 那个 502 **没有 `Server` 头** → 不是 nginx 发的 → 嫌疑从"我们的服务"缩到"链路中间" |
| 结论要跟着证据走 | 关掉 VPN 后明文 30/30 正常，"必须上 TLS"就变成了"当前不必" |
| 被吞掉的错误会伪装成成功 | `>/dev/null 2>&1 &&` 让"暂停失败"显示为"任务 success" |
| 探测路由要用真实存在的端点 | 用 `/airflow/execution/health` 探到 405 而误判方向；用真实端点时 **401 才说明路由存在** |
| 不要手工裁剪框架的依赖集 | 想省掉 `[mysql]` extra，结果连续踩三个坑，官方打包早已配齐 |
| 不要直接改框架的元数据库 | 我用 SQL 删 `dag_run` 行，导致两个 run 并发、内存闸门误判 |
| 版本差异要实测 | `http2 on;` 是 nginx 1.25.1+ 语法，本项目钉 1.24.0 |
| 沙箱加固会咬到子进程 | `ProtectHome=yes` 让 docker 读不到 `$HOME/.docker`，`docker compose` 直接失效 |
| **不要覆盖正在运行的 shell 脚本** | bash 是**边读边执行**脚本文件的。覆盖它会让正在运行的实例按旧偏移读到新内容 → 引号错乱报 "unexpected EOF"。实测：`reconcile` 对账**已经成功**（11458 窗口零差异），却因我在它运行期间覆盖了 `run-batch-pipeline.sh` 而被判失败 —— 一个纯粹的假故障 |
| **不要在 DAG run 进行中修改 DAG 文件** | dag-processor 会重新解析，并**把新增任务注入到正在运行的 run 里**。实测：`archive_behavior` 因此在该 run 中被提前执行，而当时服务器上的脚本还是旧版，报"未知阶段" |
