## 1. 目标

Sprint 6 已经建好了"只读数据服务"：只读账号、SQL 守卫、统一响应信封、
指标口径字典、表结构接口。Sprint 7 要做的是**让数据能被问**：

```text
自然语言问题 → 指标口径检索 → SQL 生成 → 安全检查 → 只读执行 → 带来源的回答
```

这正是 `PROJECT_DESIGN_V1.md` 第 7.1 节写的处理流程。本 Sprint 实现它的
**最小可用形态**（单轮工具调用循环），把"能不能问出正确的数"先做扎实，
多步推理与状态管理留给 Sprint 8 的 LangGraph。

### 1.1 与设计流程的对应关系（两步不在 Agent 进程里）

| 设计步骤 | 实际落点 | 为什么放那里 |
| --- | --- | --- |
| 问题理解 / 指标识别 | `services/agent`（提示词 + `metrics_lookup` 工具） | 需要 LLM |
| 元数据检索 | `services/agent`（`tables_lookup` 工具） | 需要 LLM |
| SQL 生成 | `services/agent`（LLM） | — |
| **SQL 安全检查** | **`services/api/app/sqlguard.py`** | 放在服务端，**Agent 无法绕过**；放在 Agent 里等于让被约束者自己当裁判 |
| **Doris 查询（只读账号）** | **`services/api/app/doris.py`** | Agent 进程里根本没有数据库凭据 |
| 结果分析 / 来源说明 | `services/agent` | 需要 LLM |

因此 Agent 侧的"安全检查"**不是一段代码，而是一条边界**：
它只有一条取数通道，而那条通道是受约束的。

## 2. 架构

```text
┌────────────────────────────────────────────────────────────────┐
│ 浏览器  http://<ip>/data/#/ask                                  │
└───────────────────────────┬────────────────────────────────────┘
                            │ Nginx :80
        ┌───────────────────┴────────────────────┐
        │ /data/          → 静态看板（services/web） │
        │ /data/api/      → uvicorn 127.0.0.1:8000 │
        │ /data/api/query → 同上（只放行 POST）      │
        │ /data/agent/    → uvicorn 127.0.0.1:8100 │
        └───────────────────┬────────────────────┘
                            │
┌───────────────────────────▼────────────────────────────────────┐
│ services/agent（systemd: data-platform-agent，用户 dpagent）      │
│   提示词 + 工具调用循环                                           │
│   工具：metrics_lookup / tables_lookup / sql_query /            │
│         reconciliation                                        │
│   **没有数据库凭据，没有 mysql 依赖**                            │
└───────────────────────────┬────────────────────────────────────┘
                            │ 只经 HTTP 调数据服务
┌───────────────────────────▼────────────────────────────────────┐
│ services/api（systemd: data-platform-api，用户 dpapi）           │
│   只读账号 agent_ro  +  SQL 守卫（仅 SELECT / 表白名单 / LIMIT）  │
│   POST /query  ← Agent 唯一的取数入口                            │
└───────────────────────────┬────────────────────────────────────┘
                            │ MySQL 协议
┌───────────────────────────▼────────────────────────────────────┐
│ Apache Doris（容器）                                             │
│   ecommerce.*      实时链路（分钟窗口）                          │
│   lakehouse_ads.*  离线链路（天 / 分钟）                         │
└────────────────────────────────────────────────────────────────┘
```

**关键设计：进程边界即权限边界。**
Agent 进程里没有数据库凭据，也没有 mysql 客户端依赖。
它能做的查询，与"一个人类用户在浏览器里点看板"能做的完全相同。
于是 `AGENTS.md` 第 10.1 节「Agent 不允许直接拥有数据库管理员权限」
由架构保证，而不是靠代码自觉 —— 想绕过也没有入口。

**为什么两个服务分开部署（不是一个进程两个路由）：**

| 理由 | 说明 |
| --- | --- |
| 故障隔离 | LLM 慢/限流/欠费时只影响问答，看板与只读接口不受影响 |
| 权限隔离 | Agent 单元拿不到数据库凭据 |
| 独立重启 | 换模型/换 Key 只需重启 Agent |
| 依赖隔离 | 两个 venv：升 Agent 的 `openai` 不会影响看板接口 |

## 3. 只读查询节点：`POST /query`

这是本 Sprint 唯一**接受外部 SQL** 的接口，也是安全上最需要说清楚的一处。

### 3.1 请求与响应

```jsonc
// 请求
{ "sql": "SELECT COUNT(*) AS c FROM ecommerce.ads_realtime_trade_1m", "limit": 200 }

// 响应（统一信封）
{
  "data": {
    "rows": [{ "c": 11459 }],
    "row_count": 1,
    "elapsed_ms": 22,
    "executed_sql": "SELECT COUNT(*) AS c FROM ecommerce.ads_realtime_trade_1m LIMIT 200"
  },
  "source": { "tables": ["ads_realtime_trade_1m"], "metric_definitions": [...], "note": "..." },
  "generated_at": "2026-09-26T22:45:03+08:00"
}
```

### 3.2 三道防线

| 防线 | 位置 | 拦住什么 |
| --- | --- | --- |
| ① SQL 守卫 | `sqlguard.validate_select` | 非 SELECT、多语句、注释、DDL/DML、白名单外的表；强制 LIMIT |
| ② 只读账号 | Doris `agent_ro` | 即使守卫被绕过，写操作仍被数据库拒绝 |
| ③ 连接级超时 | `read_timeout=15s` | 慢查询断开，不拖垮集群 |

### 3.3 为什么返回 `executed_sql`

守卫会**改写**语句（补上/收敛 LIMIT）。返回**实际执行的那一条**，
才能满足 `AGENTS.md` 第 10.1 节「Agent 不得伪造查询结果」——
"我查了这句话"必须可核对，而不是靠调用方自述。

### 3.4 为什么这个接口用 POST（其余接口全是 GET）

是**长度**问题，不是语义问题：LLM 生成的 SQL 常带多列与多个聚合，
实测轻易超过 2KB；放查询串会撞上各级代理的 URL 长度限制
（nginx `large_client_header_buffers` 默认 8KB，中间设备可能更小），
表现为"简单问题能问、复杂问题 502"这种最难定位的故障。

Nginx 侧为该路径**单独开精确匹配的 location 并只放行 POST**；
其余路径仍是 `limit_except GET HEAD OPTIONS { deny all; }`。

### 3.5 血缘表名由服务端提取

`sqlguard.extract_tables()` 与校验**共用同一套正则**。
如果让调用方自报读了哪些表，血缘字段就失去可信度；
共用正则还能保证"校验了什么"与"报告了什么"永远一致。

## 4. Agent 实现

### 4.1 工具集合（刻意最小）

| 工具 | 作用 | 权限最小化考量 |
| --- | --- | --- |
| `metrics_lookup` | 查指标口径字典 | 读 `sql/metadata/metrics.md`，无参数风险 |
| `tables_lookup` | 查表结构与分层 | 只读元数据 |
| `sql_query` | 执行只读 SQL | **唯一的取数通道**，受三道防线约束 |
| `reconciliation` | 查批流对账结论 | 回答"数据准不准" |

没有"列出所有表"这类工具：白名单固定（19 张表），
直接写进系统提示词比让模型多绕一轮更省 token 也更稳定。

### 4.2 循环的三条硬约束与落点

| 约束（`AGENTS.md` 第 10.1 节） | 代码落点 |
| --- | --- |
| 不得伪造查询结果 | 回答附 `tables` / `executed_sql` / `steps`，全部可核对 |
| 查询失败必须能重新规划 | 工具失败**不中断循环**，错误文本回交模型改写（见 `tools.py` 的 `_send`） |
| 必须能说明数据来源 | `evidence[].tables` 汇总为 `tables` 随回答返回 |

### 4.3 终止性

- 最多 `AGENT_MAX_TOOL_ROUNDS`（默认 6）轮工具调用；
- 超过或超时后调用 `_finalize()` 强制收尾，且**收尾请求不携带 tools**
  （否则模型还能继续发起调用，循环停不下来）；
- 收尾后在响应里标记 `truncated=true`，让用户知道答案可能不完整。

### 4.4 思考模式默认关闭（有意的取舍）

DeepSeek 的思考模式默认**开启**，官方文档明确写着：

> 携带了 `tools` 参数的请求，在后续所有请求中，必须完整回传
> `reasoning_content` 给 API —— 即使该轮模型未实际进行工具调用。
> 若未正确回传，API 会返回 400 报错。

对"生成 SQL"这个场景，收益与代价不成比例：

| | 思考模式开 | 思考模式关（本项目默认） |
| --- | --- | --- |
| token 成本 | 成倍增加（每轮思维链都要回传） | 基准 |
| 实现复杂度 | 必须严格回传 `reasoning_content`，漏了报 400 | 上下文拼接简单 |
| 可复现性 | 同一问题两次可能生成不同 SQL | 更稳定（配合 `temperature=0`） |

因此默认关闭。代码里由 `assistant_message()` 统一负责回传该字段 ——
即使将来打开，调用方也不需要关心这个细节。

**模型选 `deepseek-flash`**：本项目上下文很短（口径字典 + 表结构 + 一条 SQL），
不需要 pro；flash 支持 Tool Calls，价格约为 pro 的 1/4.5。

## 9. 踩坑记录

### 9.1 同一台机器上两个服务目录都叫 `app`，无法同时导入

`services/api/app/` 与 `services/agent/app/` 是两个独立部署单元，
但包名相同，Python 里无法同时按 `app.*` 导入。

**处理**：`tests/conftest.py` 统一让 agent 目录优先；
跨服务行为由 HTTP 冒烟测试覆盖（那才是它们真实的交互方式）。
已确认现有 `services.api.app.*` 的导入不受影响。

### 9.2 新增路由后忘了重启数据服务 → 404

Sprint 7 给数据服务加了 `POST /query`。部署脚本最初只重启 Agent，
数据服务仍在跑旧代码 → Agent 提问收到 404，而两个服务状态都显示 active。

**处理**：`deploy-agent.sh` 现在**一并重启数据服务**（它无状态，代价几百毫秒），
并在注释里写明原因。

### 9.3 前端把绝对路径当相对前缀，拼出了 `/data/api/api/...`

`<meta name="api-base" content="/data/api">` 给的是**绝对路径**。
重构时把它当成"相对前缀"又拼了一次 `/api`，整站所有请求 404 ——
表现为看板全页报错，看起来像后端挂了。

**处理**：显式定义 `API_BASE` 与 `AGENT_BASE` 两个**完整基址**，
`buildUrl(base, path, params)` 只拼一次，注释里写明"绝不能再叠前缀"。

### 9.4 `set -o pipefail` + `grep -q` 会把"命中"变成失败（最隐蔽的一个）

```bash
printf '%s' "$大字符串" | grep -qF -- '关键字'   # 明明命中，if 里却是假
```

退出码实测 **141**。原因：`grep -q` 命中后**立即退出**并关闭管道读端，
此时 `printf` 还没写完，于是 printf 收到 SIGPIPE 而死（141）；
在 `pipefail` 下管道整体取"最后一个失败者"，于是返回 141 而不是 grep 的 0。

- 影响范围：凡是"大输入 + 提前退出的过滤器"都会中招；
- 为什么只有验收脚本中招：它 source 了 `scripts/lib/common.sh`，而后者开了
  `set -euo pipefail`；同样的命令写在临时脚本里（没开 pipefail）就正常 ——
  这正是它难排查的原因；
- 处理：`_contains()` 内部临时 `set +o pipefail`，脚本其余部分保持开启。

### 9.5 用 JSON 的空白假设去断言，会误判成"功能坏了"

FastAPI 默认输出**紧凑 JSON**：`{"code":"NOT_SELECT"}`；
而手写与 `python -m json.tool` 是 `{"code": "NOT_SELECT"}`。
断言写死带空格的版本 → 真实响应永远匹配不上，
表现为"拒绝原因不正确"，而守卫工作得好好的。

**处理**：`normalize_json()` 去掉分隔符后的空白再比对。

### 9.6 归一化不能用在源码上

上面的 `normalize_json()` 一旦被用到**源码文本**上，
源码里的 `key: 'ask'` 会被改成 `key:'ask'`，再也匹配不上。
因此拆成两个函数：`check_contains`（JSON 响应，先归一化）与
`check_in_source`（源码，原样匹配）。

> 9.4 ~ 9.6 是同一类问题：**断言本身写错，却表现为产品缺陷**。
> 这类问题的危害比"没有断言"更大 —— 它会让人去改本来正确的产品代码。
> 因此每条都写清了"为什么这么写"，而不只是把代码改对。

### 9.7 公网访问偶发 502 —— 请求根本没到服务器（已解决）

实测客户端经公网访问约 15~40% 概率收到 502。逐项排查：

| 判据 | 实测 |
| --- | --- |
| nginx 访问日志里的 5xx | 只有 22 条 503（是早前 Doris 内存事故期间 API 返回的），**无 502** |
| `TcpExtListenOverflows` / `ListenDrops` | 0 / 0 |
| `TcpInErrs` | 0 |
| 服务端自测连续 5 次 | 全部 200 |
| `somaxconn` / listen backlog | 4096 / 511（均充裕） |
| **那个 502 的响应头** | **没有 `Server` 头、响应体为空** —— nginx 的 502 必带 `Server: nginx/1.24.0` 与 HTML 错误页，所以**它不是 nginx 发的** |

**结论**：502 不是 nginx 产生的，请求在到达服务器之前就被中间设备改写了
（客户端本机跑着 VPN 代理，出口节点是可疑的一环）。

- 影响：演示时页面可能随机失败，看起来像前端坏了；
- **已解决（2026-09-26）**：站点启用 HTTPS（TLS 终止在 nginx），
  加密后中间设备既看不到 URL 也改不了响应体。
  公网实测 **64/64 全部 200**。完整处置见
  [`SPRINT_6.md` 第 8 节](SPRINT_6.md)（改的是服务层入口，故记在那里）；
  备用手段（网络受限时）：`ssh -N -L 18080:127.0.0.1:443`，
  然后访问 `https://127.0.0.1:18080/data/`。
